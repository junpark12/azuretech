Scope: deployment guidance and a separate upgrade observation

Confidential Virtual Machines (CVMs) add a hardware-enforced boundary around an AKS node. They are useful when sensitive workloads must reduce their trust in the cloud host and hypervisor without being rewritten for an enclave SDK. They do not make every container a separate trusted execution environment, secure an application automatically, or remove normal Kubernetes operating responsibilities.

Evidence boundary. This article translates and corrects a September 2026 engineering guide. Regional and quota observations originated on September 15, with configuration and selected capability checks updated on September 17. They are historical, subscription-specific observations, not official availability commitments. The provisioning walkthrough targets Azure Linux 3; the recorded Kubernetes upgrade used Ubuntu 24.04. No new cluster deployment, upgrade, quota request, performance test, or shutdown timing measurement was performed for this publication. Recheck current official support, subscription restrictions, quota, and allocation capacity before deployment.

The practical starting point is an ordinary System pool and a CVM User pool, with workload-specific placement rules and no custom dedicated taint on the CVM pool. This is an operational baseline, not an exclusivity or high-availability guarantee. The article covers the trust boundary, cost, maintenance, OS disk choices, regional discovery, quota planning, deployment, migration, and what the shutdown sample actually established.

Three protections, three different jobs

ProtectionWhat it addressesWhat it does not establish
CVMData in use: VM memory and execution state protected from the hypervisor and host management code through supported AMD SEV-SNP hardware and a CVM-specific node image.That an application cannot be compromised, or that mutually untrusted Pods are isolated from each other by hardware.
Disk encryptionData at rest. Azure Managed Disks use server-side encryption with platform-managed keys by default; customer-managed keys are a separate configuration choice.Protection for plaintext in an application process, TLS in transit, or automatic activation of every confidential disk encryption option.
Application and platform securityVulnerability management, least privilege, secret handling, image provenance, network restrictions, and safe logging.These controls remain necessary even on a CVM node.

TLS protects data in transit; CVM protection addresses a different stage of its lifecycle. Persistent Volumes, external databases, an ingress proxy on an ordinary node, and a logging destination outside the CVM are not automatically brought inside its boundary. Trace sensitive data from ingress and TLS termination through processing, storage, telemetry, and backup.

The node VM is the trust boundary

The AKS CVM documentation explicitly places all Pods on a CVM node in the same trust boundary. The guest OS, kernel, kubelet, node agents, and application Pods share that VM boundary. Kubernetes administrator access, guest root, privileged containers, and vulnerable agents still matter. CVM is not Pod Sandboxing and is not a per-Pod TEE.

This can help address requirements concerning infrastructure-operator access to sensitive customer, financial, or regulated data while retaining Deployment, Service, and scaling patterns. It does not itself deliver certification or regulatory compliance. Application code may remain unchanged, but scheduling, storage, availability, and OS-dependent integrations still require testing.

Attestation and secret release are not intrusion detection

A vTPM protects keys and boot measurements. Attestation verifies evidence about the execution platform and its security configuration. Azure uses platform attestation in the CVM lifecycle; an application-specific policy that releases a secret only to a verified environment is a separate design. You do not need to implement that application policy merely to create a CVM node pool.

Where required, connect guest attestation to a deliberately designed secret or key-release policy, including identity, verification, authorization, and renewal behavior. Do not describe this as a mechanism that automatically detects an application compromise and locks its memory again: a successful attestation does not prevent later application vulnerabilities or credential misuse. See the confidential VM overview.

System pools, User pools, and honest placement rules

System/User describes the pool's role; CVM/ordinary VM describes its hardware protection. CVM is not inherently User-pool-only. A System pool can use a supported CVM SKU and OS when all System-pool and CVM constraints are satisfied. Protecting the System pool may be appropriate if its components process information included in your threat model, but it is not required for a CVM User node's memory protection.

A System pool is also not the AKS managed control plane. Changing its VM size or protection does not turn the managed API server or etcd into your CVM node pool. Current System-pool documentation requires Linux, support for at least 30 Pods, at least 4 vCPUs and 4 GB memory per VM, and at least two System nodes; three are recommended. The one-node System pool in the later historical lab observation is not a production sizing recommendation.

PoolIntended usePlacement responsibility
Ordinary System poolCentral system services such as CoreDNS and metrics-server.Pool mode influences scheduling but does not by itself enforce all desired placement.
Ordinary User pool, if neededGeneral applications that do not require confidential compute.Give those applications their own pool selectors when they must stay off CVM nodes.

Do not accidentally exclude required node agents

Network and CSI node drivers must be present where their node-level functions are required. Log and metric collectors may also need a DaemonSet on each CVM node. Central CSI controllers and metrics-server need not run on every node. App Routing and other add-ons must be evaluated by the actual controller and data-path roles, not their names or namespaces.

The no-custom-taint baseline avoids unintentionally blocking required agents and add-ons. A taint is not needed to enable CVM protection. Conversely, neither kube-system membership nor being a DaemonSet exempts a Pod from arbitrary custom taints. If you introduce a taint, verify each component's supported tolerations; hand-editing a managed DaemonSet can be undone by reconciliation or upgrades. See taints and tolerations.

Node Ready is only the first check. Validate DNS, cross-Pod communication, PVC attachment and read/write, metrics, logs, and routing. Restrict who can deploy privileged agents or edit scheduling rules. An untrusted privileged workload on the same CVM node is still inside the shared guest trust boundary.

A selector constrains one workload, not the whole pool

# Merge into the sensitive Deployment's spec.template.spec.
nodeSelector:
  kubernetes.azure.com/agentpool: REPLACE_WITH_CVM_POOL

# For a different, ordinary workload, use its own ordinary User pool instead:
# nodeSelector:
#   kubernetes.azure.com/agentpool: REPLACE_WITH_GENERAL_POOL

Replace the placeholder with the real pool name; Kubernetes does not expand shell variables in a manifest. A nodeSelector is a required scheduling constraint. If no suitable CVM node is available, a newly scheduled Pod remains Pending instead of falling back to an ordinary pool. Existing selectors and required node affinity must also be satisfied.

This is not exclusive reservation. Other eligible Pods, including applications without selectors, can still land on the CVM pool. Manage ordinary workload placement too; use admission policy where enforcement is required. A label is neither cryptographic attestation nor per-Pod isolation. Changing this example does not remove any taints already present on an existing pool.

Maintenance: design for restart and recovery

The DCasv5 specification lists Live Migration and Memory Preserving Updates as unsupported. Do not depend on moving a running process to another host while preserving its execution state. Compared with a configuration that can successfully use live migration, some host maintenance can require application restart or advance application-level failover.

Operational possibility, not measured frequency. The source did not measure how often CVMs restart. This is not a claim that every update reboots a node, that a prior Freeze count becomes an equal number of CVM reboots, or that ordinary VM live migration always succeeds. A failed host may provide no opportunity for migration at all.

Unresolved v6 discrepancy: on September 17, the source AKS SKU response reported MemoryPreservingMaintenanceSupported=True for Standard_DC4as_v6 and Standard_DC4ads_v6. The public DCasv6 and DCadsv6 specifications retrieved for this article still list both Live Migration and Memory Preserving Updates as unsupported. These are different evidence sources, not a resolved support statement. Ask Azure Support what applies to the exact AKS SKU, image, region, and maintenance event. That API field does not prove Live Migration support.

Design for a service that survives process restart, rather than merely tolerating a brief pause. Use replicas, placement across appropriate failure domains, durable external state, idempotent retries, and a maintenance plan. A PodDisruptionBudget can constrain supported voluntary evictions during normal drain; it cannot stop hardware failure, enforce a platform maintenance deadline, or prevent a VM reboot.

EventShutdown opportunityImportant limit
Normal AKS node-pool upgradeCordon/drain and normal Pod termination allow signal handling, a suitable grace period, and an optional preStop hook.Application cleanup still has to finish within the available budget.
Platform RedeployAKS node auto-drain attempts cordon and drain.Best effort: insufficient notice, deadlines, or failures can prevent completion.
Platform RebootThe AKS node auto-drain table specifies no action.Guest OS/kubelet shutdown behavior is separate; do not assume every Pod receives its full grace period.

See AKS node auto-drain and Scheduled Events. When notice is available, stop accepting work, complete suitable in-flight work, persist checkpoints, release connections, and hand off roles. terminationGracePeriodSeconds controls Kubernetes' normal Pod termination budget; it does not force Azure to postpone platform maintenance for that duration.

Graceful shutdown helps clean up before interruption. Replication, external state, and retries help when cleanup is impossible. You need both.

Do not generalize the DCasv5 limitation into “CVM never supports Ephemeral OS Disk.” Hardware local storage, a supported ephemeral placement, AKS image support, and a suitable OS disk size are distinct checks. Ephemeral OS disk writes reside on local VM storage and are not durable across events such as redeployment or reimage. Keep application state on appropriate durable storage.

Request quota only when necessary

  1. Open Azure Portal Quotas, choose Compute, and filter to the intended subscription and region.
  2. Select the exact VM family and request the desired final limit, including existing usage and planned headroom.
  3. If direct adjustment is unavailable or denied, use the support workflow with the region, SKU, requested vCPU limit, and intended use.
  4. After approval, reread both family and Total Regional vCPU limits and usage. The official quota process says family approval automatically increases regional quota, but verify the resulting headroom before deployment.

The following optional command submits a real quota change request; it is not a read-only check. Do not run it where the current quota is already sufficient. Set a final limit justified by your plan, not an increment or a value lower than your current limit.

az quota update --scope "$SCOPE" --resource-name "$FAMILY" \

Migrate gradually

  1. Establish the CVM pool and verify networking, storage, add-ons, and observability.
  2. Merge the desired selector into each sensitive workload and roll it out, retaining other necessary scheduling constraints.
  3. Verify real Pod placement, service behavior, PV access, throughput, latency, and logs.
  4. Move workloads incrementally with appropriate replicas, disruption budgets, and storage-zone compatibility.
  5. Keep a rollback path before retiring the old pool. Do not delete or drain it merely because new nodes report Ready.

Understand Kubernetes' termination budget

In the normal Pod termination flow, kubelet initiates local shutdown and the container runtime normally signals PID 1. A configured preStop hook consumes the same grace budget before the stop signal; it does not get another independent 30 seconds. This sample has no such hook. Remaining processes can be forcefully killed when the grace period expires. Kubernetes documents edge cases, including a small one-off extension for a still-running preStop hook and restarted termination handling; do not treat 30 seconds as a universal wall-clock stopwatch for every failure mode.

Readiness and endpoint propagation happen through separate control loops. Because the sample has no Service or traffic test, there is no evidence here about end-to-end traffic removal or request loss. Adding a single-replica PDB could block the intended drain and would change the experiment; it has deliberately not been added.

Collect the missing evidence in a separately authorized lab

  1. Verify all three selectors, initial Pod identities, image identity, Ready state, and the 30-second grace setting before a planned test.
  2. Use an independent persistent log destination, or an observation tool that reconnects when the API connection drops. Node-local logs can disappear during reimage; deleted Pod logs may no longer be retrievable through kubectl.
  3. Correlate each original Pod's shutdown_started and shutdown_completed timestamps and elapsed field with the container runtime termination reason and exit code.
  4. Track replacement Pod identity, placement, readiness, and restart counts separately. If evaluating service continuity, design an appropriate traffic and availability test rather than assuming this manifest supplies one.
  5. Redact runtime Pod/node names and infrastructure details before sharing collected logs. A later standalone Pod-deletion experiment is additional evidence, not a reconstruction of the missing upgrade evidence.

Adopt CVM for the right threat model

CVM is valuable when the requirement includes protecting data in use from cloud-host access. If the immediate objective is general web-application security, identity, patching, secret management, and network controls may be higher-priority work. Treat confidential compute as an additional layer, not a substitute.

  • Define the VM-level trust boundary and map every sensitive data path, including ingress, storage, and telemetry.
  • Use a supported CVM size and OS image; separate Azure Linux 3 guidance from Ubuntu-based measurements.
  • Start with ordinary System and CVM User pools when appropriate, then validate actual add-on and workload placement. Selectors do not reserve a pool exclusively.
  • Verify SKU visibility, AKS eligibility, quota, zones, and capacity independently, including scale-out and surge headroom.
  • Resolve the v6 maintenance and DCasv6 ephemeral-disk evidence conflicts for your exact configuration before relying on those features.
  • Benchmark complete service behavior and total cost. Design for restarts and interrupted cleanup, not assumed live migration or a promised shutdown window.
  • Use the sample as a lab-only observation aid. Do not promote its successful upgrade result into a graceful-shutdown, zero-downtime, or HA guarantee.
