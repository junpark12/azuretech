Unofficial lab guide, not a Microsoft service guarantee. This English article distinguishes current documented behavior from historical observations and untested tuning hypotheses. The source review checked Microsoft Learn on September 17, 2026, including the policy reference dated August 18, 2026. This editorial work did not redeploy resources or rerun Azure experiments. Detection rate, latency, call count, HTTP status, and stream termination examples are not SLAs.

Important correction: the documented default response window is 1,000 characters, not 10,000. The request window is 10,000 characters and cannot be changed with window-size. Explicit historical response settings of 3,000 and 10,000 characters remain examples, not defaults.

The downloadable base-policy.xml and its matching policy-payload.json are passthrough baselines with no Content Safety policy. Review inherited policies separately. Deploying those files alone does not add this protection.

1. Architecture and the streaming contract

The client sends a chat-completions request through Azure API Management (APIM) to an Azure OpenAI or compatible Foundry model deployment. An inbound llm-content-safety policy can inspect the prompt; an outbound instance can inspect the generated response. The policy does not perform classification locally: it calls a separate Azure AI Content Safety resource through a dedicated APIM backend entity.

  1. Configure model routing with set-backend-service and authenticate APIM to the model with authentication-managed-identity.
  2. Optionally inspect the inbound request using Prompt Shields, harm categories, and blocklists.
  3. Forward the backend response with buffer-response="false" for Server-Sent Events (SSE).
  4. Place llm-content-safety in outbound to buffer and evaluate streaming text using a sliding window.

The model and Content Safety backends need separate configuration and authorization. Request and response inspection can use different categories, thresholds, or blocklists. For a streaming policy violation, the documented stream handler stops forwarding subsequent events rather than returning a 403. Text already delivered to the client cannot be retracted. Authentication errors, inbound rejections, and backend failures can still produce other HTTP results; this is not a promise that every streaming request returns 200.

This is a manual Bash/WSL lab, not an unattended deployment script. Read each step before execution. Resource creation incurs cost, and a policy PUT replaces the policy at that scope. }

5. Policy attributes and documented semantics

<llm-content-safety backend-id="content-safety-backend"
                    shield-prompt="false"
                    enforce-on-completions="false"
                    window-size="3000"
                    window-overlap-size="500">
    <categories output-type="EightSeverityLevels">
        <category name="Hate" threshold="4" />
        <category name="SelfHarm" threshold="4" />
        <category name="Sexual" threshold="4" />
        <category name="Violence" threshold="4" />
    </categories>
    <blocklists>
        <id>pii-known-values</id>
    </blocklists>
</llm-content-safety>

This is an illustrative policy fragment, not a complete deployment. Keep children in the documented order: categories before blocklists. The policy can appear multiple times in one policy document. Supported sections are inbound and outbound, not backend or on-error; documented scopes include global, workspace, product, and API.

5.1 Policy attributes

AttributeMeaningRequired/default
backend-idThe APIM backend entity used to call Content Safety. Policy expressions are supported.Required; no default.
shield-promptEnables prompt-attack/jailbreak inspection when true.Optional; false.
enforce-on-completionsWhen the policy is inbound, also evaluates completions. Ignored when the policy is outbound. Do not infer streaming coverage from this attribute alone; validate explicit outbound inspection.Optional; false.
window-sizeText window size in characters for evaluation. Configurable only for responses; requests use 10,000 characters. Policy expressions are supported. This does not specify exact flushing, internal character representation, or call count.Optional; response default 1,000.
window-overlap-sizeCharacters shared by adjacent inspection windows. Without overlap, a pattern spanning a logical inspection boundary can be missed.Optional; no overlap when omitted.

5.2 Categories and inclusive thresholds

SettingDefinition
categoriesOptional container of category rules.
output-typeDefaults to FourSeverityLevels, with outputs 0, 2, 4, 6. EightSeverityLevels returns 0 through 7.
category.nameRequired per rule: Hate, SelfHarm, Sexual, or Violence.
category.thresholdRequired per rule. The current documented comparison blocks severity greater than or equal to the threshold. Values below it are allowed. Thresholds run from 0 (strictest) to 7 (most permissive).

With threshold 4, EightSeverityLevels blocks 4–7, and FourSeverityLevels blocks its returned values 4 and 6. Finer-grained output does not guarantee better accuracy or a different decision for a particular input. Threshold 0 can reject even content scored 0.

5.3 Blocklists, regular expressions, and safe fixtures

blocklists is an optional container of id references to lists registered on the Content Safety resource; APIM does not create the list. IDs support policy expressions. Lists can handle organization-specific terms, known sensitive values, or format patterns that the four harm categories do not represent. This is not a complete PII detector or a guarantee against disclosure: test spelling changes, normalization, boundary behavior, and service failures.

Regex is supported: the Content Safety REST 2024-09-01 TextBlocklistItem schema includes optional isRegex. When true, text is a regular expression; false or omitted creates a plain-text item. Do not assume plain-text matching is identical to a case-sensitive substring comparison. Test case, word boundaries, normalization, and inspection boundaries. This corrects the older claim that blocklists could not use regex.

{
  "blocklistItems": [
    { "description": "Plain-text example", "text": "hate" },
    { "description": "Regex example", "text": "b[i1][a@][s\\$]", "isRegex": true }
  ]
}

There is no dedicated blocklist command in the reviewed core Azure CLI. Use the Content Safety data-plane REST API. Where disableLocalAuth=true, use an Entra token rather than an account key. 5.4 Streaming behavior: evidence and current debug tracing

Historical, environment-specific evidence: the 200/403 comparison, first inspected segment of 198 characters, 14-byte download, and data: [DONE] below belong to particular past requests. They are not guaranteed across gateways, models, or policy versions. The requests generated different model responses, not the same controlled byte sequence. Sanitized fixture lengths need not match the original observed lengths.

The documented sliding-window handler buffers events and stops subsequent event forwarding when it detects a streaming violation. It does not issue a 403 for that streaming violation. The same policy reference separately describes 403 responses when requests or responses exceed Content Safety character limits. A small response window does not prove every length-related error impossible.

Do not infer exact service calls from arithmetic: 11,000 characters with a 1,000-character window does not establish exactly 11 windows or 11 Content Safety calls. Overlap, SSE and message structure, trailing text, retries, and implementation details can matter. This corrects an unverified inference in the earlier lab narrative.

Why status and headers cannot identify the blocking component

The source observed x-ms-rai-invoked: true on successful requests too. That header alone does not prove that the model's native content filter caused a rejection. Correlate the request with APIM policy tracing to distinguish APIM Content Safety from model filtering, authentication failures, limits, and unrelated errors.

5.5 Window size, overlap, boundary detection, and streaming latency

Tuning hypotheses and an experiment design—not new benchmarks or official recommended values. Larger windows do not make detection accuracy increase monotonically. Detection, context preservation, perceived responsiveness, end-to-end time, analysis volume, and cost are separate outcomes. Measure them together for the actual gateway, model, overlap, and load.

ChangePossible benefitPossible cost or limitation
Increase window-sizeA longer string, pattern, or context may fit within one analysis segment.Accumulating text may delay first content or later delivery. More context does not guarantee a more accurate classification.
Decrease window-sizeSmaller segments may become available for inspection and release sooner.More frequent inspections can add service latency, throttling pressure, and cost. A smaller window is not always faster.
Increase window-overlap-sizeMay reduce misses when a pattern spans adjacent inspection windows.Repeatedly analyzes some text; analysis volume, call frequency, latency, or cost may rise. Actual calls must be observed, not assumed.

window-size sets the analysis segment size; window-overlap-size sets how much adjacent segments share. They are not interchangeable knobs. Settings such as 1,000/200 and 3,000/500 characters are comparison candidates, not universal recommendations.

A boundary example: LAB_BLOCK_ / MARKER

Registered literal: LAB_BLOCK_MARKER

Logical inspection window A: ... LAB_BLOCK_
Logical inspection window B: MARKER ...

If neither independently inspected segment contains the full literal, a match may be missed. This illustrates a logical inspection-window boundary, not a claim that splitting a network packet or SSE event necessarily causes a miss. The gateway may assemble text across transport events before evaluating it. Test those boundaries separately.

  • Choose overlap with the length of the text that must match and its required surrounding context in mind, not the number of characters in the regex source code.
  • Variable-length regex matches and long-context decisions may not fit a fixed overlap. Whitespace, normalization, alternative spellings, and format variations add separate coverage gaps.
  • Overlap can reduce a boundary risk but cannot guarantee all detections. Larger windows alone do not eliminate boundary effects.
  • Even if a later inspection stops transmission, the prefix already delivered cannot be recalled. This policy alone cannot promise that no sensitive fragment is ever exposed.

Why streaming can feel bursty

Waiting for enough text and then waiting for Content Safety can turn incremental output into pause → batch delivery → pause. The exact flush trigger and batch size are not established here. A large window's accumulation time competes with a small window's potentially more frequent inspection overhead. Compare window and overlap together instead of treating a smaller window as a guaranteed latency optimization.

MeasurementWhat to record
Time to first contentTime from request start to the first nonempty content delta, not first HTTP headers or an empty SSE event.
Content-delta interarrival timesGaps, long pauses, and batch delivery patterns. Compare repeated-run p50 and p95, not just the mean.
End-to-end timeRecord normal completion, blocking, disconnects, and timeout separately. A short response stopped by a block is not a performance improvement.
Boundary detection and missesPlace the same synthetic literal or pattern before, across, and after expected logical boundaries; vary overlap while holding the content fixed.
Service calls, analysis volume, errors, and costUse available service metrics and minimal trace metadata to measure calls/analysis volume, 429s, failures, and cost. Dividing character count by window size is not a measured call count.
  1. Start with a controlled test backend replaying fixed synthetic SSE output; keep content, output length, and event timing fixed while moving the marker relative to likely inspection boundaries. This isolates buffering from model variability. The source supplies a design, not a ready-made replay server.
  2. Compare a passthrough baseline with no added safety policy against several window/overlap combinations. Keep input, output length, concurrency, and relevant environment settings constant, and repeat runs.
  3. Then test actual model generation separately. A model can change whether, where, and in what format it emits the marker, so two model calls are not a controlled same-output experiment.
  4. Keep the tested blocklist out of inbound when testing outbound; otherwise the prompt can be blocked before generation. Use synthetic fixtures only.

The source's proposed overlap of 10–20%, with examples of 300–500 characters for a 3,000-character window, is an experimental starting point, not an official ratio. Evaluate missed boundary matches alongside repeated-analysis overhead. No exact call-count guarantee or measured latency distribution is supplied.

Character-counting limitation: the historical author observed ASCII and Hangul characters behaving as one character each. Both are in the Basic Multilingual Plane, so this cannot distinguish Unicode code points from UTF-16 code units. Emoji, supplementary-plane characters, and combining characters were not verified. Do not transfer the REST blocklist item's code-point length definition to APIM's streaming implementation. Compare UTF-8 bytes, Python len(), and the actual analyzed segments separately.

5.6 Large inbound requests: coding and agent workloads

Agent requests can combine a long system prompt, tool definitions, history, file content, and diffs. One source observation described a coding-agent request with 10 tools and an approximately 67 KB JSON body. An earlier description of approximately 67,000 characters lacked a separate character count; bytes and characters are not interchangeable.

Documented limit versus unexecuted experiment: the policy reference describes a 10,000-character request window and a 403 when Content Safety character limits are exceeded. It does not establish here that all messages and tools are serialized into one undivided inspection string, or that automatic splitting never occurs. JSON byte size alone cannot predict rejection. The following is a validation design, not a newly measured cutoff or a reproduction of the original 67 KB tool-schema request.

  1. First reduce unnecessary context and tool-schema bulk; explicitly define allowed request size and how to handle excess. Do not automatically disable inbound safety to avoid length errors. Changing shield-prompt or harm thresholds is not a length-limit workaround.
  2. Use outbound inspection as an additional layer, not proof that length errors cannot occur. Outbound-only protection removes input-stage protection against attacks and harmful input; document that gap in security review.
  3. A custom inspection design needs structured JSON parsing, splitting, and failure handling. Inspecting only the last user message omits system messages, history, and tools and is not equivalent to inspecting the full request.

Policy parsing errorElement order or a fragment incorrectly deployed as a full policy.Put categories before blocklists; merge fragments into the proper existing section and preserve the full policy envelope.
