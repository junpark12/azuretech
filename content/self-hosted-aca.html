What this design solves

A GitHub-hosted runner is convenient until a workflow needs a private database, an internal API, a controlled outbound path, or a carefully maintained toolchain. An always-on self-hosted VM solves some of those requirements but adds idle compute, patching, and capacity management. This guide uses event-driven Azure Container Apps Jobs to start an ephemeral GitHub Actions runner when a matching job is queued.

The design combines a workload-profiles Container Apps environment, its Consumption profile, a dedicated infrastructure subnet, Azure Firewall and a user-defined route, private endpoints for Azure Container Registry and Key Vault, and a GitHub App rather than a long-lived personal access token. A small Express application provides a concrete deployment target: the runner authenticates to Azure using its managed identity and performs an App Service zip deployment.

This is a sanitized technical reconstruction, not a claim that these public examples were deployed. The source records successful end-to-end deployment after several configuration fixes. Its earlier progress notes, example snippets, README, and archived proposal describe different stages. The instructions below reconcile those stages, identify repairs, and exclude original account details and screenshots.

Ephemeral means the registered runner accepts one job and is then discarded. It does not mean an untrusted workflow is safe, an execution is guaranteed exactly once, or every Azure resource becomes free at idle. The runner can reach its authorized private services and managed identity while executing; restrict who can submit work to it.

The complete execution and authentication flow

  1. An authorized user dispatches a workflow. GitHub queues a job with runs-on: [self-hosted, container-app].
  2. The managed KEDA GitHub runner scaler polls the configured repositories using GitHub App credentials. It enumerates workflow runs and queued jobs, applying scope and label filters.
  3. A nonzero eligible queue causes Container Apps to create job executions, subject to the event configuration and platform limits. The example uses one replica per execution and one required successful replica.
  4. Container Apps pulls the runner image from private ACR and resolves the Key Vault-backed secret using the job identity. Private DNS and authorization must work before the runner script can help.
  5. The startup script signs an RS256 JWT using the GitHub App private key. It exchanges that JWT for an installation access token, then exchanges the installation token for a runner registration token.
  6. The runner registers at the repository or organization URL with its custom label and --ephemeral. Organization scope can additionally use a restricted runner group.
  7. GitHub assigns an eligible job. The workflow checks out source, selects Node.js, installs locked dependencies, packages only application files, and deploys through Azure managed identity.
  8. The runner reports its result and exits after one job. When no eligible work remains, no further executions are requested with min-executions=0. Preserve diagnostic logs before ephemeral storage disappears.

Private access is not the same as internet egress control

The Container Apps environment is attached to a VNet. Its infrastructure subnet is exclusively reserved for that environment; do not place a VM, another environment, an App Service integration, or even a private endpoint in that subnet. Create separate subnets for private endpoints and Azure Firewall. Size them for platform reservations and expected scaling rather than treating the minimum prefix as a capacity recommendation.

A workload-profiles environment supports the UDR/firewall design used here. Its Consumption profile can still run serverless jobs. Do not confuse that with a legacy Consumption-only environment, whose networking capabilities differ. The selected profile controls compute behavior; VNet connectivity, DNS, routes, network security rules, and service authorization determine which private resources the workload can actually reach.

  • Internal environment: avoids an internet-facing environment ingress endpoint. Jobs do not need an inbound HTTP endpoint. Internal-only is not a blanket denial of all VNet traffic and does not itself create a forced-egress route.
  • Default route: an infrastructure-subnet 0.0.0.0/0 UDR with VirtualAppliance next hop sends matching outbound traffic to the firewall. More-specific system, peering, gateway, or user routes can take precedence.
  • Private endpoints: ACR and Key Vault data-plane access uses their private IPs when DNS resolves correctly. The associated private DNS zones must be linked or forwarded to the client's VNet.
  • Private databases and APIs: require actual VNet peering or VPN/ExpressRoute connectivity, correct return routes, DNS resolution, destination firewall rules, and application credentials. A default internet route does not provide that connectivity.
  • SCM deployment: reaching App Service's public site is not proof that the runner can reach its SCM/Kudu endpoint. An App Service private endpoint provides inbound access to the app and SCM with suitable DNS. App Service VNet integration instead concerns the web app's outbound connectivity.

For an inspected private-network path, add a more-specific route to the firewall where necessary, permit only the required destination prefixes and ports, and ensure symmetric routing. For direct peering, use the peering-generated system routes; VNetPeering is not a user-defined-route next-hop type. A gateway route is appropriate only when a compatible gateway path actually exists. Never invent a next hop to bypass a required inspection boundary.

Create the GitHub App and choose runner scope

  1. Open the appropriate account or organization's Settings, Developer settings, GitHub Apps, and create an app. Give it an approved descriptive name and a legitimate homepage. A webhook is unnecessary for this polling design, so disable it.
  2. For the repository-scoped example, request Actions read access for polling, Administration read/write for runner registration, and mandatory Metadata read access. For organization-scoped runners, add Organization Self-hosted runners read/write. Confirm exact permissions against the GitHub REST endpoint and the KEDA version supported by your Container Apps environment.
  3. Record the numeric App ID, generate a private key, and keep the PEM in approved secure storage. The App ID is not the same as the installation ID or a client ID.
  4. Install the app on the intended owner and only the repositories it needs. Record that installation ID. An app definition without an installation cannot issue usable installation access tokens for this workflow.
  5. For an organization, create a runner group that allows only approved repositories and workflows as supported. Keep privileged deployment runners away from untrusted public-repository work.
  6. If app permissions change after installation, have the installation owner review and accept the new request in Installed GitHub Apps. Editing the app definition does not automatically elevate an existing installation.

The source also tried Actions write and Workflows write permissions. They are not a baseline requirement for simply reading queued jobs and registering a runner. Workflows write is relevant to modifying workflow files, which this sample does not do. Grant additional permissions only for an identified operation, not to suppress an unexplained error.

Prepare the runner image and hardened startup script

The downloads contain a complete non-root Ubuntu runner Dockerfile and start.sh. The image supplies curl, Git, jq, OpenSSL, zip/unzip, runner runtime dependencies, and Azure CLI. The application itself is not baked into this image: GitHub checks it out for each job, and App Service hosts the resulting Node application.

The provided local source snapshot already includes Azure CLI and zip in its Dockerfile. An older archived, unmerged proposal instead added conditional installation using sudo inside the workflow. That proposal is not treated as merged. Installing these prerequisites during a trusted image build is appropriate here because the runner executes as an unprivileged user and the deployment should not depend on sudo being available.

JWT and token exchange details

The script creates an iat value 60 seconds in the past to allow modest clock skew and an exp value 540 seconds in the future, then signs an RS256 JWT. This stays within GitHub's short JWT lifetime model. It calls POST /app/installations/{installation_id}/access_tokens with Authorization: Bearer ${JWT}, followed by the scope-specific runner registration endpoint with the installation token.

The original script already uses the GitHub App JWT in its token-exchange authorization header. The public download preserves that authentication flow and strengthens its handling: it requires nonempty inputs, validates owner/repository/scope formats, bounds connection and request time, checks successful HTTP status and nonempty token fields, and never prints response bodies. Signing or token errors fail closed, with additional validation before runner configuration.

# This is the key authentication sequence, not the whole startup script.
INSTALL_TOKEN=$(request_token \
  "app/installations/${GITHUB_APP_INSTALLATION_ID}/access_tokens" \
  "$JWT" "Installation token")
REG_TOKEN=$(request_token "$REGISTRATION_PATH" "$INSTALL_TOKEN" \
  "Runner registration token")

./config.sh --unattended --name "runner-$(hostname)" \
  --url "$RUNNER_URL" --token "$REG_TOKEN" \
  "${GROUP_ARGS[@]}" --ephemeral --labels "$RUNNER_LABELS"
exec ./run.sh

Use the complete downloaded script, not this isolated excerpt. Runner groups are passed only for organization scope. The script does not replace an existing runner registration. It unsets the private key and bootstrap tokens before executing workflow work, and uses exec to avoid an unnecessary outer shell. These are defensive improvements, not a guarantee of credential isolation from code sharing the same container and managed identity.

Build only an allowlisted context

Put only the Dockerfile, startup script, and the downloaded build-context allowlist renamed to .dockerignore in a dedicated image-build directory. Do not build from a directory containing a private key, repository history, backup archives, or application secrets. .gitignore alone does not constrain a Docker/ACR build context.

Supply a supported runner release and its SHA-256 from the official actions/runner releases. The source used version 2.335.1; that is a historical value, not a current recommendation. The repaired Dockerfile requires an explicit version and verifies the archive before extracting it. The Azure CLI installer and Ubuntu base remain external build dependencies: review them and pin versions/digests under a maintained image policy.

# On an approved private-connected build host with Docker and ACR push rights:
az acr login --name "$ACR_NAME"
docker build --build-arg RUNNER_VERSION="$RUNNER_VERSION" \
  --build-arg RUNNER_SHA256="$RUNNER_SHA256" \
  --tag "$ACR_LOGIN_SERVER/$IMAGE_NAME:$IMAGE_TAG" .
docker push "$ACR_LOGIN_SERVER/$IMAGE_NAME:$IMAGE_TAG"

If using Docker-free ACR Tasks instead, configure a supported private-capable build path, such as an appropriately networked dedicated agent pool where available, and verify its access to the registry, source context, package feeds, and required platform endpoints. A plain hosted az acr build request is not proof that its worker can access a private-only registry.

# Only after an approved compatible ACR Tasks agent pool is configured:
: "${ACR_AGENT_POOL:?Set the reviewed agent pool}"
az acr build --registry "$ACR_NAME" --agent-pool "$ACR_AGENT_POOL" \
  --image "$IMAGE_NAME:$IMAGE_TAG" --file Dockerfile \

  --build-arg RUNNER_SHA256="$RUNNER_SHA256" .

The source temporarily enabled ACR public access and changed its default network action from Deny to Allow for a hosted build, then restored private-only access. It also observed that enabling public access alone did not override the Deny rule. These are historical, security-sensitive choices, not recommended defaults. Do not widen registry access or evade a policy merely to make a build pass.

After changing the Dockerfile or script, rebuild and push a new immutable tag or approved digest and update the job image. Editing a local Dockerfile does not change running containers. A stale image was an important source troubleshooting lesson, especially for az: command not found. This runner has no Docker daemon; the image-build host is a separate component, not a promise that arbitrary Docker builds work inside Container Apps Jobs.

Wait for successful environment provisioning before creating jobs. Verify DNS, firewall dependencies, and subnet delegation when environment provisioning stalls. Networking and diagnostic prerequisites apply to platform components as well as the runner container.

Configure the complete KEDA event rule

The scaler's owner, repository list, scope, App ID, installation ID, and labels must agree with the runner container and the installed GitHub App. In the baseline, the app installation can access the selected repository, the runner registers at that repository, and both runner and workflow use the custom label container-app.

The following JSON construction and ARM update are a source-derived bootstrap repair, not a verbatim source command. They convert the already prepared Manual job to Event while supplying the complete event configuration in one update. They contain only IDs and secret references, never the PEM. Inspect the generated configuration and your job before applying it. Confirm that the API version and generic resource update are supported in your environment.

EVENT_CONFIG=$(jq -n \
  --arg owner "$GITHUB_OWNER" --arg repo "$GITHUB_REPO" \
  --arg app "$GITHUB_APP_ID" --arg installation "$GITHUB_APP_INSTALLATION_ID" \
  '{
    parallelism: 1,
    replicaCompletionCount: 1,
    scale: {
      minExecutions: 0,
      maxExecutions: 5,
      pollingInterval: 30,
      rules: [{
        name: "queued-runner-work",
        type: "github-runner",
        metadata: {
          owner: $owner,
          runnerScope: "repo",
          repos: $repo,
          labels: "container-app",
          targetWorkflowQueueLength: "1",
          applicationID: $app,
          installationID: $installation
        },
        auth: [{secretRef: "runner-app-key", triggerParameter: "appKey"}]
      }]
    }
  }')
az resource update --ids "$JOB_ID" --api-version 2024-03-01 \
  --set properties.configuration.triggerType=Event \
  "properties.configuration.eventTriggerConfig=$EVENT_CONFIG" \
  --remove properties.configuration.manualTriggerConfig --output none

  --min-executions 0 --max-executions 5 --polling-interval 30 \

  --scale-rule-metadata \
  "owner=$GITHUB_OWNER" "runnerScope=repo" "repos=$GITHUB_REPO" \
  "labels=container-app" "targetWorkflowQueueLength=1" \

For organization mode, set both scopes to org, pass the chosen runner group to the container, and set repos to an explicit comma-separated list visible to that app installation. Do not change only the runner's environment variables and leave the scaler pointing at a different owner or scope.

Rate limits and repository filtering

GitHub App installation rate limits depend on the installation and account context; they are not universally 15,000 requests per hour. Consult the actual rate-limit response headers and GitHub documentation. KEDA can make several requests per repository and queued run, so even a seemingly moderate polling frequency can become expensive across many repositories. Avoid scanning the whole organization unnecessarily, stagger or consolidate equivalent scalers, tune polling, and use conditional-request options only where the managed scaler version supports them.

A simple planning estimate is polling cycles per hour multiplied by repository/run/job enumeration requests per cycle, plus registration and other API traffic. This is an estimate, not a source measurement. Watch primary and secondary rate-limit responses and backoff behavior rather than increasing polling speed when queue detection is failing.

Validate one execution before increasing scale

  1. First verify the target application independently from an approved network path. A local zip deployment proves the target deployment path only; it does not prove KEDA detection or runner execution.
  2. Dispatch a small trusted workflow using the same runs-on labels. Observe GitHub's Queued state and then the Container Apps execution list.
  3. Confirm that an execution starts, pulls the expected image, obtains the secret, registers a runner at the correct scope, and receives the intended job.
  4. Run the supplied deployment workflow. Check Node setup, locked dependency installation, the explicitly recognized test stub, identity login, and zip deployment as separate stages.
  5. From a client authorized for the target endpoint, verify the app and health route. Use an explicit version marker in a real application if you need to prove which revision is deployed; request timestamps alone are insufficient.
  6. Confirm the runner exits and does not accept a second job. Inspect stale registrations and failed/cancelled executions rather than assuming ephemeral cleanup always succeeds after forced termination.

Trust boundaries, maintenance, and cost controls

Separate trust levels before scaling

A self-hosted deployment runner is a privileged execution surface. Repository writers, mutable actions, dependency lifecycle scripts, and workflow changes can influence code executed inside it. The managed identity can access the Web App and authorized vault secrets; the VNet may expose internal services. Ephemeral compute reduces persistence between jobs but does not remove these powers during a job.

  • Keep deployment repositories/workflows trusted and reviewed. Do not let an untrusted pull request execute on a runner holding production network access or identity.
  • Use separate jobs, identities, GitHub App installations, runner groups, and network segments for materially different trust levels. Labels route work; they are not an authorization boundary.
  • Restrict the App installation to required repositories and give Azure roles at the smallest practical scope. Review whether sharing one identity for secret reads and deployment meets your risk model.
  • Rotate the GitHub App key with an overlap plan, update the Key Vault reference or version as appropriate, verify new executions and scaler authentication, then revoke the old key. Do not assume every component refreshes a versionless reference immediately.
  • Forward protected diagnostics, review runner cleanup after failures, and avoid logging complete environments, secrets, JWTs, installation tokens, registration tokens, or publish profiles.

Maintain the image, not just the workflow

Schedule a reviewed image rebuild process, such as a weekly maintenance pipeline, that checks the Ubuntu base, runner release, Azure CLI, and required tools. The source illustrated a cron-triggered ACR task; its source authentication and worker networking must be designed separately for a private repository and registry. Do not paste a long-lived GitHub token into a public task command. Use an approved integration and secret store, then verify build results and promote a tested tag/digest to the job.

Automatic runner updates are retained in the supplied registration behavior. They do not eliminate the need for image maintenance: repeatedly booting an old image costs time and may violate runner support requirements. Disabling updates is possible only with a deliberate compliant replacement cadence, not as a blanket rule that every disabled-update runner is unsupported.
