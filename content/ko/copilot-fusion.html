Fusion은 모델뿐 아니라 실행 방식도 선택합니다

GitHub Copilot Fusion은 새로운 기반 모델이 아니라, 실행 시점에 모델을 선택하고 협업을 조정하는 라우터·오케스트레이터입니다. 사용자가 매번 모델을 고르는 대신 처리 수준을 선택하면, Fusion이 모델·단계별 추론 수준·실행 패턴을 결정하고 최종 답변 하나를 제공합니다. 개발자와 검토 절차를 함께 배정하는 기술 리드에 비유할 수 있습니다.

독립적인 학습 자료이며 공식 지침, 가격 약속이나 SLA가 아닙니다. 제품 설명은 2026년 11월 17일 GitHub 문서와 대조했습니다. 아래 과거 관측은 제공된 11월 16일 노트에 근거하며, 게시 준비 과정에서 원시 로그와 스크린샷을 독립적으로 확인하지 않았습니다. 반복 가능한 라우팅 규칙, 품질 향상, 지연 분포나 비용 절감을 입증하지 않습니다. 지원 범위, 모델 구성, 플랜, 요금과 UI는 변경될 수 있습니다.

이 글은 제공된 학습 자료를 재구성했으며, 2026년 11월 4일 게시되고 11월 5일 갱신된 Chomado의 일본어 소개 글을 참고했습니다. 전체 번역문은 아닙니다. GA 날짜는 2026년 10월 28일 GitHub 출시 안내로, 상세 동작은 현재 Fusion 개념 문서로 확인했습니다.

Fusion이 모든 작업에서 여러 모델을 호출하는 것은 아닙니다. 반대로 최종 답변이 하나라는 이유만으로 모델도 하나만 참여했다고 볼 수는 없습니다.

모델·에이전트·라우팅·추론 수준을 구분합니다

개념의미
모델텍스트, 코드나 다음 행동을 생성하는 언어 모델입니다.
코딩 에이전트모델에 지시, 파일 접근, 도구와 실행 루프를 결합한 시스템입니다. 실행 환경도 결과에 영향을 줍니다.
라우팅작업을 수행할 모델을 선택합니다.
오케스트레이션초안 작성, 평가, 비평, 수정 등의 단계와 역할을 조정합니다.
추론 수준개별 단계에서 사용하는 모델의 추론 설정입니다. Fusion 전체 처리 수준과 동일하지 않습니다.
토큰·지연 시간·AI 크레딧각각 텍스트 처리 단위, 응답까지 걸린 시간, Copilot 사용량 계량 단위입니다. 어느 것도 답변 품질 자체를 직접 측정하지는 않습니다.

Fusion은 모델 선택, 추론 수준과 실행 방식을 함께 조정합니다. 같은 대화라도 간단한 이름 변경과 여러 서비스의 호환성을 유지해야 하는 수정은 서로 다른 처리가 적합할 수 있습니다.

컨텍스트 창은 개별 단계의 모델이 처리할 수 있는 정보의 한도입니다. Fusion 자체에 더 큰 컨텍스트 창이 생기는 것은 아니며, 표시되는 한도는 사용 모델들을 고려한 보수적인 값입니다. 공식 문서는 캐시 토큰의 이점을 유지하도록 가능한 경우 주 대화의 모델을 유지하고 보조 모델에는 필요한 맥락만 전달한다고 설명합니다. 라우팅은 매번 무조건 모델을 바꾸기보다 캐시 경계, 대화 복잡도 변화, 시스템 상태와 가용성을 고려합니다.

Standard·High·Max는 처리 우선순위를 나타냅니다

처리 수준공식 문서의 우선순위시작점으로 생각할 수 있는 예시
Standard비용·품질·지연의 균형을 맞추며 작업마다 모델 하나를 선택합니다.함수 설명과 작고 명확하게 테스트할 수 있는 변경입니다.
High추가 시간과 크레딧을 쓸 가치가 있는 작업에 균형 잡힌 오케스트레이션을 적용합니다.복잡한 오류 수정이나 범위가 분명한 여러 파일의 변경입니다.
Max토큰 효율도 고려하면서 최고 수준의 해결 능력, 깊은 추론과 철저한 분석을 우선합니다.여러 원인이 가능한 어려운 동시성 오류입니다.

이 업무 예시는 학습용이며 공개된 라우팅 알고리즘이 아닙니다. High가 정확히 두 모델을 뜻하거나 Max가 모든 모델 실행을 뜻하지 않으며, 어느 쪽도 정답을 보장하지 않습니다. 특히 세 처리 수준과 세 실행 패턴을 일대일 대응으로 이해하면 안 됩니다.

문서에는 VS Code 인라인 채팅에서 빠른 모델이 필요한 상황에 사용하는 Fusion Fast도 나옵니다. 사용자가 직접 선택할 수는 없습니다. 이 글은 별도의 로컬 모델 라우팅 프리뷰가 아니라 사용자가 선택하는 세 처리 수준에 집중합니다.

Single·Cascade·Critique는 서로 다른 질문에 답합니다

Single: 한 모델이 작업을 완료합니다

Request -> model A -> final result

모델 하나도 파일을 읽고, 도구를 호출하고, 테스트를 실행하며, 도구 결과를 처리하는 과정에서 반복 호출될 수 있습니다. Single은 API 호출 한 번이나 도구 미사용을 뜻하지 않습니다. 작은 함수 설명은 직관적인 예시이지만, 특정 설명 요청이 Single이었다는 증거는 아닙니다.

Cascade: 초안을 평가하고 필요할 때만 상향합니다

Request -> efficient model's draft -> judge
                                      |
                         +------------+------------+
                         |                         |
                       accept                   escalate
                         |                         |
                       result              stronger model -> result

핵심은 해당 작업 안에서 조건부로 상향 처리한다는 점입니다. 예를 들어 날짜 파서 초안이 보통 날짜는 처리하지만 시간대 경계를 놓칠 수 있습니다. 평가자는 초안을 채택할지 상향할지 판단하며, 세부 기준 전체는 공개되지 않았습니다. 이후의 다른 사용자 요청에 다른 모델이 나타났다는 사실만으로 Cascade라고 볼 수는 없습니다.

Critique: 독립적인 비평을 모아 수정합니다

Request -> model A's draft
                   |
             +-----+-----+
             |           |
          critic B    critic C
             |           |
             +-----+-----+
                   |
          aggregated feedback
                   |
          model A revises -> final result

현재 개념 문서는 여러 모델이 병렬로 독립적인 비평을 만들고, 취합한 피드백을 원래 모델이 반영한다고 설명합니다. 출시 안내는 초안·검토·수정 형태로 더 간단히 소개합니다. 위 그림은 개념도이며, B와 C는 실제 관측한 모델 배정이나 보장된 리뷰어 수가 아니라 설명용 표기입니다.

할인 계산기라면 반올림에 대한 비평과 음수 금액·중복 할인에 대한 비평이 도움이 될 수 있습니다. 이는 가정한 검토 관점이지 제품의 고정 역할이 아닙니다. 추가 호출은 시간과 사용량을 늘릴 수 있으므로 멀티 모델 처리가 항상 더 빠르지는 않습니다.

과거 관측: 두 요청에서 서로 다른 모델이 기록되었습니다

제공된 노트에는 2026년 11월 16일 VS Code에서 Fusion을 선택하고, Standard로 함수 설명을 요청한 뒤 High로 주문 계산 코드를 수정한 기록이 있습니다. 처음의 작은 함수는 다음과 같습니다.

def greet(name):
    return f"Hello, {name}!"


if __name__ == "__main__":
    print(greet("Python"))

첫 요청은 함수 설명과 더 명확한 함수명 제안이었습니다. 두 번째 요청 전에는 예제를 주문·쿠폰·배송비·도서산간 추가비·디지털 상품을 다루도록 확장했습니다. 이 요청은 API와 입력 검증 동작 유지, SAVE10 최소 주문액·할인 상한 준수, 할인 후 무료 배송 판단, 디지털 전용·혼합 주문 구분, 단위 테스트 작성과 실행을 요구했습니다.

같은 모델 이름의 행이 반복되어도 독립적인 모델 수나 비평 횟수를 뜻하지는 않습니다. 테스트와 수정을 반복하는 흐름도 일반적인 단일 모델 에이전트에서 나타납니다. 타당한 결론은 제한적입니다. Fusion을 선택한 상태에서 서로 다른 요청에 서로 다른 모델 이름이 기록되었다는 것입니다.

로컬 기록 조회와 실행 패턴 판별을 구분합니다

노트는 로컬 CLI 형식의 이벤트 로그로 해당 채팅을 살펴보았습니다. 접근 권한이 있는 환경에서 대상 채팅을 찾으려면 세션의 사용자 질문과 시각을 먼저 대조해야 합니다. 최근 수정된 폴더가 다른 CLI 대화일 수도 있습니다. 이러한 기록의 존재 여부와 스키마는 클라이언트·버전에 따라 다릅니다.

다음 읽기 전용 Bash 예시는 jq가 필요합니다. 자리표시자는 본인의 대상 세션 ID로 비공개 환경에서 바꾸십시오. 도구 인자에는 소스 코드, 비공개 경로, 프롬프트나 자격 증명이 포함될 수 있으므로 의도적으로 출력하지 않습니다. 원시 출력은 검토 없이 공개하지 마십시오.

f="$HOME/.copilot/session-state/SESSION_ID/events.jsonl"

jq -r 'select(.type=="assistant.message") | [.timestamp, .data.model] | @tsv' "$f"

jq -r 'select(.type=="tool.execution_start") | [.timestamp, .data.toolName] | @tsv' "$f"

이 필드는 과거 환경에서 보고된 구조이며, 공식 Fusion 진단 명령이나 고정된 로깅 계약이 아닙니다. 모델 필드가 없으면 미확인이지 모델이 실행되지 않았다는 증거가 아닙니다. 파일을 읽는 것은 설정을 바꾸지 않지만 코딩 요청은 작업 공간을 수정하고 크레딧을 사용할 수 있습니다. 이 글을 준비하며 로깅이나 텔레메트리 설정을 변경하지 않았습니다.

“확실히 Single은 아니었다”는 결론조차 이 증거의 범위를 넘습니다. 더 넓은 트레이스 안의 두 에이전트 호출이 각각 Single일 수도 있습니다. Cascade나 Critique를 확정하려면 요청 경계와 평가·상향 또는 비평·취합·수정의 인과관계가 필요합니다. 이러한 관계는 검증하지 못했습니다. 한 모델이 도구를 사용한 뒤 다시 호출되는 것도 Single과 모순되지 않습니다.

추가 검토는 토큰과 총비용을 늘릴 수 있습니다

Fusion 자체의 별도 기능 요금은 없습니다. GitHub 문서는 사용한 각 모델의 표준 요율로 과금하며, High나 Max가 Standard보다 많은 AI 크레딧을 사용할 수 있다고 설명합니다. 검토 과정에서 관련 맥락·초안의 입력 토큰, 피드백 출력 토큰, 수정을 위한 추가 호출이 발생할 수 있습니다.

Illustrative usage components:
  drafting
+ judging / critique, if used
+ escalation / revision, if used

Not every task incurs every component.

단계 사이에서 맥락을 전달한다고 매번 대화 전체를 캐시 없이 재전송한다는 뜻은 아닙니다. 필요한 맥락만 전달하고 캐시 입력과 저렴한 모델을 사용하면 일부 부담을 줄일 수 있습니다. 모델별 단가가 다르므로 토큰이 많아도 더 비싸지 않을 수 있고, 토큰이 적어도 더 저렴하다고 보장할 수 없습니다.

가정한 처리 방식통화가 아닌 설명용 비용 단위합계
고성능 모델 직접 사용1010
Cascade에서 초안 채택2 + 13
Cascade에서 상향 처리2 + 1 + 1013

위 값은 절충 관계를 설명하는 가상 단위이며 실제 요율이나 관측한 상향 빈도가 아닙니다. 개별 작업은 더 비쌀 수 있고 평균 효율은 작업 구성에 달려 있습니다. 대기, 재시도, 추가 질문, 수동 수정, 사용량과 최종 품질을 포함해 만족할 만한 결과까지의 전체 작업을 비교해야 합니다.

기간 한정 안내: 11월 17일 확인한 공식 개념 문서는 유료 Copilot 플랜의 Fusion 모델 비용을 2026년 11월 30일까지 30% 할인한다고 설명합니다. 구독료 전체의 30% 할인이 아니며, 이후에도 유지된다고 가정하면 안 됩니다. 예산을 정하기 전에 최신 모델 요금 문서를 확인하십시오.

Copilot Max 구독 플랜과 Fusion Max 처리 수준은 다른 개념입니다. 모든 플랜에서 제공된다는 말이 모든 수준과 모델을 어디서나 쓸 수 있다는 뜻은 아닙니다.

Fusion은 구독과 기업·조직 정책상 사용 가능한 모델을 선택합니다. 관리자는 Fusion용 모델 허용 범위와 기본 처리 수준을 정할 수 있습니다. 데이터 상주, FedRAMP, 평가 모델 제한도 적용되며 Fusion은 이를 우회하지 않습니다. 필요한 모델이 비활성화되면 Max가 보이지 않을 수 있고, 사용 가능한 모델이 없으면 Fusion 자체가 표시되지 않습니다.

특정 수준이 없다면 UI 오류로 단정하기 전에 플랜 권한, 허용 모델과 적용 정책, 클라이언트 버전을 확인하십시오. 공식 문서의 GA 클라이언트는 VS Code, Copilot CLI, Copilot app, JetBrains IDEs입니다.

출처가 있는 발표값이지 여기서 재실행한 결과는 아닙니다. 60점이 독자의 프로젝트 성공률 60%라는 뜻은 아닙니다. 모델뿐 아니라 에이전트 하네스, 도구, 작업 집합과 평가 환경도 중요합니다. 평균 API 비용은 구독료가 아니며, 평균 시간 절감이 개별 요청의 40% 개선을 보장하지는 않습니다.

모델별 강점과 선택적인 검토는 효율 개선이 가능한 이유를 설명하지만, 발표된 절감이 어떤 내부 메커니즘 때문인지 입증하지는 않습니다. 평가 조건은 GitHub Copilot Benchmarks에서 확인하십시오. 앞의 과거 관측 두 종류는 독립적인 벤치마크 재현이 아닙니다.

Auto·HydraFusion·서브에이전트는 계층이 다릅니다

Fusion은 기존 Auto의 모델 선택과 Project HydraFusion의 멀티 모델 오케스트레이션을 결합합니다. Auto가 주로 담당 모델을 골랐다면 Fusion은 모델들이 함께 일하는 방식도 조정합니다. 출시 안내에 따르면 기존 Auto·HydraFusion·HydraFusion Max 프리뷰 선택은 대응하는 Fusion 수준으로 전환됩니다. HydraFusion을 별도 설치할 필요는 없습니다.

UI 이름이 바뀌었다고 auto가 포함된 모든 식별자가 없어지는 것은 아닙니다. 현재 빌드의 CLI 문서는 이 식별자를 이용한 자동 선택을 명시적으로 지원합니다. 별칭을 추측하기보다 아래의 확인된 명령을 사용하십시오.

Fusion은 서브에이전트와 별도로 작동하며 자체적으로 서브에이전트를 시작하지 않습니다. 테스트 담당과 문서 담당 에이전트를 나누는 것은 다른 계층의 작업 위임이지, Fusion이 Critique를 실행했다는 증거가 아닙니다.

의도적으로 시작하고 커밋 전에 작업 공간을 확인합니다

지원 클라이언트를 업데이트하고 모델 선택 메뉴에서 Fusion과 사용 가능한 수준을 선택합니다. 학습은 Standard에서 시작하고, 범위가 명확한 큰 작업에는 High, 추가 시간과 사용량을 감수할 가치가 있는 깊은 분석에는 Max를 고려할 수 있습니다. 이는 활용 제안이지 보장된 라우팅 결과가 아닙니다.

다음 선택 예시는 Copilot CLI 1.0.113-0 문서에서 확인했습니다. 대화형으로 고르거나 현재 세션의 자동 라우팅을 선택합니다.

/model
/model auto

Auto를 사용하는 새 세션의 Fusion 수준을 설정하고 시작하는 방법은 내장 구성 가이드에 다음과 같이 나옵니다.

copilot config fusionTier standard
copilot --model auto

첫 명령은 사용자 영구 설정을 바꿉니다. Fusion 수준 값은 standard, high, max이며 관리 설정이 우선할 수 있습니다. 예시를 읽기 위해 실행할 필요는 없습니다. 변경 전 값을 비공개로 기록하고 단순 체험이었다면 나중에 복원하십시오. 이 값을 다른 라우팅 프로필이나 개별 모델 추론 설정과 섞으면 안 됩니다. 위 명령은 문서로 확인했으며 이 환경의 설정을 바꾸기 위해 실행하지 않았습니다.

공식 문서는 진행 중 단계와 모델을 볼 수 있고 응답 아래 처리 수준 이름에 마우스를 올리면 사용 모델을 볼 수 있다고 설명합니다. 표현 방식은 클라이언트에 따라 다릅니다. 모델 목록은 참여 여부에 대한 유용한 증거이지만 실행 패턴의 완전한 인과관계를 자동으로 설명하지는 않습니다.

폐기한 초안이 남긴 작업 공간 변경은 자동으로 되돌아가지 않습니다. 커밋 전 변경 파일과 차이를 검토하고 적절한 테스트와 최종 동작을 확인하십시오. 최종 답변에 채택되지 않은 초안도 파일 변경을 남겼을 수 있습니다.

실무에서는 요청한 처리 수준, 실제 기록된 모델·도구 활동, 아직 입증하지 못한 내부 실행 관계를 구분하는 것이 핵심입니다. 품질·지연·비용을 비교할 때도 이 경계를 유지하십시오.
