느린 응답은 진단 결과가 아니라 조사할 질문입니다

Hosted Agent 요청에는 플랫폼 접수, 세션 샌드박스 준비, 애플리케이션 초기화, 모델 처리, 도구, 전송을 기다리는 시간이 들어갈 수 있습니다. 이 지연 전체를 “콜드 스타트”라고 부르면 조사 대상을 정하는 데 필요한 구분을 놓칩니다. 먼저 네 가지를 따로 물어보세요. 플랫폼이 보고한 시작 유형은 무엇인지, 유용한 답변 텍스트가 언제 도착했는지, 스트림이 언제 끝났는지, 어떤 트레이스가 그 구간을 설명하는지입니다.

비공식 과거 관찰이며 성능 보장이나 SLA가 아닙니다. 아래 측정 다섯 건은 2026년 9월 30일에 기록되었습니다. 2026년 10월 7일에 발행한 이 글은 해당 기록과 측정 코드를 검토한 것이며, 공개를 위해 실험을 다시 실행하지 않았습니다. 결과는 워크로드, 모델, 배포, 세션 상태, 네트워크 및 서비스 변경에 따라 달라집니다. 진단 타이밍은 SLA나 과금 지표가 아닙니다.

측정 대상 에이전트는 스트리밍 Responses 프로토콜, GPT-5 모델 배포, 고정된 에이전트 지침을 사용했고 MCP, 검색, 세션 파일 도구에 접근할 수 있었습니다. 기준 프롬프트는 도구 없이 짧게 준비 완료를 답하도록 요청했습니다. 이 요청이 에이전트 초기화를 없애거나 내부의 도구 관련 활동이 전혀 없음을 보장하지는 않습니다. 배포 기록에는 CPU 한 개와 메모리 2 GiB가 적혀 있었지만, 측정 과정에서 활성 버전을 별도로 고정하거나 다시 검증하지는 않았습니다.

앞서 공개된 Zenn의 호출 일곱 건 연구가 이번 조사의 계기가 되었습니다. 그 연구는 다른 최소 구성 에이전트와 모델/API 동작을 사용했으며, 그 측정값과 그래픽은 이 글의 호출 다섯 건 데이터가 아닙니다. 그 연구와 본문의 다섯 건 어느 쪽도 지연 분포, 백분위수 또는 보편적인 콜드 스타트 추가 비용을 확립하지 않습니다.

시간만 보고 추측하지 말고 시작 유형을 분류하세요

보고된 유형구분하는 대상입증하지 않는 사항
Cold새 세션 실행 환경을 시작하는 요청입니다.에이전트의 최초 호출이라는 뜻도, 공유 인프라와 이미지 캐시가 비어 있다는 뜻도 아닙니다.
Warm이미 실행 중인 세션을 사용하는 요청입니다.모델 호출, 재시도, 도구 또는 응답 전달이 빠르다는 보장은 없습니다.
Resume유휴 세션을 다시 시작하는 요청입니다.저장된 상태를 복원하는 비용이 Warm 호출과 같다는 뜻은 아닙니다.

명령 이름, 요청한 테스트 모드 또는 경과 시간이 아니라 x-ms-debug-latency-session-start-type으로 각 결과를 분류하세요. 요청한 모드는 별도로 보관합니다. Warm을 요청했더라도 세션이 유휴 상태가 되었다면 실제로는 Resume일 수 있습니다. 헤더가 없으면 추측하지 말고 유형 미확인으로 남깁니다.

현재 공식 세션 문서는 해당 에이전트 버전에서 생성한 세션의 유휴 제한 시간을 120–3,600초 범위에서 설정할 수 있고 기본값은 900초라고 설명합니다. 이는 문서화된 구성 값이지, 이 다섯 건으로 측정한 전환 임계값이 아닙니다. 기록된 Resume은 테스트 세션을 명시적으로 중지하고 유휴 상태를 확인한 뒤 수행했으므로 자연스러운 유휴 제한 시간 동작을 입증하지 않습니다. 유휴 동작이 궁금하다면 실제 상태 전환을 측정하고 적용되는 버전 구성을 확인해야 합니다.

모든 타이머의 시작점과 종료점을 명시하세요

호출에 문서화된 지연 진단을 활성화합니다. Responses와 Invocations 프로토콜을 지원하지만 두 프로토콜의 세션 연결 방식은 다릅니다.

x-ms-debug-latency-enabled: true
응답 헤더 접미사문서화된 구간 또는 의미
session-start-type관측한 시작 유형으로 cold, warm 또는 resume입니다.
platform-preprocessing-ms접수, 인증, 세션 조회 및 오케스트레이션입니다.
infra-setup-ms마이크로 VM 프로비저닝이며 일반적으로 Warm에서는 생략됩니다.
container-readiness-ms마이크로 VM 생성부터 컨테이너가 준비 완료를 보고할 때까지이며 일반적으로 Warm에서는 생략됩니다.
container-response-ms프록시 전달부터 응답 헤더 확정까지이며 요청 전송, 연결 설정, 에이전트 처리, 재시도 및 출력 정책 버퍼링을 포함합니다.
response-begin-ms서비스 접수부터 응답 헤더 확정까지입니다. 첫 본문 바이트, 첫 SSE 이벤트, 첫 답변 텍스트 또는 완료까지의 시간이 아닙니다.

이 접미사는 모두 x-ms-debug-latency- 접두사를 사용하며 시간 값은 정수 밀리초입니다. 문서에 설명된 구성 요소 네 개가 모두 수집되면 합계는 response-begin과 같습니다. Cold나 Resume에서 프로비저닝 경계를 수집하지 못하면 플랫폼은 인프라와 readiness 헤더를 생략하고 해당 시간을 preprocessing에 포함할 수 있습니다. 누락은 측정된 0이 아닙니다.

클라이언트 필드동일한 HTTP 요청 시작점부터 측정하는 종료 이벤트
client_headers_msHTTP 상태와 응답 헤더를 수신합니다.
client_first_body_chunk_ms비어 있지 않은 첫 디코딩된 본문 청크를 수신합니다. 연결 유지 또는 수명 주기 이벤트일 수 있습니다.
client_first_text_ms비어 있지 않은 첫 답변 텍스트 델타를 파싱합니다.
client_response_completed_ms응답 완료 이벤트를 수신합니다.
client_stream_end_ms응답 본문 스트림을 정상적으로 끝까지 읽습니다.
client_elapsed_ms클라이언트의 스트림 처리와 응답 정리가 끝나거나 실패 또는 중단으로 대기가 종료됩니다.

공개한 총시간 다섯 개는 client_stream_end_ms를 초로 변환하여 원래 기록의 반올림 값을 사용한 것입니다. 스트리밍 HTTP 호출 직전에 시작하여 본문 반복자를 끝까지 읽은 뒤 종료합니다. 첫 텍스트까지의 시간도, 더 넓은 범위의 경과/정리 필드도 아닙니다. 토큰 취득과 Resume 전 중지/폴링 대기는 이 구간 밖에서 측정했습니다. 클라이언트 타임스탬프는 누적값이므로 서로 더하면 안 됩니다.

response.output_text.delta는 이 클라이언트에서 텍스트를 사용할 수 있게 된 시점을 나타내며, 반드시 모델 내부의 첫 토큰 경계와 같지는 않습니다. response.completed 이벤트는 스트림이 닫히기 전에 올 수 있습니다. 텍스트 델타가 없으면 null을 유지하고 정상 완료를 시간 초과 또는 실패한 응답과 구분합니다. 원문 요약은 호출별 첫 텍스트나 응답 완료 값을 공개하지 않으므로 이 글도 이를 만들어 내지 않습니다.

공식 x-ms-debug-latency-final 트레일러는 HTTP/2 이상에서 최선의 노력 방식으로 제공됩니다. 서비스 접수부터 측정한 first_byte_ms와 total_last_byte_ms가 포함될 수 있습니다. 과거 HTTPX 클라이언트는 트레일러를 수집하지 않았으며 HTTP/2를 요청했다고 실제로 협상되었다고 단정할 수 없습니다. 같은 응답을 나중에 GET으로 조회하면 최종 일관성과 문서화된 제약 아래 원래 호출의 저장된 타이밍을 받을 수 있습니다. 이는 GET 자체의 측정값이 아닙니다. 클라이언트와 서버 시간의 차이가 자동으로 순수 네트워크 RTT가 되는 것도 아닙니다.

워크로드를 바꾸지 않고 측정 설계를 재현하세요

호출 권한이 있는 환경에서 폐기 가능한 테스트 세션을 사용하세요. 호출에는 비용이 발생하고 도구가 실행될 수 있습니다. 이 글을 위해 클라우드 작업을 수행하지 않았습니다. 다음 코드 조각은 요청과 계측 규약을 설명하며 바로 실행할 수 있는 클라이언트가 아닙니다. 자격 증명과 상관관계 식별자를 비공개로 보관하고 원시 프롬프트, 답변 페이로드, 인증 헤더 또는 환경 덤프를 기록하지 마세요.

  1. 대상 배포, 모델 설정, 합성 프롬프트, 클라이언트 위치, 연결 정책 및 테스트 시간을 비공개로 기록합니다. 비교하는 동안 라우팅과 구성을 바꾸지 않습니다. 의도한 Cold 표본 직전에 Playground 메시지나 점검용 호출을 보내지 않습니다.
  2. Cold를 위해 세션 연결 정보 없이 스트리밍 Responses 요청을 한 번 보냅니다. 반환된 세션 연결 정보를 안전하게 저장합니다. 값이 없거나 유효하지 않거나 예상과 다르면 새 세션으로 조용히 대체하지 않습니다.
  3. Warm을 위해 같은 세션 연결 정보로 같은 요청을 바로 보냅니다. 프롬프트와 설정을 유지하되 대화 이력을 추가하지 않습니다. 과거 클라이언트는 표본마다 별도의 HTTP 클라이언트를 생성했으므로 지속 연결 벤치마크가 아니었습니다.
  4. 명시적으로 승인한 Resume 테스트에서는 해당 테스트 세션만 중지하고 제한 시간이 있는 폴링으로 유휴 상태를 확인한 후 같은 세션을 호출합니다. 중지/폴링 시간을 분리합니다. 표본을 만들기 위해 공유 에이전트를 중지하거나 파일을 삭제하거나 재배포하지 않습니다.
  5. HTTP 성공, 유효한 SSE 스트림, 응답 완료, 정상 스트림 종료 및 예상한 실제 시작 유형을 모두 확인한 뒤에만 해당 유형의 성공 표본으로 인정합니다. 불일치와 실패한 시도는 별도로 보존하고 자동 재시도 결과로 덮어쓰지 않습니다.
  6. 필요하면 새 세션에서 Cold 표본을 추가합니다. 실패, 실제 프로토콜, 누락 헤더, 토큰 수, 관측 도구 및 타이머 경계를 보존합니다. 통계적 결론을 내리기 전에 표본 수를 계획하세요. 다섯 건은 대표성 있는 백분위수를 구하기에 부족합니다.

Responses에서는 세션 연결 정보를 JSON 본문에 넣습니다. 다음 설명용 코드는 호출자가 변수를 안전하게 제공했다고 가정하며 그 자체로 요청을 보내지 않습니다.

payload = {
    "model": model_deployment,
    "input": synthetic_prompt,
    "stream": True,
}
if test_session_id is not None:
    payload["agent_session_id"] = test_session_id
# Intentionally omit conversation and previous_response_id.

agent_session_id는 샌드박스와 저장된 파일 시스템을 재사용하며 그 자체로 대화 이력을 다시 전달하지 않습니다. conversation이나 previous_response_id를 추가하면 비교 대상이 달라집니다. Invocations에서는 세션 연결 정보를 쿼리 매개변수로 전달하므로 Responses의 본문 규칙을 그대로 적용하면 안 됩니다. 애플리케이션 코드도 자체 세션 상태를 유지할 수 있으므로 워크로드가 완전히 격리되었다고 주장하기 전에 이를 확인하세요.

다음 타이밍 조각은 이미 인증된 HTTP 클라이언트, 안전한 요청 헤더, 분할 UTF-8 데이터·여러 줄 이벤트·오류를 올바르게 처리하는 SSE 파서가 있다고 가정합니다. 전송 설정, 세션 저장, 예외 처리 및 공개용 내보내기 로직은 의도적으로 생략했습니다. 이 조각을 원래 실험 클라이언트로 오해하지 말고 기존 코드에 계측을 추가하세요.

from time import perf_counter

first_text_ms = None
completed_ms = None
start = perf_counter()
async with client.stream("POST", invocation_url,
                         headers=headers, json=payload) as response:
    headers_ms = (perf_counter() - start) * 1000
    response.raise_for_status()
    async for event in parse_sse(response):
        elapsed_ms = (perf_counter() - start) * 1000
        if (event.get("type") == "response.output_text.delta"
                and event.get("delta") and first_text_ms is None):
            first_text_ms = elapsed_ms
        if event.get("type") == "response.completed":
            completed_ms = elapsed_ms
    stream_end_ms = (perf_counter() - start) * 1000
# Validate response status and observed start type before accepting a sample.
# Never treat a timeout as successful stream completion.

원본 클라이언트는 HTTP 및 전체 대기에 제한 시간을 두고, 클라이언트 자동 재시도를 사용하지 않으며, 저장된 테스트 세션 중지에 명시적 허용을 요구했습니다. 이 안전장치가 에이전트 내부 SDK 재시도를 비활성화한 것은 아닙니다. 클라이언트의 시간 초과나 취소가 서버 작업 종료를 입증하지는 않습니다. 원본은 실제 구성과 상관관계 ID를 로컬에 저장하고 반환된 세션 헤더에 의존했으며, 현재 공식 예제는 응답 페이로드의 세션 정보도 설명합니다. 재사용 가능한 공개 클라이언트라면 검토된 프로토콜 호환 연결 전략, 안전한 내보내기 및 실패 경로 테스트가 필요합니다. 여기서는 실행 파일 다운로드를 제공하지 않습니다.

기록된 다섯 건은 서로 대체 가능한 콜드 스타트 다섯 번이 아닙니다

표는 원문의 묶음 순서를 유지합니다. 첫 세션의 Cold → Warm → Resume 순서 다음에 별도 세션의 Cold 두 건을 표시합니다. A, B, C는 공개용 표기이며 실제 세션 식별자가 아닙니다. 원문에는 B와 C의 Warm 또는 Resume 측정값이 없습니다. 표에 있는 다섯 건은 모두 정상 완료되었고 요청한 시작 유형과 일치했습니다.

기록 행시작 유형세션 관계HTTP 요청 시작 → 스트림 종료 (초)

첫 세션의 중지/폴링 대기는 8.15초였으며 25.92초의 Resume 결과에서 제외했습니다. 보고된 구성 변경 없이 Cold는 83.74초에서 18.10초, 25.35초로 달라졌습니다. 컨테이너 readiness는 약 4.3–4.5초였으며 Cold 응답 전체 시간이 아닙니다. 기록에 호출별 readiness 세부 값이 없으므로, 이 다섯 건에 임의의 구성 요소 값을 배정한 누적 차트를 만들면 오해를 유발합니다.

이 작은 표본에서는 Warm 한 건이 Cold 및 Resume보다 짧았습니다. 이는 관찰 결과이며 세션을 계속 실행했을 때의 이점을 통제된 방식으로 추정한 값이 아닙니다. Cold는 세 건이지만 Warm과 Resume은 각각 한 건이고, 순서를 무작위로 배정하거나 반복된 짝 비교를 하지 않았습니다. 여기서는 평균, 백분위수, 신뢰 구간 또는 보장된 지연 목표를 도출하지 않습니다.

첫 세션의 로그로 좁힌 조사 범위

과거 조사에서는 첫 세션의 세 호출을 기존 Application Insights 및 Foundry 로그와 연결했습니다. 다음 값은 해당 호출 안에서 서로 다른 관측 지점을 측정한 것으로, 앞의 총시간을 구성하는 가산 항목이 아닙니다.

관측 구간 (초)Cold, 세션 AWarm, 세션 AResume, 세션 A
최초 내부 응답 저장 왕복11.460.1611.40

첫 Cold 호출의 모델 요청 경로가 길었지만 프로젝트 API 구간에 43.54초가 걸린 이유는 여전히 설명되지 않았습니다. 이 구간은 순수 모델 추론 시간이 아닙니다. 저장 왕복도 백엔드 저장 처리 이상의 작업을 포함합니다. 약 11.4초는 Cold와 Resume 모두에서 나타났으므로 이 관찰만으로 두 총시간의 큰 차이를 설명할 수 없습니다.

조회한 기록에서 HTTP 429나 재시도 근거를 찾지 못했지만, 어디에서도 재시도가 없었다는 증명은 아닙니다. 일부 Cold 하위 span이 누락되었습니다. 확인한 기준 호출 트레이스의 MCP 통신은 초기화와 도구 검색에 해당했으므로 업무 도구 실행으로 다시 분류하면 안 됩니다. 클라이언트 스트림의 도구 목록이 비어 있어도 내부 활동이 없었다고 입증할 수 없습니다.

트레이스는 합산 목록이 아니라 타임라인으로 읽으세요

상위 span은 하위 작업을 포함하고, 같은 계층의 span은 동시에 실행될 수 있으며, 클라이언트·플랫폼·모델 로그의 시작과 끝 경계도 다를 수 있습니다. 보이는 시간을 모두 더하면 같은 작업을 중복 계산합니다. 실제 경과 시간을 설명하려면 작업과 상하위 관계를 맞추고 공통 타임라인에서 중첩을 확인하여 전체 소요 시간을 결정하는 경로를 찾아야 합니다. 시스템 간 타임스탬프를 비교할 때는 시계 정렬과 계측 공백에도 주의해야 합니다.

별도의 과거 도구 요청 캡처에는 최상위 트랜잭션 25.9초가 표시되어 있었습니다. 검색 도구 span은 754 ms였으며, 그 안의 750 ms 하위 구간에는 토큰 취득 455 ms와 검색 HTTP 요청 291 ms가 들어 있었습니다. 이는 중첩된 구간이지 별도로 더할 독립 지연이 아닙니다. 이 캡처는 기준 측정 다섯 행 중 하나가 아니며 이미지만으로 시작 유형을 판별할 수 없습니다. 원본 이미지와 도구 이름은 재현하지 않습니다.

같은 경계끼리 비교하세요. 모델 사용량의 마지막 토큰까지 시간, 에이전트 호출 span, 응답 헤더 확정, 클라이언트 스트림 종료는 서로 다른 질문에 답합니다. 계측되지 않은 시간은 “설명되지 않은 시간”이지 자동으로 플랫폼 콜드 스타트, Python import 시간 또는 네트워크 지연이 아닙니다. 원인을 지정하기 전에 초기화, 자격 증명, 모델 요청, 도구 검색, 도구 실행, 재시도, 직렬화 및 출력 버퍼링에 span을 추가하세요.

증상에 따라 다음 측정을 선택하세요

증상다음 확인 사항피해야 할 결론
지연 헤더가 없거나 유형이 예상과 다름진단 활성화 헤더, 프로토콜, 프록시 응답 성공 및 올바른 세션 연결을 확인하고 유형 미확인 또는 불일치 결과를 보존합니다.“인프라 헤더가 없으니 시작 비용은 0이다.”
인프라 또는 preprocessing 시간이 큼올바르게 분류한 호출 여러 건을 비교합니다. 승인된 지원 조사를 위해 타임스탬프, 응답 상관관계 및 헤더를 비공개로 보관합니다.“로컬 패키지를 바꾸면 플랫폼 접수 지연이 해결된다.”
컨테이너 readiness 시간이 큼프로세스 시작, import, 의존성 로딩 및 readiness에 타임스탬프를 남깁니다. 애플리케이션이 요청을 받을 수 있기 전에 수행하는 작업을 확인합니다.“첫 애플리케이션 로그 이전의 시간은 전부 import 시간이다.”
헤더는 빨리 오지만 유용한 텍스트가 늦음첫 본문 청크와 첫 답변 델타를 비교하고 모델, 도구, 재시도 및 버퍼링 span을 조사합니다.“헤더나 SSE 연결 유지 신호가 왔으니 답변이 시작되었다.”
첫 텍스트는 빠르지만 완료가 늦음출력 길이, 토큰 간 간격, 이후 도구 작업, 완료 이벤트 및 스트림 종료를 따로 확인합니다.“첫 텍스트 시간이 짧으면 전체 응답도 짧다.”
클라이언트 시간 초과 또는 불완전한 스트림실패와 부분 타이밍을 기록하고 확인된 세션을 비공개로 보관하며 재시도 전에 서버 작업이 계속되는지 조사합니다.“시간 초과는 완료된 표본이거나 확실한 취소이다.”

공식 진단 문서는 게이트웨이나 SDK, 취소 또는 스트림 도중 오류 때문에 트레일러가 사라질 수 있다고 설명합니다. 저장된 결과의 헤더는 나중에 나타날 수 있고, 비동기 결과는 플랫폼 오버헤드 타이밍만 제공하며, 실패한 프록시 응답과 WebSocket 호출에는 같은 지연 헤더가 나오지 않습니다. 이러한 맥락에서 누락을 해석해야 하며 조용히 0으로 바꾸면 안 됩니다.

이 관찰로 입증된 최적화는 없습니다

타당한 결론은 조사 범위가 좁아졌다는 것이지 해결책이 입증되었다는 것이 아닙니다. 이 표본에서 첫 Cold가 유난히 길었고 readiness는 비교적 일정했으며 긴 프로젝트 API 구간은 해결되지 않았습니다. 작은 이미지, 다른 모델, 더 긴 유휴 제한 시간, 추가 용량 또는 워밍업 요청이 지연을 없앤다고 입증하는 변경 전후 결과는 이 기록에 없습니다.

현재 Microsoft 지침은 시작 작업을 측정하고, 패키지 설치와 컴파일을 이미지 빌드 단계로 옮기며, 모델과 도구 지연을 별도로 조사하도록 권장합니다. 확인한 병목에 맞춰 변경한 뒤 통제된 비교를 반복하세요. 초기화를 늦추면 지연이 없어지는 대신 readiness에서 첫 요청으로 이동할 수 있습니다. 컴퓨팅을 계속 활성 상태로 유지하면 비용과 세션 동작이 달라질 수 있으므로 비용 없는 확실한 지연 해결책이 아닙니다.

향후 평가에서는 에이전트 버전, 프롬프트, 모델 설정, 도구 정책 및 연결 정책을 일정하게 유지하고, 입력/출력 토큰 수를 기록하며, 독립 세션 여러 개와 반복 Warm 관측을 수집하고, 성공과 함께 실패도 보고하세요. 모든 표본에 측정 경계와 실제 관측한 시작 유형을 공개하면 근본 원인이 아직 밝혀지지 않았어도 증거로 활용할 수 있습니다.
