범위, 근거 및 공개 경계

이 글은 2026년 9월 14–15일에 수행하고 9월 15일에 문서화한 개념 증명의 원본 개요, 백엔드/정책 가이드, 모니터링 가이드 및 부속 리소스 검토를 통합합니다. 별도의 전용 AI Gateway 미리 보기 계층이 아니라 정책을 사용하는 기존 APIM Standard v2를 다룹니다. APIM, Foundry 계정 및 네트워킹이 이미 존재한다고 가정하며 전체 인프라 프로젝트나 자동 배포 패키지가 아닙니다.

원문에서는 회로 차단기를 갖춘 Single 백엔드 두 개, 풀 하나, APIM 시스템 할당 관리 ID의 추론 RBAC, 최종 작업 세 개를 갖춘 HTTP API 하나 및 Application Insights 로깅을 구성했습니다. 기록된 사용자 테스트에서 Legacy Chat과 Responses는 HTTP 200을 반환했고 v1 Chat도 작동한다고 사용자가 보고했습니다. 한 트랜잭션은 백엔드 1이 429를 반환한 후 백엔드 2가 200을 반환하여 최종 APIM 상태가 200이 되는 것을 보여 주었습니다. 이는 원문의 관찰이며 이 공개판을 위해 수행한 테스트가 아닙니다.

모든 리소스 이름, 구독 및 보안 주체 식별자, 배포 별칭, 호스트 이름, 응답 식별자, 환경별 경로는 매개 변수입니다. 사용 전에 YOUR_* 값을 대체해야 합니다. 원본 스크린샷과 비공개 소스 링크는 공개하지 않습니다. 소유권, 차이, 권한, 롤백 및 동시성을 검토하지 않고 기존 프로덕션 ID에 템플릿을 적용하지 마세요.

아키텍처와 사전 요구 사항

Client -- HTTPS + APIM subscription key --> APIM Standard v2
                                                 |
                                  Outbound VNet Integration
                                  Managed identity token
                                                 |
                                           YOUR_POOL_ID
                                            /        \
                           YOUR_BACKEND_1_ID          YOUR_BACKEND_2_ID
                                   |                         |
                          Private Endpoint          Private Endpoint
                                   |                         |
                         YOUR_FOUNDRY_ACCOUNT_1    YOUR_FOUNDRY_ACCOUNT_2
                             Same model, version, deployment name and API features
  • APIM과 통합된 VNet은 같은 구독 및 지역에 있어야 합니다. Standard v2 아웃바운드 VNet 통합을 활성화하세요. 인바운드 프라이빗 엔드포인트만으로는 백엔드 연결이 제공되지 않습니다.
  • NSG와 Microsoft.Web/serverFarms 위임이 있는 전용 APIM 서브넷을 사용합니다. Foundry 프라이빗 엔드포인트는 다른 서브넷에 배치하고 각 계정의 연결이 승인됨 상태여야 합니다.
  • APIM의 DNS 경로를 통해 각 일반 백엔드 서비스 FQDN이 의도한 프라이빗 엔드포인트 주소로 확인되도록 합니다. 서비스 FQDN과 HTTPS 인증서 검증을 유지하세요. 프라이빗 IP를 호출하거나 백엔드 URL을 privatelink 별칭으로 직접 바꾸지 마세요.
  • 모든 백엔드는 동일한 모델, 모델 버전, 배포 이름, API 동작 및 요청 매개 변수를 지원해야 합니다. 배포가 다르면 호스트만 전환하는 것으로 충분하지 않습니다.
  • 각 Foundry 계정 범위에서 APIM의 시스템 할당 관리 ID에 Cognitive Services OpenAI User를 부여합니다. Application Insights에는 별도의 Monitoring Metrics Publisher 할당이 필요합니다.
  • 클라이언트 인증은 APIM이 적용합니다. Foundry는 클라이언트의 APIM 구독 키가 아니라 APIM의 ID 토큰을 받습니다.

아웃바운드 통합은 퍼블릭 APIM 진입점을 프라이빗으로 만들지 않습니다. Foundry 프라이빗 엔드포인트가 있다고 모든 추론 호출이 프라이빗 경로를 사용했다는 뜻도 아닙니다. 원문의 두 계정은 하나의 구독에 있었습니다. 같은 테넌트의 구독 간 설계 지침은 포함되었지만 해당 PoC가 실제 구독 간 배포를 입증하지는 않았습니다. 별도로 언급된 프라이빗 엔드포인트/네트워킹 가이드는 선택된 원본 패키지에 없었으며 여기에서 임의로 재현하지 않습니다.

1단계: 개별 백엔드 등록

각 계정을 Single 백엔드로 생성하고 회로 차단기는 풀이 아니라 해당 백엔드에 연결합니다. 다운로드 가능한 single-backends.json에는 항목 두 개가 있습니다. 각각 호스트만 포함한 HTTPS URL을 사용하고 인증서 체인 및 인증서 이름 검증을 활성화하며 다음 차단기를 사용합니다.

{
  "properties": {
    "type": "Single",
    "protocol": "http",
    "url": "https://YOUR_FOUNDRY_1_HOST",
    "tls": {"validateCertificateChain": true, "validateCertificateName": true},
    "circuitBreaker": {
      "rules": [{
        "name": "throttle-429",
        "failureCondition": {
          "count": 1,
          "interval": "PT1M",
          "statusCodeRanges": [{"min": 429, "max": 429}]
        },
        "tripDuration": "PT1M",
        "acceptRetryAfter": true
      }]
    }
  }
}

protocol: http는 백엔드 리소스의 열거형 값이며 HTTPS URL을 안전하지 않은 HTTP로 만들지 않습니다. 60초 관찰 기간 안에 429가 한 번 발생하면 차단기가 열립니다. 기본 지속 시간은 60초이고 Retry-After를 수락합니다. 작업 정책이 전체 /openai/... 경로를 제공하므로 백엔드 URL에 해당 경로를 중복하지 마세요.

두 백엔드 JSON 파일 모두 [resource ID, request body] 쌍의 배열을 사용합니다. 첫 항목은 대상 ARM ID이고 두 번째 항목만 개별 PUT 본문입니다. 다운로드한 배열 전체를 백엔드 PUT으로 보내면 잘못된 요청입니다. pool.json도 쌍 하나만 포함하지만 같은 래퍼 형식을 사용합니다.

[
  ["/subscriptions/YOUR_SUBSCRIPTION_ID/resourceGroups/YOUR_APIM_RESOURCE_GROUP/providers/Microsoft.ApiManagement/service/YOUR_APIM_NAME/backends/YOUR_BACKEND_1_ID",
   {"properties": {"type": "Single", "url": "https://YOUR_FOUNDRY_1_HOST"}}]
]
# Envelope illustration only: use the complete downloaded properties object.

수동 변경 시 사용하지 않는 백엔드 ID를 선택하고 먼저 검사하세요. 완전한 요청 객체 하나를 수정해 YOUR_SINGLE_BACKEND_JSON_PATH로 추출한 후 사용하는 원문의 관리 패턴은 다음과 같습니다.

az rest --method get \
  --url "https://management.azure.com/subscriptions/YOUR_SUBSCRIPTION_ID/resourceGroups/YOUR_APIM_RESOURCE_GROUP/providers/Microsoft.ApiManagement/service/YOUR_APIM_NAME/backends/YOUR_BACKEND_1_ID?api-version=2024-05-01" \
  --query '{id:id,url:properties.url}' --output json
# Continue only after a successful, explicit ResourceNotFound (404) result.
# A 200 means the ID already exists; choose another ID or review a controlled change.
# A 401, 403, timeout, or network failure does not mean the resource is absent.
az rest --method put \
  --url "https://management.azure.com/subscriptions/YOUR_SUBSCRIPTION_ID/resourceGroups/YOUR_APIM_RESOURCE_GROUP/providers/Microsoft.ApiManagement/service/YOUR_APIM_NAME/backends/YOUR_BACKEND_1_ID?api-version=2024-05-01" \
  --body @YOUR_SINGLE_BACKEND_JSON_PATH --output none

계정마다 반복합니다. GET 후 PUT은 원자적인 생성 전용 보호가 아닙니다. 이 과정에서 동시 구성 변경을 방지하세요. 원래 자동화는 전용 리소스 그룹, 소유권 설명/태그 및 기존 설정을 확인했습니다. 다른 환경을 대상으로 삼기 위해 이런 보호 장치를 제거하지 마세요. 백엔드 등록만으로는 풀 라우팅, API 정의, 토큰 전달 또는 성공적인 추론이 성립하지 않습니다.

2단계: 풀 구성과 분산 전략 선택

원문의 풀은 두 Single 백엔드의 전체 ARM ID를 참조하며 각각 우선순위 1, 가중치 1이고 자체 서비스 URL은 없었습니다. 먼저 Single 백엔드를 등록하고 URL/TLS/차단기/소유권 설정을 검사한 후 pool.json의 두 번째 객체를 수정해 https://management.azure.com/YOUR_APIM_RESOURCE_PATH/backends/YOUR_POOL_ID?api-version=2024-05-01로 전송합니다. 여기서 YOUR_APIM_RESOURCE_PATH는 앞에 슬래시를 추가하지 않은 전체 subscriptions/... 서비스 경로입니다. Single 백엔드와 동일하게 명시적인 404 확인 및 동시 변경 방지 보호 장치를 사용하세요.

전략구성동작과 제한
라운드 로빈동일 우선순위, 가중치 1:1사용 가능한 멤버 간 요청이 대략 고르게 분산됨. 정확한 교대 호출이나 균등한 토큰 소비는 아님
가중치 기반동일 우선순위, 가중치 3:1적절한 표본에서 요청이 약 75%/25%로 분산됨. 남은 TPM을 조회하거나 해당 토큰 비율을 강제하지 않음
우선순위 기반백엔드 A 우선순위 1, B 우선순위 2A를 우선 사용하고 우선순위가 높은 그룹의 멤버가 차단되어 사용할 수 없을 때 B를 사용
우선순위와 가중치 결합우선순위 그룹 내 가중치주 그룹 안에서 분산하고 우선순위가 높은 모든 멤버를 사용할 수 없을 때 다음 그룹을 사용

우선순위 숫자가 작을수록 우선합니다. 응답이 느리거나 남은 TPM이 낮다는 이유만으로 여기서 설명한 우선순위 전환이 발생하지는 않습니다. 모델/버전/API/매개 변수가 일치하면 PTU 우선/종량제 대체 구성을 우선순위 그룹으로 구현할 수 있습니다. 복구된 주 멤버는 차단기가 트래픽을 허용하면 다시 선택 대상이 됩니다. 이미 실패한 요청을 다시 보내는 것은 풀이 아니라 재시도 정책의 역할입니다.

계정 여섯 개로 확장한다면 여섯 개를 모두 같은 우선순위에 두어 처리량을 지속적으로 사용하거나 주 멤버 세 개와 보조 멤버 세 개로 구성할 수 있습니다. 주 그룹을 사용할 수 있는 동안에는 일반적으로 대기 그룹의 처리량을 사용하지 않습니다. 이는 설계 대안이지 두 계정 PoC에 적용한 변경이 아닙니다. 분산 게이트웨이의 선택과 회로 차단기 동작은 근사적으로 작동하며 라운드 로빈 자체가 가장 높은 가용성을 보장하지는 않습니다.

선택 사항: 팀 우선 라우팅

원문에서는 클라이언트 팀마다 별도 풀을 두는 방식을 검토했지만 구현하지 않았습니다. 같은 Single 백엔드를 재사용하되 해당 팀의 풀에서 자기 팀 계정에 우선순위 1, 다른 계정에 우선순위 2를 지정합니다. 정책이 context.Subscription.Id로 풀을 선택하면 풀이 사용 가능한 멤버를 선택합니다. 원시 키를 매핑 키로 저장하거나 요청마다 풀 우선순위를 바꾸지 마세요.

  • context.Subscription.Id는 APIM API 액세스 구독 ID이지 Azure 리소스 구독 ID가 아닙니다. 같은 APIM 구독의 기본 키와 보조 키는 이 라우팅 결정에서 구분할 수 없습니다.
  • 클라이언트별로 APIM 구독을 따로 발급하고 알 수 없거나 누락된 구독을 명시적으로 거부하거나 처리합니다.
  • 다른 팀 계정으로의 대체를 허용하기 전에 권한과 비용 책임에 합의합니다. 백엔드를 공유하면 할당량, 부하 및 차단기 영향도 공유됩니다. 풀이 달라도 용량을 예약하지 않습니다.
  • 처음 선택한 팀 풀을 재시도 블록 안에서도 유지합니다. 다운로드 가능한 고정 풀 XML은 매 재시도마다 공통 풀로 초기화하지 않도록 의도적으로 수정해야 합니다.
  • 응답, 에이전트 또는 스레드 상태는 Foundry 계정 간에 자동 공유되지 않습니다. 계정 수준 장애 조치에는 별도의 상태 전략이 필요합니다.

3단계: APIM 관리 ID에 추론 액세스 부여

APIM → ID → 시스템 할당에서 ID가 활성화되어 있는지와 YOUR_APIM_PRINCIPAL_ID를 확인합니다. 각 Foundry 계정에서 액세스 제어(IAM) → 역할 할당 추가 → Cognitive Services OpenAI User → 관리 ID를 열고 APIM을 선택한 뒤 보안 주체 ID를 확인하고 계정 범위에 할당합니다. 원문에서는 계정당 하나씩 두 개를 할당하고 Chat Completions와 Microsoft.CognitiveServices/accounts/OpenAI/responses/*를 포함하는 데이터 작업을 검사했습니다.

공개 기본 제공 역할 정의 식별자 5e0bd9bd-7b93-4f28-af87-19fc36ad61bd는 Cognitive Services OpenAI User를 나타냅니다. 환경 식별자가 아니라 잘 알려진 Azure 역할입니다. PE, VNet, 프로젝트 또는 개별 모델 배포에 할당하는 것은 여기서 설명하는 구성이 아닙니다. APIM은 추론을 위해 구독 전체의 Contributor나 Owner가 필요하지 않습니다.

az apim show --subscription YOUR_APIM_SUBSCRIPTION_ID \
  --resource-group YOUR_APIM_RESOURCE_GROUP --name YOUR_APIM_NAME \
  --query identity.principalId --output tsv
az role assignment list --subscription YOUR_FOUNDRY_SUBSCRIPTION_ID \
  --scope YOUR_FOUNDRY_ACCOUNT_RESOURCE_ID \
  --assignee-object-id YOUR_APIM_PRINCIPAL_ID \
  --query '[].{role:roleDefinitionName,principalId:principalId,scope:scope}' -o table
# Create only after the successful listing confirms no equivalent assignment.
az role assignment create --subscription YOUR_FOUNDRY_SUBSCRIPTION_ID \
  --scope YOUR_FOUNDRY_ACCOUNT_RESOURCE_ID \
  --assignee-object-id YOUR_APIM_PRINCIPAL_ID \
  --assignee-principal-type ServicePrincipal \
  --role 5e0bd9bd-7b93-4f28-af87-19fc36ad61bd \
  --query '{id:id,principalId:principalId,roleDefinitionId:roleDefinitionId,scope:scope}' -o json

작업자는 적절한 RBAC 관리자 역할 등을 통해 대상 범위에서 Microsoft.Authorization/roleAssignments/write 권한이 있어야 합니다. Contributor만으로는 부족합니다. 같은 Entra 테넌트의 다른 구독에서도 동일한 시스템 할당 ID에 역할을 할당할 수 있습니다. 계정 관리자가 APIM 구독을 읽을 수 없다면 포털에서 APIM을 찾지 못할 수 있습니다. assignee-object-id와 ServicePrincipal로 보안 주체 Object ID를 전달하면 표시 이름/Graph 조회를 피할 수 있지만 역할 할당 권한을 우회하지는 않습니다. APIM ARM ID나 애플리케이션 Client ID를 대신 넣지 마세요. 테넌트 간 네트워크 도달 가능성이 테넌트 간 관리 ID 인증을 성립시키지는 않습니다.

RBAC와 토큰 전달 정책은 별도 단계입니다. RBAC 전파 시간을 고려하고 나중에 승인된 실제 테스트로 올바른 추론 대상을 확인하세요. 유지된 대상 https://cognitiveservices.azure.com은 프라이빗 호스트가 아니라 공개 서비스 식별자입니다.

4단계: API와 작업 정의

Language Model/Foundry 가져오기 마법사 자산이 아니라 일반 HTTP API를 만듭니다. YOUR_API_ID, YOUR_API_DISPLAY_NAME, HTTPS, 접미사 openai, subscriptionRequired=true, 키 헤더 Ocp-Apim-Subscription-Key, 키 쿼리 이름 subscription-key를 사용합니다. 운영에서는 헤더를 권장합니다. 정책이 URL이 없는 풀을 선택하므로 serviceUrl은 지정하지 않습니다.

az apim api list --subscription YOUR_SUBSCRIPTION_ID \
  -g YOUR_APIM_RESOURCE_GROUP --service-name YOUR_APIM_NAME \
  --query "[?name=='YOUR_API_ID' || path=='openai'].name" -o tsv
# Stop if either the intended ID or the openai path already exists.
az apim api create --subscription YOUR_SUBSCRIPTION_ID \
  -g YOUR_APIM_RESOURCE_GROUP --service-name YOUR_APIM_NAME \
  --api-id YOUR_API_ID --display-name "YOUR_API_DISPLAY_NAME" \

5단계: 작업 XML 적용과 인바운드 처리 이해

chat.xml, legacy-chat.xml, responses.xml을 각각 수정하고 대응하는 작업에만 적용합니다. 원문에서는 한 번에 하나의 작업 정책만 적용하고 무관한 드리프트를 거부했으며, Accept: application/json 및 format=rawxml로 저장된 정책을 다시 읽어 정규화된 XML을 비교했습니다. 저장된 정책이 일치한다는 것은 배포 검증이지 추론 성공 검증이 아닙니다.

  1. <base />는 상위 인바운드 정책을 유지합니다.
  2. <set-variable name="attemptCount" value="@(0)" />는 전달 시도 집계를 초기화합니다.
  3. rewrite-uri는 /openai를 포함한 전체 백엔드 경로를 설정합니다. copy-unmatched-params=false는 추가 쿼리 매개 변수의 자동 전달을 막을 뿐 JSON 본문을 막지 않습니다.
  4. Foundry 호출 전에 수신 api-key, Ocp-Apim-Subscription-Key 및 Cookie 헤더를 삭제합니다. APIM은 이미 구독 키를 인증했으며 이후에도 context.Subscription을 사용할 수 있습니다.
  5. 상관 관계를 위해 x-ms-client-request-id를 context.RequestId.ToString()으로 덮어씁니다.
  6. Cognitive Services 대상과 ignore-error=false로 authentication-managed-identity를 사용합니다. 토큰 획득 실패를 무시하지 않으며 정책은 APIM 시스템 ID로 백엔드 Authorization을 설정합니다.
<authentication-managed-identity
  resource="https://cognitiveservices.azure.com"
  ignore-error="false" />

Legacy는 고정 배포 경로로 다시 쓰고 호출자가 다른 버전을 보냈더라도 api-version을 2024-10-21로 덮어씁니다. 일반적인 배포/버전 통과 전달이 아닙니다. Responses는 /openai/v1/responses로 다시 쓰며 set-body가 없습니다. input, store, previous_response_id는 클라이언트의 선택으로 유지됩니다.

백엔드 처리: 횟수가 제한된 429 재시도

<retry condition="@(true &amp;&amp; context.Response != null &amp;&amp; context.Response.StatusCode == 429)"
       count="1" interval="1" first-fast-retry="false">
  <set-variable name="attemptCount"
    value="@(context.Variables.GetValueOrDefault&lt;int&gt;(&quot;attemptCount&quot;, 0) + 1)" />
  <set-backend-service backend-id="YOUR_POOL_ID" />
  <forward-request timeout="60" http-version="1" follow-redirects="false"
    buffer-request-body="true" buffer-response="false"
    fail-on-error-status-code="false" />
  <!-- The complete downloads include backend-attempt trace metadata here. -->
</retry>

retry는 자식을 한 번 실행한 후 null이 아닌 응답의 상태가 429인 경우에만 반복합니다. count=1, interval=1, first-fast-retry=false는 1초 후 한 번 추가 시도한다는 의미로, 전송은 최대 두 번입니다. 이 조건은 400, 401, 403, 5xx 또는 응답이 없는 연결 실패를 재시도하지 않습니다. 풀 선택이 블록 안에 있으므로 개별 차단기가 반응한 후 각 전송에서 사용 가능한 멤버를 선택할 수 있습니다.

  • timeout=60은 각 시도에서 응답 헤더를 기다리는 시간에 적용되며 전체 요청 또는 스트림 완료 기한이 아닙니다.
  • http-version=1은 HTTPS 백엔드 연결에서 HTTP/1을 사용합니다. 리디렉션은 따르지 않습니다.
  • buffer-request-body=true는 재시도를 위해 요청을 유지합니다. buffer-response=false는 스트리밍/SSE 전달을 허용하지만 이 구성이 스트리밍을 성공적으로 테스트했다는 근거는 아닙니다.
  • fail-on-error-status-code=false는 400–599만으로 즉시 on-error로 이동하는 것을 막아 바깥 retry가 429를 검사하도록 합니다. 실패를 성공으로 바꾸지는 않습니다.
  • 정책은 모든 백엔드를 사용할 수 없을 때의 503 같은 응답을 숨기지 않습니다. 원문은 모든 멤버가 차단된 상황의 전체 복구 테스트를 완료하지 않았습니다.

시도별 메타데이터

전달 후 backend-attempt는 requestId, operation, attempt, configuredBackend, backendId, backendHost, status, elapsedMs, retryAfter, retryAfterMs를 기록합니다. 원문에서 context.Backend.Id는 풀 ID로 남을 수 있었지만 context.Request.Url.Host는 실제 Foundry 멤버를 식별했습니다. 풀 식별자를 선택된 계정으로 집계하지 마세요. 호스트를 구성된 FQDN 및 Application Insights 종속성 대상과 일치시킵니다.

elapsedMs는 요청 시작부터 누적된 시간이지 해당 시도의 개별 추론 지연 시간이 아닙니다. 추적 메타데이터는 비어 있을 수 없으므로 비어 있거나 공백만 있는 Retry-After 및 retry-after-ms 헤더는 not-present로 기록합니다. 이 정규화는 추적 값에만 영향을 줍니다. 실제 헤더를 다시 쓰거나 재시도 시점 또는 회로 차단기를 바꾸지 않습니다. 프롬프트, 응답 텍스트, 쿠키, 자격 증명 헤더는 추적 필드가 아닙니다.

Responses 상태, 저장 및 계정 간 실패

현재 Responses 템플릿은 store=false를 강제하지 않습니다. 이전 정책은 이를 강제했으며 원문에서는 나중에 알려진 해당 변환만 제거하고 저장된 XML을 확인한 뒤 다른 정책은 그대로 두었습니다. 제거 후 별도 추론 재실행은 문서화되지 않았습니다. HTTP 예제는 여전히 클라이언트 테스트 선택으로 store=false를 지정합니다. store를 생략하면 서비스 기본값을 따르며 저장이 허용될 수 있습니다.

원문에서는 한 Foundry 계정에서 생성한 응답을 다른 계정에서 참조하면 실패하는 현상을 관찰했습니다. 결과는 HTTP 400, type invalid_request_error, param previous_response_id, code previous_response_not_found였습니다. 배포 이름이 같다고 응답 상태를 공유하는 것은 아닙니다. 이는 조용히 대화 맥락을 잃는 현상이 아니라 명시적 오류이며 현재 429 전용 정책은 이를 재시도하지 않습니다.

또 다른 관찰에서는 store=false 테스트에서 ID를 제공했을 때 문맥에 맞는 답변을 반환했습니다. 따라서 이런 ID가 모두 즉시 실패해야 한다거나 store=false가 즉각적이고 완전한 삭제를 입증한다고 주장하지 마세요. 뒷받침되는 결론은 더 제한적입니다. 계정 전환으로 이전 응답 ID를 확인할 수 없게 될 수 있습니다. 장기 보존과 ID 수명은 검증되지 않았습니다.

대화 방식설계 요구 사항
input으로 기록 재전송클라이언트가 관련 사용자 입력, 어시스턴트 출력 및 도구 항목을 유지합니다. 계정의 서버 측 상태에 대한 의존도가 낮으며 이 풀 예제에서 권장하는 방식입니다.
previous_response_id 연결대화 상태를 보유한 계정으로 라우팅하고 ID 유효성을 관리하며 장애 조치로 계정이 바뀔 때 기록 재전송 또는 다른 복구 경로를 구현합니다.

이 템플릿에는 대화 선호도나 상태 복구가 구현되어 있지 않습니다. 정책은 previous_response_id를 삭제하거나 변환하지 않습니다. 원문에는 store=false, null previous_response_id/conversation, 기본 서비스 계층, 도구 없음 및 128토큰 상한의 요청 스키마 생성기 테스트도 남아 있었지만 현재 XML에는 validate-content나 해당 스키마가 포함되어 있지 않습니다. 이전에 검토한 32-KiB 요청 검증 제한도 적용하지 않습니다. 테스트 스크립트 예산과 출력 제한은 보편적인 게이트웨이 제한이 아닙니다.

6단계: 기존 Application Insights 연결

이 절차는 이미 준비된 Insights 리소스를 연결하며 새로 만들지 않습니다. Logger는 대상과 인증을 지정합니다. API Diagnostic은 그 Logger를 사용해 무엇을 얼마나 수집할지 지정합니다. Logger만 생성해서는 API 로깅이 완료되지 않습니다.

  1. 보안/관리 ID 또는 동등한 포털 블레이드에서 APIM의 시스템 할당 ID를 확인합니다.
  2. YOUR_APPLICATION_INSIGHTS_NAME의 IAM에서 해당 ID에 Monitoring Metrics Publisher를 부여하되 범위를 해당 Insights 리소스로만 제한합니다. 이 역할에는 Microsoft.Insights/Telemetry/Write와 Microsoft.Insights/Metrics/Write가 포함됩니다.
  3. Foundry 추론 역할을 로그 수집 권한으로 착각하지 마세요. 추론 대상은 그대로 유지합니다.

메타데이터에는 여전히 URL, 작업 이름, 상태 및 시간이 포함될 수 있습니다. 알려진 자격 증명 매개 변수를 마스킹해도 임의의 쿼리 이름에 들어 있는 임의의 비밀을 인식하지는 못합니다. URL에 프롬프트, 개인정보, 토큰 또는 키를 넣지 마세요. 정책 추적 심각도는 진단 상세 수준 임계값을 충족해야 합니다. 원문 문서는 추적 정책의 내보내기가 Application Insights 샘플링의 영향을 받지 않는다고 설명합니다. 요청 샘플링을 줄여도 명시적 추적 레코드가 비례해서 감소한다고 볼 수 없습니다.

7단계: 요청, 종속성 및 시도 검사

인증되지 않은 401처럼 전달 전에 거부된 요청에는 backend-attempt 추적이 없습니다. 원문은 9월 14일 07:26:54 UTC에 이런 요청 하나와 07:26:56의 상관 관계가 있는 AppRequests 이벤트 타임스탬프를 기록했습니다. 이후 Legacy 호출 세 개는 종속성 세 개와 backend-attempt 추적 세 개를 생성했고 각각 attempt=1, status=200으로 백엔드 2, 백엔드 1, 백엔드 2를 선택했습니다. 해당 추적의 수집 지연은 약 190–199초였으며 고정된 서비스 간격이 아닙니다.

Legacy 전용 토큰 사용량 추적

legacy-chat.xml만 backend/retry 내부에서 forward-request와 backend-attempt 뒤에 choose id="legacy-token-usage"를 추가합니다. Content-Type이 application/json으로 시작하는 HTTP 200 응답에서 실행됩니다. SSE에서는 실행되지 않으며 buffer-response=false, 요청/응답 본문 진단 설정 또는 metrics=false를 변경하지 않습니다.

정책은 preserveContent:true로 응답을 JObject로 읽습니다. 입력은 prompt_tokens 또는 input_tokens, 출력은 completion_tokens 또는 output_tokens를 사용하고 total_tokens도 함께 받습니다. 세 필드 모두 JTokenType.Integer여야 usageStatus=reported가 됩니다. 그렇지 않으면 usageStatus=not-reported이고 토큰 필드는 null입니다. model이 없으면 not-reported를 사용합니다. 원래 모델 텍스트와 추론 세부 정보는 별도의 청구 토큰 합계로 사용하지 않습니다.

APIM 구독 ID를 사용하면 한 구독의 기본/보조 키가 합쳐지며 키 교체 시 논리적 ID를 바꿀 필요가 없습니다. 클라이언트별 귀속을 위해서는 클라이언트마다 별도 APIM 구독이 필요합니다. PreserveContent는 호출자가 응답을 계속 받을 수 있게 합니다. 추적은 선택한 메타데이터만 기록하며 프롬프트, 답변 텍스트 또는 인증 자료를 기록하지 않습니다. XML은 속성 안의 As<JObject> 같은 C# 제네릭을 이스케이프합니다.

traces
| where timestamp > ago(24h)
| where message has "llm-usage"
| extend Usage=parse_json(tostring(customDimensions.usage)),
         SubscriptionId=tostring(customDimensions.subscriptionId),

         InputTokens=tolong(Usage.inputTokens),

| summarize RecordedResponses=count(), InputTokens=sum(InputTokens),
            OutputTokens=sum(OutputTokens), TotalTokens=sum(TotalTokens)
  by SubscriptionId, BackendHost, Model
| order by TotalTokens desc

not-reported 레코드는 별도로 집계하세요. 사용량 누락은 0이 아니라 알 수 없음입니다. 다운로드 쿼리에는 개별 요청 검사와 사용량 누락 건수가 포함됩니다. 승인된 새 Legacy 비스트리밍 호출 후 응답의 usage, X-PoC-Request-Id, X-PoC-Backend-Host를 새 llm-usage 행과 비교하세요. 과거 추적에는 소급 적용되지 않습니다.

첫 429 뒤에 200이 오면 backend-attempt에는 두 시도가 모두 있고 llm-usage는 성공한 시도를 기록합니다. 이 블록은 401, 429, 5xx 및 SSE를 제외합니다. 응답 없는 요청, 중단된 스트림 및 로그 손실 때문에 완전한 청구 원장이 될 수는 없습니다. 원문은 배포된 원시 XML과 로컬 XML의 일치를 검증했지만 블록 추가 이후 실제 새로 내보낸 llm-usage 값은 아직 대조하지 않았습니다. 이전 backend-attempt 성공을 이후 추가된 토큰 기능의 검증과 혼동하지 마세요.

운영 점검, 보존 및 비용

로그가 없으면 30분에서 1시간 범위를 살펴보고 다음 순서로 확인합니다. 올바른 API 진단/대상, 로거 ID와 Insights 범위 역할 할당, 쿼리 범위와 타임스탬프, 실제 백엔드 실행과 추적 심각도, 작업 영역 일일 상한, 마지막으로 Azure Monitor 수집 및 인증 엔드포인트 연결입니다.

평가한 모니터링 경로는 관리 ID와 퍼블릭 Azure Monitor 엔드포인트를 사용했습니다. Foundry PE 연결이 원격 분석까지 프라이빗으로 만들지는 않습니다. 프라이빗 모니터링이 필요하다면 별도의 AMPLS, 프라이빗 DNS 및 라우팅 설계가 필요합니다. 원문에서는 AMPLS, 모니터링 프라이빗 엔드포인트 또는 네트워크 규칙 변경을 추가하지 않았습니다.

PoC는 100% 수집, 30일 작업 영역 보존 및 1-GB 일일 수집 상한을 사용했습니다. 테이블 기본값이 작업 영역 기본값과 다를 수 있어 AppRequests, AppDependencies, AppTraces, AppExceptions의 Analytics 및 총 보존 기간도 명시적으로 30일로 설정했습니다. 작업 영역 설정이 모든 테이블을 제어한다고 가정하지 말고 작업 영역 → 테이블 → 테이블 관리를 확인하세요.

원문 조사 당시 East US 2 Analytics Logs 가격은 무료 허용량, 협의 할인 및 세금을 적용하기 전 약 USD 2.76/GB였습니다. 이는 당시 참조 가격이지 현재 견적이 아닙니다. 일일 상한은 엄격한 비용 한도가 아닙니다. 수집이 상한을 초과할 수 있고 상한에 도달하면 로그가 손실될 수 있습니다. 요청량, 명시적 추적 내보내기, 보존, 수집 성능 및 비용을 함께 고려하세요. 샘플링을 줄인 후의 원시 Request/Dependency 행 수는 실제 전체 요청 수와 같지 않을 수 있습니다.

수동 요청 예제와 테스트 범위

네 개의 .http 다운로드에는 VS Code REST Client가 필요합니다. 확장 호스트가 상속하는 환경에 APIM_SUBSCRIPTION_KEY를 설정하고 필요하면 VS Code를 완전히 다시 시작한 후 YOUR_APIM_HOST와 YOUR_DEPLOYMENT_NAME을 대체합니다. Foundry 공급자 키나 Azure 구독 ID가 아니라 APIM API 액세스 키를 사용하세요. 키를 파일과 Git에 넣지 마세요. 각 요청은 수동으로 시작하며 추론 요금이 발생할 수 있습니다.

  • v1test.http는 model 필드, api-version 없음, max_completion_tokens=128, reasoning_effort=none, stream=false, store=false를 사용합니다.
  • legacytest.http는 고정 배포 URL과 2024-10-21을 사용합니다. 원문의 max_completion_tokens=10000과 reasoning_effort=high를 의도적으로 유지하므로 다른 예제의 128토큰 비용 특성과 다릅니다. 프롬프트는 영어로 번역되어 있습니다.
  • responsetest.http는 max_output_tokens=128, 추론 수준 none, stream=false, store=false로 단일 Responses 요청을 보냅니다. 완료 상태와 진단 헤더를 검사하세요.
  • responsetest2.http는 합성 코드를 사용하는 첫 턴, 클라이언트가 기록을 재전송하는 후속 요청, YOUR_PREVIOUS_RESPONSE_ID를 사용하는 후속 요청을 비교합니다. 마지막 값은 새로 생성한 응답 ID로 대체하세요. 기록 예제는 첫 턴의 확인 응답 지시를 의도적으로 재전송하지 않습니다. 실제 대화에서는 필요한 어시스턴트 출력과 도구 항목을 유지해야 합니다. 백엔드 변경은 보장되지 않습니다. previous_response_id를 제거하면 UNKNOWN을 기대하는 별도의 기록 없는 대조군이 됩니다.

원본 Python unittest 파일 세 개를 모두 읽었으며 민감 정보를 제거한 참조 전용 다운로드로 포함했습니다. 원본 스크립트 디렉터리, 렌더러/설정/템플릿 및 소유권 상태가 제공되지 않아 단독 실행할 수 없습니다. 원문의 어설션을 만들어 낸 도우미로 대체하지 않고 유지했습니다. 다운로드 헤더는 종속성, 합성 픽스처 및 클라우드 검증이 없다는 점을 설명합니다. 호환되는 원본 프로젝트를 별도로 검토할 때만 POC_SOURCE_ROOT를 설정하세요. 이 환경 변수 또는 필수 도우미 파일이 없으면 부트스트랩은 명시적으로 실패합니다. 단위 테스트 픽스처에 프로덕션 자격 증명을 넣지 마세요.

원문 변경 이력과 검증 경계

원문의 순차적 자동화 이력은 일부 단계 노트가 아직 적용되지 않았다고 설명한 이유를 보여 줍니다. 원본 스크립트는 포함하지 않으며 해당 명령을 사용 가능한 배포 진입점으로 취급해서는 안 됩니다. 순서는 configure-apim.py --backends-only, 이어서 --pool-only; grant-inference-role.sh; configure-apim.py --api-only; Chat용 apply-chat-policy.py, 이어서 --legacy; Chat과 Legacy용 --fix-trace-metadata; monitoring.py; apply-chat-policy.py --responses; --responses --remove-store-override; --legacy --add-token-usage였습니다. 이는 쓰기 범위를 보호하면서 원본 환경에서 승인받아 수행한 변경이지 이 공개 페이지를 위해 수행한 작업이 아닙니다.

다운로드와 공식 참조

모든 다운로드는 사용자의 값을 입력해야 하는 민감 정보 제거 원문 기반 템플릿이며 검증된 배포 결과물이 아닙니다. single-backends.json과 pool.json은 원문의 쌍 배열 래퍼를 유지합니다. 세 XML 정책은 전달, 횟수가 제한된 재시도, 추적 및 오류 헤더 로직을 유지합니다. 네 HTTP 파일은 서로 다른 클라이언트 테스트를 유지합니다. monitoring.kql에는 가이드의 쿼리 일곱 개가 있습니다. logger.json은 가이드의 로거 구조를 재현하고 diagnostic.json은 문서화된 설정을 하나의 템플릿으로 구성합니다. test_gateway.py, test_legacy_usage.py, test_monitoring.py는 참조 전용이며 누락된 원본 도우미 모듈과 템플릿이 필요합니다. 독립 실행형 테스트 도구가 아닙니다. 다운로드를 준비하면서 원본 스크립트를 실행하거나 클라우드 리소스를 변경하지 않았습니다.
