범위와 읽기 안내

이 문서는 2026년 7~8월의 ASE v3 조사를 종합합니다. 원래 목표는 프런트 엔드 CPU 및 메모리 메트릭에 반응하는 것이었습니다. 그러나 조사에서 메트릭 샘플 누락과 상당한 확장 지연이 확인되어, 예약에 따른 선제적 용량 확보로 방향을 바꿨습니다. 초기 실험용 런북을 구현하기 전에 최종 설계 방향을 읽으세요.

중요: 이 문서는 관찰에 기반한 분석이며 Microsoft의 공식 지침이 아닙니다. 측정값, 청구에 관한 추론, 포털 동작 및 API 특성은 특정 테스트 환경을 설명하며 다른 환경에 적용된다는 보장이 없습니다. 특히 프런트 엔드 가격, 청구 공식 및 청구 동작 해석은 관찰 데이터에 근거하며 Microsoft의 공식 가격 발표, 계약상 약속 또는 SLA가 아닙니다. 아키텍처나 예산을 결정하기 전에 최신 문서와 가격, Microsoft와 체결한 계약을 확인하세요.

테스트 구성은 East US의 외부 VIP ASE v3, Linux I1v2 작업자, Node.js 22 LTS 샘플 애플리케이션, 시스템 할당 관리 ID를 사용하는 Automation 계정이었습니다. 서비스가 보고한 프런트 엔드 크기는 Standard_D2d_v4였습니다. 실제 환경 식별자는 변수로 대체했습니다.

누락은 0이 아님

원문에서는 누락 구간이 average: 0, count: 0으로 표시되는 것을 확인했습니다. 호환되는 메트릭 쿼리에 Count를 포함하고 count > 0인 점만 사용하세요. 평균이 null이 아닌지만 필터링하면 누락된 측정값을 유휴 용량으로 오인하여 위험한 축소를 유발할 수 있습니다. 메트릭이 지원하는 집계를 사용하세요. 애플리케이션 요청량은 합계이며 작업자 CPU처럼 평균이 아닙니다.

애플리케이션 Requests를 수요의 대리 지표로 사용하고, 작업자 CPU, 메모리, HttpQueueLength는 보조 신호로 활용하세요. 작업자 CPU는 프런트 엔드 CPU가 아닙니다. AverageResponseTime은 애플리케이션 사용 환경 저하를 나타낼 수 있지만 이것만으로 프런트 엔드 병목을 분리해 판단할 수는 없습니다.

원문은 게시된 PowerShell 런북을 유지했지만 시간 조사 후 반응형 일정을 비활성화했습니다. 런북 소스 자체는 저장소에 없습니다. 이 절은 보고된 동작을 설명하며 다운로드 가능하거나 프로덕션에 바로 적용할 수 있는 구현이 아닙니다.

인증에는 Connect-AzAccount -Identity를 사용했습니다. ASE 범위에 Monitoring Reader를 할당했습니다. Ingress 쓰기에는 App Service Environment Contributor가 필요했고 Website Contributor만으로는 Microsoft.Web/hostingEnvironments/configurations/write 권한이 없었습니다. 실험에는 앱/요금제 조작과 초기 모니터링 실험을 위한 더 광범위한 리소스 그룹 역할도 있었습니다. 사용하지 않는 광범위한 할당을 프로덕션에 그대로 복사하지 마세요.

조사에서 권장한 방향

요청한 프런트 엔드가 수십 분 후에 도착한다면, 수분 내에 급증하는 트래픽을 반응형 확장으로 안정적으로 흡수할 수 없습니다. 제안된 대안은 안정적인 기본값, 선택적 일일 시간대, 명시적 이벤트 재정의를 정기적으로 조정하는 목표 상태 일정이었습니다.

{
  "timeZone": "Korea Standard Time",
  "default": 2,
  "daily": [
    {"days": "Mon-Fri", "from": "08:00", "to": "20:00", "min": 3}
  ],
  "overrides": [
    {
      "start": "2030-01-15T08:00",
      "end": "2030-01-15T13:00",
      "min": 4,
      "reason": "Example event",
      "owner": "EVENT_OWNER"
    }
  ]
}

이는 설명용 스키마이며 활성 일정이나 실행 가능한 구현이 아닙니다. 사용 전에 예제 이벤트 날짜와 담당자를 바꾸세요.

  • 요구 사항이 겹치면 마지막 쓰기 우선 방식이 아니라 요청된 하한의 최대값을 적용하세요.
  • 선행 시간 설정을 자동으로 적용하세요. 관찰에 따른 계획 모델에서 40분의 여유는 08:00 이벤트에 대해 07:20까지 요청해야 한다는 뜻입니다. 자신의 환경에 적합한 여유 시간을 측정하세요.
  • 만료된 재정의는 무시하고 오래된 항목에는 경고하며 이벤트 종료 후 최소값을 낮추세요.
  • 비용이 큰 입력 실수를 방지하도록 명시적인 최대 허용 설정값을 적용하세요.
  • 일정 시간대를 명시적으로 변환하세요. Automation 작업은 UTC로 실행됩니다.
  • 구성이 잘못되면 현재 용량을 유지하고 운영자에게 경고하세요. 이벤트 중에 아무 알림 없이 기본값으로 재설정하면 안 됩니다.
  • 반복 실행되는 조정기를 사용해 호출 실패를 재시도하되 확장 중에 충돌하는 변경은 피하세요.

배포 및 문제 해결에서 얻은 교훈

  • 할당량: 배포 전에 대상 지역을 확인하세요. 지원되는 지역이라도 사용 가능한 할당량이 0일 수 있습니다.
  • SCM 연결 가능 여부: 네트워크 시간 초과와 인증 응답을 구분하세요. ASE 네트워킹 요구 사항을 검토하고 필요한 원본/포트로 액세스를 제한하세요. 실험실의 광범위한 인터넷 허용 규칙을 복사하지 마세요.
  • 런타임: az webapp list-runtimes --os-type linux를 확인하세요. 원문 환경에서는 Node 20이 거부되어 지원 옵션 중 Node 22 LTS를 선택했습니다.
  • 중지된 앱: 이전 시작 실패로 애플리케이션이 중지된 상태에서도 배포는 성공할 수 있습니다. 애플리케이션 상태와 시작 로그를 확인하세요.
  • Kudu 401: 의도한 배포 인증 방법을 확인하세요. 인증된 배포 실패를 우회하려고 기본 게시 자격 증명을 자동으로 활성화하지 마세요.
  • Ingress 403: Website Contributor로 충분하다고 가정하지 말고 관리 ID의 ASE 범위 쓰기 권한을 확인하세요.
  • 메트릭 샘플 없음: 지원되는 앱/요금제 신호를 수집하고 누락 데이터를 기록하세요. 0으로 채운 공백을 근거로 축소하지 마세요.
  • 부하 형태: 프런트 엔드는 요청을 프록시합니다. CPU를 소모하는 엔드포인트는 주로 작업자에 부하를 주므로 프런트 엔드 압력을 분리하지 못합니다. 테스트 권한이 있는 환경에서만 부하 테스트를 수행하세요.

과거 부하 실행에서는 HTTP 200 응답 126,458개, 중앙값 지연 0.81초, 약 180 요청/초가 보고되었습니다. 언급된 샘플 애플리케이션의 상태, CPU 소모, 메모리 할당 엔드포인트와 배포 패키지는 저장소에 없습니다. 원본 스크린샷, 지원 기록 및 환경 주소는 의도적으로 배포하지 않습니다.
