미리 보기의 배경과 범위

이 문서는 2026년 6월 10일 기능 비교와 이후의 Managed Instance on Azure App Service 개념 증명 보고서를 통합합니다. Azure SQL Managed Instance가 아니라 Windows 애플리케이션 호스팅을 다룹니다. 미리 보기의 제공 여부, API, 제한 및 포털 화면은 바뀔 수 있으므로 배포 전에 최신 제품 개요를 확인하세요.

초기 기능 개요에서는 프라이빗 엔드포인트의 범위와 최대 확장 규모가 미확정 상태였습니다. 이후 PoC에서는 앱 범위의 프라이빗 엔드포인트와 P1v4 요금제의 최대 작업자 30개를 관찰했습니다. 이 결과는 해당 실험을 명확히 설명하지만 모든 지역, SKU 또는 향후 릴리스에 적용되는 불변의 제한을 정립하지는 않습니다.

기능과 운영 책임

사용자 지정 구성 요소와 지속되는 구성

원문 개요는 설치 스크립트 사용 사례로 COM 구성 요소, 레지스트리 설정, IIS 구성과 ACL, MSI 설치 관리자, GAC 어셈블리, 사용자 지정 런타임, 지원되는 Windows 기능, 타사 구성 요소를 제시합니다. 이는 지원되는 레거시 Windows 워크로드를 위한 호환성 옵션이지 임의의 OS 변경을 허용한다는 의미가 아닙니다.

PowerShell 설치 스크립트를 ZIP으로 패키징하여 Azure Storage에 저장하고 관리 ID 액세스를 구성하세요. 시작 시 실행하여 교체되거나 확장으로 추가된 인스턴스에 구성을 다시 적용합니다. 스크립트는 반복 실행 가능하게 만들고 시작 및 실패 동작을 테스트하세요. RDP로 수동 변경한 내용은 일시적이며 배포 수단이 아닙니다.

설치 로그는 C:\InstallScripts\<SCRIPT_NAME>\Install.log에 있으며 콘솔/플랫폼 로그와 통합된다고 설명되어 있습니다. 레지스트리 어댑터는 민감한 레지스트리 값을 Key Vault 기반 구성으로 분리할 수 있습니다. 설치 스크립트나 소스 제어에 비밀을 넣지 마세요.

네트워킹, ID, 스토리지

지원되는 구성에 따라 생성 후 요금제 수준의 VNet 통합을 추가할 수 있습니다. 원문은 NSG, NAT Gateway, 라우팅 및 프라이빗 DNS를 다룹니다. PoC는 들어오는 프라이빗 엔드포인트가 여전히 개별 애플리케이션을 대상으로 함을 확인했습니다. 인바운드 액세스, 아웃바운드 라우팅, 이름 확인 및 Bastion 액세스를 서로 다른 문제로 다루세요.

기능 비교에서는 요금제 수준 관리 ID와 Key Vault 통합을 설명합니다. 그렇다고 모든 스토리지 마운트 작업이 ID 기반 인증을 지원하는 것은 아닙니다. 특히 이후 PoC에서는 키가 비활성화된 환경에서 포털의 Azure Files 마운트를 완료하지 못했습니다.

UNC/네트워크 공유 액세스, 드라이브 매핑 및 임시 로컬 스토리지가 호환성 기능으로 제시되었습니다. 임시 스토리지는 영구 애플리케이션 스토리지가 아닙니다. 원문은 임시 스토리지 2 GB를 인용했으며, 현재 SKU별 동작을 검증해야 합니다.

일반적인 애플리케이션 운영

원문은 TLS, 사용자 지정 도메인 바인딩, Microsoft Entra ID 기반 App Service Authentication, GitHub Actions, Azure DevOps, ZIP/패키지 배포, 패키지에서 실행과 같은 익숙한 배포 방식을 설명합니다. 이들은 Managed Instance만의 차별점이 아닙니다. 여기서 다루는 차별점은 지원되는 Windows 사용자 지정과 Bastion 기반 진단입니다.

원문은 당시 사전 설치된 런타임으로 .NET Framework 3.5/4.8 및 .NET 8을 나열했습니다. 대상을 선택하기 전에 런타임 지원과 수명 주기를 확인하세요. 로그 설계에는 요금제 수준 설치, 레지스트리 어댑터 및 마운트 이벤트를 포함하고, 로그 스트림 및 Azure Monitor 통합을 조기에 검증해야 합니다.

PoC 필수 조건과 변수

원문의 미리 보기 범위는 ASE 외부에서 Pv4/Pmv4 SKU로 실행하는 Windows 웹앱이었습니다. 당시 지원 지역은 East Asia, West Central US, North Europe, East US, Australia East, Central India, South India였습니다. 검토 범위에서는 도메인 가입, NTLM/Kerberos, Linux/컨테이너 워크로드, WebJobs 및 TCP/NetPipes가 지원되지 않는 것으로 보고되었습니다. 이 목록을 영구적인 사실로 보지 말고 최신 문서를 다시 확인하세요.

PoC는 앱 2개, 사용자 할당 ID, 스토리지 계정/공유, 분리된 프라이빗 엔드포인트 및 앱 통합 서브넷, Standard Bastion 배포를 사용했습니다. 아래 명령은 원문에 기반한 예제이며 완전한 자동 배포가 아닙니다. 비용과 권한을 먼저 검토하세요. 전용 PoC 리소스 그룹과 사용하지 않는 비중첩 주소 범위를 선택하세요.

요금제 생성 및 식별

원문에서는 먼저 Windows Premium v4 요금제를 만든 뒤 REST로 미리 보기 전용 속성을 구성했습니다. 미리 보기 CLI 제공 여부와 스키마는 바뀔 수 있으므로 이 순서를 사용하기 전에 지원되는 생성 흐름을 확인하세요. 관찰된 중요한 구분 속성은 요금제 속성 isCustomMode: true였으며, hyperV나 isXenon가 아니었습니다.

# Windows is the default; do not add --is-linux for this Windows plan.
az appservice plan create -g "$RESOURCE_GROUP" -n "$PLAN_NAME" \
  -l "$LOCATION" --sku P1V4
PLAN_ID=$(az appservice plan show -g "$RESOURCE_GROUP" -n "$PLAN_NAME" --query id -o tsv)

az rest --method patch \
  --url "https://management.azure.com${PLAN_ID}?api-version=2024-11-01" \
  --body "{\"properties\":{\"isCustomMode\":true,\"planDefaultIdentity\":{\"identityType\":\"UserAssigned\",\"userAssignedIdentityResourceId\":\"$IDENTITY_ID\"}}}"

az resource show -g "$RESOURCE_GROUP" \
  --resource-type "Microsoft.Web/serverfarms" -n "$PLAN_NAME" \
  --query "{isCustomMode:properties.isCustomMode,tier:sku.tier,size:sku.size,maxWorkers:properties.maximumNumberOfWorkers}" -o json

az webapp create -g "$RESOURCE_GROUP" -p "$PLAN_NAME" -n "$APP_ONE"
az webapp create -g "$RESOURCE_GROUP" -p "$PLAN_NAME" -n "$APP_TWO"
az appservice plan show -g "$RESOURCE_GROUP" -n "$PLAN_NAME" \
  --query "{numberOfSites:numberOfSites,isCustomMode:isCustomMode}" -o json

원문이 기대한 결과는 isCustomMode: true, 계층 PremiumV4, 크기 P1v4 및 최대 작업자 30개였습니다. 요금제 생성 명령이 성공했다고 기능이 활성화되었다고 가정하지 말고 실제 응답을 확인하세요.

요금제 수준 통합과 Bastion RDP

관찰된 미리 보기에서 앱 수준 VNet 통합은 서버 팜의 VirtualNetworkSubnetId를 업데이트하라는 메시지와 함께 실패했습니다. 여기서 사용하는 아웃바운드 통합은 각 사이트가 아니라 Managed Instance 요금제에 구성하세요.

az appservice plan update -g "$RESOURCE_GROUP" -n "$PLAN_NAME" \
  --vnet "$VNET_NAME" --subnet "$APP_SUBNET_NAME"
az rest --method get \
  --url "https://management.azure.com${PLAN_ID}?api-version=2024-11-01" \
  --query "properties.{used:vnetConnectionsUsed,max:vnetConnectionsMax}" -o json

: "${NSG_NAME:?Set NSG_NAME}"
az network nsg create -g "$RESOURCE_GROUP" -n "$NSG_NAME" -l "$LOCATION"
az network nsg rule create -g "$RESOURCE_GROUP" --nsg-name "$NSG_NAME" \
  -n Allow-Bastion-RDP --priority 200 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes "$BASTION_SUBNET_CIDR" \
  --destination-address-prefixes "$APP_SUBNET_CIDR" --destination-port-ranges 3389
az network vnet subnet update -g "$RESOURCE_GROUP" --vnet-name "$VNET_NAME" \
  -n "$APP_SUBNET_NAME" --network-security-group "$NSG_NAME"

: "${BASTION_PUBLIC_IP_NAME:?Set BASTION_PUBLIC_IP_NAME}"
: "${BASTION_NAME:?Set BASTION_NAME}"
az network public-ip create -g "$RESOURCE_GROUP" -n "$BASTION_PUBLIC_IP_NAME" \
  -l "$LOCATION" --sku Standard --allocation-method Static
az network bastion create -g "$RESOURCE_GROUP" -n "$BASTION_NAME" -l "$LOCATION" \
  --vnet-name "$VNET_NAME" --public-ip-address "$BASTION_PUBLIC_IP_NAME" \
  --sku Standard --enable-tunneling true --enable-ip-connect true

NSG 예제는 원문의 Bastion→작업자 RDP 규칙을 다루며 완전한 Bastion 네트워킹 정책은 아닙니다. 필수 Bastion 네트워킹 규칙 전체와 기존 NSG를 검토하세요. 연결하여 사용하지 않는 동안에도 Bastion과 공용 IP에는 요금이 발생합니다.

  1. 지원되는 포털에서 App Service 요금제의 설정 → 구성 → Bastion/RDP 영역을 엽니다.
  2. Bastion을 통한 원격 데스크톱 허용 옵션을 활성화하고 저장합니다.
  3. 인스턴스를 열어 원하는 작업자를 선택하고 Bastion을 통해 연결을 선택합니다.
  4. IIS 관리자, 이벤트 뷰어 및 로그로 진단하고 영구 변경 사항은 설치 스크립트에 반영합니다.

원문은 당시 활성화 스위치가 포털에만 있었고 문서화된 CLI/API 설정 방법은 없었다고 보고했습니다. 상태 확인에는 properties.network.rdpEnabled를 읽었습니다. 원클릭 연결은 임시 자격 증명을 자동 제공했습니다. 이를 로그, Git에 커밋할 명령 또는 문서에 출력하거나 복사하지 마세요. 작업자는 일반적인 고객 소유 VM/NIC 리소스로 노출되지 않았습니다.

IIS 관리자에서 동일한 작업자에 애플리케이션 사이트 2개가 보였습니다. 이는 해당 PoC의 액세스와 배치를 확인한 것이지 설치 스크립트의 성공적인 실행을 확인한 것은 아닙니다.

Azure Files 마운트: UI 지원과 인증 지원 구분

: "${STORAGE_ACCOUNT:?Set an existing STORAGE_ACCOUNT}"
: "${FILE_SHARE:?Set FILE_SHARE}"
az storage share-rm create -g "$RESOURCE_GROUP" --storage-account "$STORAGE_ACCOUNT" \
  --name "$FILE_SHARE" --quota 5
az storage account show -g "$RESOURCE_GROUP" -n "$STORAGE_ACCOUNT" \
  --query "{allowSharedKeyAccess:allowSharedKeyAccess,allowBlobPublicAccess:allowBlobPublicAccess}" -o json

요금제 → 설정 → 구성 → 마운트 → 새 마운트의 테스트한 양식에는 Azure Files, 스토리지 계정/공유, F: 같은 사용자 지정 드라이브 문자, 필수 Key Vault 및 비밀 필드가 있었습니다. 비밀에는 스토리지 연결 문자열이나 계정 키가 들어 있어야 했습니다.

원문의 스토리지 계정은 allowSharedKeyAccess: false였으며 PoC에서 해당 흐름으로 마운트를 완료하지 못했습니다. 미리 보기 UI에 관리 ID 마운트 옵션이 없다고 보고했습니다. 이를 관찰된 호환성 장애로 보아야 하며 모든 Azure Files 인증 모드에 대한 일반적인 단정으로 해석하면 안 됩니다. 현재 Managed Instance 마운트 기능이 조직에서 허용하는 인증 방법과 맞는지 검증하세요. 단지 테스트를 통과시키려고 키 액세스를 다시 활성화하지 마세요.

원문은 스크립트 기반 대안의 가능성을 언급했지만 검증하지는 않았습니다. 여기서는 OAuth/SAS 드라이브 매핑 우회 방법이 지원되거나 작동한다고 제시하지 않습니다.

확장 및 설치 스크립트 검증

az appservice plan show -g "$RESOURCE_GROUP" -n "$PLAN_NAME" \
  --query "{maxWorkers:maximumNumberOfWorkers}" -o json

원문의 포털과 API는 모두 P1v4의 최대 인스턴스 수를 30으로 표시했습니다. 따라서 초기 기능 비교에서 MI 전용 제한이 명확히 문서화되지 않았다는 진술은 과거의 불확실성으로 남겨 두며, 후속 환경별 측정과 모순된다는 의미는 아닙니다.

installScripts[] 참조 구조는 확인했지만 참조된 scripts 컨테이너는 비어 있었습니다. 이 문서에는 실행 가능한 scripts.zip이나 설치 스크립트 내용이 함께 제공되지 않습니다. 원문에 남아 있던 검증 계획은 다음과 같습니다.

  1. IIS 모듈, ACL, 레지스트리 설정 및 허용되는 Windows 기능 1개를 다루는, 지원 범위 내의 반복 실행 가능한 스크립트를 준비합니다.
  2. 패키지를 업로드하고 관리 ID의 Blob 액세스를 확인합니다.
  3. 지원되는 진단 경로로 시작 로그와 적용된 구성을 검증합니다.
  4. 테스트 인스턴스를 다시 시작하거나 교체한 뒤 재적용을 확인합니다.
  5. 확장 후 새 인스턴스에도 동일한 구성이 적용되는지 확인합니다.

프로덕션 준비와 정리

  • 영구 구성은 검토한 스크립트에, 비밀은 Key Vault에 보관하세요.
  • 프로덕션 배포 전에 로깅, 설치 실패 처리 및 구성 요소 패치 책임을 검증하세요.
  • NSG, 라우팅 및 이름 확인을 실제 종속성 목록에 맞추세요.
  • 스테이징에서 다시 시작, 유지 관리, 확장 및 스토리지 인증 동작을 테스트하세요.
  • Microsoft Defender for Cloud와 워크로드에 적합한 모니터링을 고려하세요.
  • Bastion, 공용 IP, 스토리지 및 요금제 비용을 검토하고 더 이상 필요하지 않은 전용 PoC 리소스를 제거하세요. 리소스 그룹을 삭제하기 전에 포함된 리소스를 확인하세요.

원본 정리 절은 Bastion의 시간당 요금을 언급한 뒤 문장 중간에서 끝납니다. 완전한 정리 절차는 없습니다. 이 문서는 원문에 없는 삭제 스크립트를 만들어 내거나 리소스가 제거되었다고 주장하지 않습니다.

지원되는 레거시 Windows 종속성과 작업자 수준 진단이 중요하다면 Managed Instance를 선택하세요. OS 사용자 지정이 필요 없고 워크로드 지원 범위가 맞으면 일반 App Service를 우선 고려하세요. 환경 전체 격리와 확장 모델이 요구 사항이라면 ASE를 별도로 평가하세요.
