4. 과거 내부 NGINX 기준 구성 재현

과거 환경은 Azure CNI와 Cilium, 노드 3개의 Standard_D2as_v5 풀 및 이미 활성화된 Application Routing 추가 기능을 사용했습니다. 퍼블릭 기본 컨트롤러가 있었으며 초기에는 Ingress나 Gateway API 리소스가 없었습니다. 실제 풀 이름, Pod CIDR 및 주소는 의도적으로 생략했습니다. 퍼블릭 컨트롤러를 방해하지 말고 내부 컨트롤러를 추가로 만드세요.

제공된 sample-app.yaml은 demo 네임스페이스, ealen/echo-server:latest를 사용하는 echo Pod 2개 및 포트 80의 echo Service를 만듭니다. 이 이미지 태그는 과거 사용된 변경 가능한 태그이므로 프로덕션에서는 검토한 버전을 고정하세요. 실습 환경에서 생성된 내부 Service는 nginx-internal-0였으며 컨트롤러 Pod 2개는 Running 상태였고 메트릭 Service는 10254를 노출했습니다. 원본 테스트 명령은 이와 일치하지 않게 nginx-internal을 조회했습니다. 실제 생성된 Service를 찾아 해당 이름을 사용하세요.

최소 HTTP 기준 구성에는 주석이 많은 변환용 입력 대신 다음 Ingress를 적용하세요.

7. 내부 공유 Gateway 및 네임스페이스 경계

Gateway는 자체 데이터 플레인과 LB를 프로비전합니다. 따라서 네임스페이스마다 여러 Gateway를 만들면 IP와 프록시 Deployment도 많아집니다. gateway-system의 공유 Gateway를 사용하면 서비스 팀이 HTTPRoute를 각자의 네임스페이스에 유지하면서 하나의 진입점을 공유할 수 있습니다. 다음 고정 주소와 서브넷은 원본 환경 값이 아닌 자리표시자이므로 적용 전에 바꾸세요.

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shared-gateway
  namespace: gateway-system
spec:
  infrastructure:
    annotations:
      service.beta.kubernetes.io/azure-load-balancer-internal: "true"
      service.beta.kubernetes.io/azure-load-balancer-internal-subnet: "YOUR_INGRESS_SUBNET"
      service.beta.kubernetes.io/azure-load-balancer-ipv4: "YOUR_PRIVATE_LB_IP"
  gatewayClassName: approuting-istio
  listeners:
  - name: http
    hostname: "*.contoso.io"
    port: 80
    protocol: HTTP
    allowedRoutes:
      namespaces:
        from: Selector
        selector:
          matchLabels:
            shared-gateway: "true"
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: catalog-route
  namespace: ns-catalog
spec:
  parentRefs:
  - name: shared-gateway
    namespace: gateway-system
  hostnames: [catalog.contoso.io]
  rules:
  - backendRefs:
    - name: catalog-service
      port: 8080

네임스페이스와 백엔드 Service를 먼저 만들고 허용할 경로 네임스페이스에 kubectl label namespace ns-catalog shared-gateway=true 레이블을 지정하세요. 원본에는 from: All도 나오며 이는 모든 네임스페이스를 허용합니다. Selector는 범위를 더 좁히는 대안입니다. 모든 호스트를 수락하려면 호스트 이름을 생략하거나 *.contoso.io 같은 지원되는 와일드카드를 설정할 수 있습니다. * 단독으로는 유효한 호스트 이름 값이 아닙니다. 와일드카드는 일반적으로 최상위 도메인을 제외합니다.

HTTPRoute → Gateway 연결에는 ReferenceGrant가 아닌 리스너의 allowedRoutes가 필요합니다. 다른 네임스페이스의 Service를 참조하는 경로에는 대상 네임스페이스의 ReferenceGrant가 필요합니다. 다른 곳의 Secret을 참조하는 Gateway도 마찬가지로 명시적인 대상 네임스페이스 권한이 필요합니다. 경로와 같은 네임스페이스의 백엔드 Service에는 네임스페이스 간 권한 부여가 필요하지 않습니다. 이러한 API 권한 중 어느 것도 NetworkPolicy를 대체하지 않습니다.

10. 과거 다중 포트 Local 상태 프로브 문제

원본에서는 생성된 Service가 다중 포트(예: 15021+80 또는 80+443)를 사용하고 externalTrafficPolicy=Local인 경우 간헐적인 connection refused와 약 50% 성공률이 관찰되었습니다. 한 포트의 LB 프로브는 Pod가 없는 노드를 제외했지만 다른 포트는 모든 노드를 정상으로 판단하는 것처럼 보였습니다. 원본은 이를 단일 healthCheckNodePort를 둘러싼 생성 Service/프로브 연결 구성 탓으로 보았고, 제품 팀이 조사 중이며 예상 일정은 없다고 보고했습니다. 이는 빌드별 인시던트 보고서이며 모든 다중 포트 Local Service가 잘못되었다는 일반적인 Kubernetes 규칙이 아닙니다.

보고된 우회 방법은 생성 Service를 편집하는 대신 사용자 지정 ConfigMap으로 포트별 프로브 주석을 추가하는 것이었습니다. 원래 재현 사례는 빈 값을 보여주었으며 키가 존재하는 것만으로 포트 80이 성공했다고 보고했습니다.

11. Gateway 주변의 Cilium 정책

중앙 집중식 NGINX 컨트롤러에서는 이전에 네임스페이스 하나를 열면 되었습니다. 네임스페이스별 Gateway는 프록시 엔드포인트를 각자의 네임스페이스로 옮기므로 기존 허용 규칙이 더 이상 인그레스를 포괄하지 못할 수 있습니다. 표준 NetworkPolicy는 Cilium에서 동작하지만 다음 예제는 엔터티 표현을 위해 CiliumNetworkPolicy를 사용합니다. 적용 전에 실제 Gateway Pod 레이블을 확인하세요. 원본은 istio.io/gateway-name을 사용하며 생성 리소스 검사에서는 gateway.networking.k8s.io/gateway-name도 사용합니다.

apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-ingress-to-gateway
  namespace: demo
spec:
  endpointSelector:
    matchLabels:
      istio.io/gateway-name: demo-istio-gw
  ingress:
  - fromEntities: [world, cluster, health, remote-node]
    toPorts:
    - ports:
      - {port: "80", protocol: TCP}
      - {port: "443", protocol: TCP}
      - {port: "15021", protocol: TCP}
엔터티의미
world클러스터 외부 주소. 범위가 넓으며 애플리케이션 허용 목록이 아님
cluster클러스터 엔드포인트/호스트. 내부 트래픽을 폭넓게 허용
host엔드포인트의 로컬 노드
remote-node일부 SNAT/프로브 경로를 포함한 다른 노드
healthCilium 상태 엔드포인트. Azure LoadBalancer 프로브의 동의어가 아님
kube-apiserverAPI 서버. 이 인그레스 예제에서는 필요하지 않음

포트 80과 443은 애플리케이션 트래픽을 전달하며 15021은 Istio 상태/준비 상태 엔드포인트입니다. 광범위한 예제는 네임스페이스 격리보다 더 많은 접근을 허용합니다. 더 좁은 모델을 위해 원본은 퍼블릭 트래픽, 상태 트래픽 및 승인된 네임스페이스를 구분합니다. 다음 예제는 로컬 노드의 상태 트래픽 허용을 명시합니다.

apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: restricted-ingress-to-gateway
  namespace: demo
spec:
  endpointSelector:
    matchLabels:
      istio.io/gateway-name: demo-istio-gw
  ingress:
  - fromEntities: [world]
    toPorts:
    - ports:
      - {port: "80", protocol: TCP}
      - {port: "443", protocol: TCP}
  - fromEntities: [host, remote-node, health]
    toPorts:
    - ports:
      - {port: "15021", protocol: TCP}
  - fromEndpoints:
    - matchLabels:
        k8s:io.kubernetes.pod.namespace: frontend-allowed
    - matchLabels:
        k8s:io.kubernetes.pod.namespace: another-allowed
    toPorts:
    - ports:
      - {port: "80", protocol: TCP}
      - {port: "443", protocol: TCP}
광범위한 예제와 좁은 범위의 예제는 대안으로 사용하세요. Cilium 허용 정책은 합산되므로 광범위한 규칙을 설치한 채 두면 좁은 규칙의 효과가 사라집니다. externalTrafficPolicy=Cluster에서는 SNAT 이후 외부 트래픽이 remote-node로 보일 수 있습니다. 따라서 80/443에서 remote-node를 차단하면 외부 접근이 중단될 수 있습니다. 먼저 Local과 그 상태 프로브를 검증한 후 원본 범위를 좁히세요. 이 템플릿이 모든 AKS 네트워크 경로에 맞는다고 가정하지 말고 실제 프로브 원본 ID와 포트 변환을 확인하세요.

확장 가능한 네임스페이스 구성을 위해 승인된 네임스페이스에 레이블을 지정하되, 정규화되지 않은 Pod 레이블이 아닌 Cilium의 네임스페이스 레이블 표현을 사용하세요. 원본에는 정규화되지 않은 access-to-demo-gw 선택자가 있습니다. 엔드포인트 ID를 확인하고 해당 버전에 맞게 올바르게 정규화된 키를 사용하세요.

kubectl label ns frontend-allowed access-to-demo-gw=true
kubectl label ns another-allowed access-to-demo-gw=true
fromEndpoints:
- matchLabels:
    k8s:io.cilium.k8s.namespace.labels.access-to-demo-gw: "true"
kubectl exec -n kube-system ds/cilium -- cilium monitor --type drop | grep "YOUR_GATEWAY_POD_IP"
kubectl exec -n kube-system ds/cilium -- cilium endpoint list | grep demo

관련 엔드포인트가 있는 노드에서 진단을 실행하세요. DaemonSet exec는 다른 노드를 선택할 수 있습니다. 원본은 Gateway에서 백엔드로의 네임스페이스 간 정책 검증을 향후 작업으로 남겨 두었습니다. 정책으로 격리되는 경우 필요한 백엔드 인그레스, Gateway 이그레스, DNS, 상태 및 aks-istio-system과의 컨트롤 플레인 통신을 명시적으로 허용하세요. 정책은 선택한 Pod의 선택한 방향을 격리하며 네임스페이스의 모든 Pod를 자동으로 격리하지는 않습니다.

12. 권장 TLS 경로: Application Routing 운영자

운영자는 두 TLS 옵션인 kubernetes.azure.com/tls-cert-keyvault-uri 및 kubernetes.azure.com/tls-cert-service-account가 설정된 GatewayClass approuting-istio의 리스너를 감시합니다. kv-gw-cert-<gateway>-<listener>라는 SPC를 만들고 Gateway 네임스페이스의 같은 이름을 가진 kubernetes.io/tls Secret으로 CSI 동기화를 조정하며 certificateRefs를 패치합니다. 자료를 가져오는 주체는 여전히 CSI이며 운영자는 이 연결 과정을 자동화합니다. 이 경로에서는 관리자가 더미 Deployment를 유지할 필요가 없습니다.

  • Application Routing 운영자, Application Routing Istio Gateway 구현 및 관리형 Gateway API를 모두 활성화하세요.
  • OIDC 발급자 및 Microsoft Entra Workload Identity를 활성화하세요.
  • Secrets Store CSI Driver용 Azure Key Vault 공급자를 활성화하세요.
  • 적절한 범위의 Owner 또는 RBAC Administrator와 Managed Identity Contributor 역할 등, 역할 할당·UAMI·페더레이션 ID 자격 증명을 만들 수 있는 권한이 있어야 합니다.
  • 기존 NGINX 사용자는 NGINX를 계속 실행하면서 Gateway 구현을 활성화할 수 있습니다. OIDC/Workload Identity는 추가로 활성화해야 할 수 있습니다.

공유 Gateway ID 범위

Gateway가 gateway-system에만 있고 HTTPRoute가 여러 서비스 네임스페이스에 있으면 ServiceAccount, FIC 및 TLS 구성은 gateway-system에만 만드세요. 운영자가 생성하는 SPC와 Secret도 그곳에 있습니다. HTTPRoute만 포함하는 서비스 네임스페이스에는 인증서 ID를 중복 생성할 필요가 없습니다. allowedRoutes를 All 또는 제한된 Selector로 설정하고 네임스페이스 간 parentRefs를 사용하세요. 이러한 경로-Gateway 연결이나 같은 네임스페이스의 Secret에는 ReferenceGrant가 필요하지 않습니다.

개발용 인증서 및 두 가지 저장 방식

수동 원본은 OpenSSL로 유효 기간 365일의 RSA-2048 테스트 루트 및 서버 인증서를 만듭니다. 원본 서버 인증서에는 SAN이 없으므로 다음 예제는 호스트 이름 검증이 가능하도록 SAN을 명시적으로 추가합니다. 개인 키는 로컬 테스트 자료입니다. 커밋하거나 내용을 공개하지 마세요.

mkdir -p httpbin_certs
openssl req -x509 -sha256 -nodes -days 365 -newkey rsa:2048 \
  -subj '/O=example Inc./CN=example.com' \
  -keyout httpbin_certs/example.com.key -out httpbin_certs/example.com.crt
openssl req -out httpbin_certs/httpbin.example.com.csr -newkey rsa:2048 -nodes \
  -keyout httpbin_certs/httpbin.example.com.key \
  -subj '/CN=httpbin.example.com/O=httpbin organization'
printf 'subjectAltName=DNS:httpbin.example.com\n' > httpbin_certs/server.ext
openssl x509 -req -sha256 -days 365 -CA httpbin_certs/example.com.crt \
  -CAkey httpbin_certs/example.com.key -set_serial 0 \
  -in httpbin_certs/httpbin.example.com.csr -out httpbin_certs/httpbin.example.com.crt \
  -extfile httpbin_certs/server.ext

# A: store separate PEM key and certificate secrets.
az keyvault secret set --vault-name "$AKV_NAME" --name test-httpbin-key --file httpbin_certs/httpbin.example.com.key
az keyvault secret set --vault-name "$AKV_NAME" --name test-httpbin-crt --file httpbin_certs/httpbin.example.com.crt

# B: combine into a PFX and import a certificate object.
# OpenSSL prompts for an export password; do not put real passwords into a published script.
openssl pkcs12 -export -inkey httpbin_certs/httpbin.example.com.key \
  -in httpbin_certs/httpbin.example.com.crt -out httpbin_certs/httpbin.example.com.pfx
az keyvault certificate import --vault-name "$AKV_NAME" \
  --name test-httpbin-cert-pfx --file httpbin_certs/httpbin.example.com.pfx \
  --password "$YOUR_PFX_PASSWORD"
원본 PFX 내보내기/가져오기 블록에는 이미 마스킹되었거나 손상된 행이 있습니다. 숨겨진 내용은 복원하지 않았습니다. 위의 두 명시적 명령은 호출자가 제공하는 암호 변수로 의도된 작업을 표현합니다. 인증서 객체로 저장하면 Key Vault 인증서 메타데이터, 만료 모니터링 및 회전을 사용할 수 있습니다. 공급자가 지원하는 개인 키 인코딩을 선택하세요.

      key: tls.crt

    useVMManagedIdentity: "true"
    userAssignedIdentityID: "$CLIENT_ID"
    keyvaultName: "$AKV_NAME"
    cloudName: ""
    objects: |

        - |

원본의 인증서 객체 변형

수동 문서는 같은 Secret 별칭 매핑을 유지하면서 objects 배열을 다음과 같이 바꿉니다.

objects: |
  array:
    - |
      objectName: test-httpbin-cert-pfx
      objectType: secret
      objectAlias: test-httpbin-key
    - |
      objectName: test-httpbin-cert-pfx
      objectType: cert
      objectAlias: test-httpbin-crt
이 별칭 패턴은 원본 지침으로 보존한 것이며 원시 PFX 비밀이 자동으로 유효한 tls.key로 변환된다는 증거가 아닙니다. objectAlias는 마운트된 내용의 이름을 바꿉니다. 인증서/개인 키 형식은 공급자와 객체 형식에 따라 다릅니다. 사용하기 전에 설치된 공급자에서 tls.crt에 PEM 인증서가, tls.key에 일치하는 PEM 개인 키가 들어 있는지 검증하세요. 모든 objectType=cert 작업이 secret API를 사용한다고 가정하지 마세요. 인증서 검색과 개인 키를 포함한 비밀 검색은 권한 및 형식 의미가 서로 다릅니다. 원본의 포괄적 주장은 지나치게 일반화되어 있습니다.

최신 자료를 추적하려면 objectVersion을 생략하세요. 이를 설정하면 해당 객체 버전으로 고정되어 새 버전으로의 자동 회전을 막습니다.

19. 중앙 인증서 저장소 및 테넌트 격리

수동 Gateway별 패턴에서 모든 네임스페이스에 SPC와 동기화 Pod를 배치하면 유지 관리가 중복됩니다. 대안은 cert-store에 SPC 1개, 복제본 2개의 동기화 Deployment 1개 및 하나 이상의 TLS Secret을 두고 다른 네임스페이스의 Gateway가 해당 Secret을 참조하도록 명시적인 ReferenceGrant를 부여하는 것입니다. 이는 단일 공유 Gateway와 다릅니다. 여기서는 여러 Gateway가 중앙 집중식 인증서를 재사용합니다.

apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: gw-can-read-tls-secret
  namespace: cert-store
spec:
  from:
  - group: gateway.networking.k8s.io
    kind: Gateway
    namespace: tenant-a
  - group: gateway.networking.k8s.io
    kind: Gateway
    namespace: tenant-b
  to:
  - group: ""
    kind: Secret
    name: httpbin-credential
# Listener fragment on a Gateway in tenant-a or tenant-b:
tls:
  mode: Terminate
  certificateRefs:
  - kind: Secret
    namespace: cert-store
    name: httpbin-credential

대상 네임스페이스의 권한이 없으면 원본에서는 ResolvedRefs=False, RefNotPermitted와 함께 해당 리스너가 프로그래밍되지 않았다고 보고합니다. 같은 네임스페이스의 다른 참조/리스너까지 실패하는 것은 아닙니다. 전체 Pod가 잘못되었다고 보지 말고 실제 리스너 조건을 확인하세요.

kubectl describe gateway "YOUR_GATEWAY_NAME" -n "YOUR_APP_NAMESPACE"
kubectl get gateway "YOUR_GATEWAY_NAME" -n "YOUR_APP_NAMESPACE" \
  -o jsonpath='{.status.listeners[*].conditions[?(@.type=="ResolvedRefs")]}'

하나의 자격 증명 모음, 여러 인증서

SPC의 objects와 secretObjects는 모두 배열입니다. 원본의 인증서 2개 예제를 재현하려면 위와 같은 ID/자격 증명 모음/테넌트 필드로 cert-store에 SPC all-tls-spc를 만들고 다음 객체 별칭과 Secret 매핑을 사용하세요. 17절의 인증서 객체 형식 주의 사항은 여전히 적용됩니다.

# spec.parameters.objects fragment:
objects: |
  array:
    - |
      objectName: tenant-a-cert-pfx
      objectType: secret
      objectAlias: tenant-a-key
    - |
      objectName: tenant-a-cert-pfx
      objectType: cert
      objectAlias: tenant-a-crt
    - |
      objectName: tenant-b-cert-pfx
      objectType: secret
      objectAlias: tenant-b-key
    - |
      objectName: tenant-b-cert-pfx
      objectType: cert
      objectAlias: tenant-b-crt
# Corresponding spec.secretObjects:
secretObjects:
- secretName: tls-tenant-a
  type: kubernetes.io/tls
  data:
  - {objectName: tenant-a-crt, key: tls.crt}
  - {objectName: tenant-a-key, key: tls.key}
- secretName: tls-tenant-b
  type: kubernetes.io/tls
  data:
  - {objectName: tenant-b-crt, key: tls.crt}
  - {objectName: tenant-b-key, key: tls.key}

동기화 Deployment를 cert-store로 이동하고 secretProviderClass를 all-tls-spc로 바꾸세요. 그러면 마운트된 볼륨 하나가 해당 SPC의 객체를 포괄합니다. 각 Gateway는 cert-store에서 자신이 사용할 TLS Secret을 참조합니다.

ReferenceGrant 권한은 from[]과 to[]의 데카르트 곱입니다. tenant-a, tenant-b 및 두 TLS Secret을 하나의 권한 부여에 넣으면 각 테넌트가 두 Secret을 모두 참조할 수 있습니다. 테넌트 격리를 위해 승인된 네임스페이스/Secret 쌍마다 권한 부여를 하나씩 만드세요. 네임스페이스 권한 부여는 특정 이름의 Gateway 하나가 아니라 해당 네임스페이스의 Gateway 전반에 권한을 부여합니다.
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: tenant-a-to-own-certificate
  namespace: cert-store
spec:
  from:
  - {group: gateway.networking.k8s.io, kind: Gateway, namespace: tenant-a}
  to:
  - {group: "", kind: Secret, name: tls-tenant-a}
---
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: tenant-b-to-own-certificate
  namespace: cert-store
spec:
  from:
  - {group: gateway.networking.k8s.io, kind: Gateway, namespace: tenant-b}
  to:
  - {group: "", kind: Secret, name: tls-tenant-b}

의도적으로 모든 테넌트가 모든 인증서를 사용하도록 허용한다면 광범위한 권한 부여 하나가 더 단순하지만 격리는 약합니다. 새 격리 테넌트마다 인증서 객체, Secret 매핑 및 쌍별 권한 부여를 추가하세요. 인증서가 서로 다른 자격 증명 모음에 속하거나(keyvaultName은 SPC별 설정), 객체 수가 많아 폴링/제한 부담이 생기거나, 소유권/변경 주기상 장애 영향을 줄여야 하면 SPC를 나누세요.

여러 SPC가 하나의 동기화 Deployment를 공유할 수도 있습니다. SPC마다 CSI 볼륨 하나와 대응하는 volumeMounts를 마운트하세요. 원본에서 볼륨만 보여주는 개략적인 구성은 다음과 같습니다.

volumes:
- name: cert-a
  csi:
    driver: secrets-store.csi.k8s.io
    readOnly: true
    volumeAttributes: {secretProviderClass: spc-cert-a}
- name: cert-b
  csi:
    driver: secrets-store.csi.k8s.io
    readOnly: true
    volumeAttributes: {secretProviderClass: spc-cert-b}

수동 문제 해결 시 누락된 마운트 유지 리소스, CSI ID 권한, 별칭/Secret 이름 불일치, 고정된 버전, 회전 설정, 복제본 배치 및 ReferenceGrant를 확인하세요. Event Grid를 통해 웹후크 또는 Logic App으로 Key Vault 만료 알림을 보내는 방안을 고려하세요. Key Vault를 원본 저장소로 삼을 필요가 없다면 Azure DNS 또는 지원되는 Gateway HTTPRoute 솔버를 사용하는 cert-manager가 별도 대안이며 여기서는 구성하지 않습니다.

20. 공유 Gateway용 HTTPRoute 패턴

아래의 모든 패턴은 VirtualService나 EnvoyFilter가 아닌 표준 Gateway API를 사용합니다. 애플리케이션 네임스페이스와 참조되는 Service를 먼저 만드세요. 공통 경로 외곽 구조는 한 번만 보여줍니다. 이후 규칙은 표시된 경로 이름, 네임스페이스, 호스트 이름 및 리스너를 사용하여 같은 외곽 구조 아래에 넣는 조각입니다. 함께 적용할 하나의 집합이 아닌 별도 예제이며 겹치는 경로는 의도적인 충돌 해결이 필요합니다.

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: YOUR_ROUTE_NAME
  namespace: YOUR_ROUTE_NAMESPACE
spec:
  parentRefs:
  - name: shared-gateway
    namespace: gateway-system
    sectionName: https
  hostnames: [api.contoso.io]
  rules: []

YOUR_ 자리표시자는 유효한 소문자 Kubernetes 이름으로 바꾸세요. https 예제에는 shared-gateway의 일치하는 HTTPS 리스너와 인증서가 필요합니다. 7절의 HTTP 전용 Gateway는 해당 리스너를 제공하지 않습니다. Service 포트는 Service의 포트이며 반드시 컨테이너 포트와 같지는 않습니다.

경로 라우팅 및 대체 경로

ns-console의 console-route, 호스트 이름 console.contoso.io에서는 /orders/list가 /list로 orders-service:8080에 도달하고 다른 모든 경로는 web-frontend:80에 도달합니다.

rules:
- matches:
  - path: {type: PathPrefix, value: /orders}
  filters:
  - type: URLRewrite
    urlRewrite:
      path: {type: ReplacePrefixMatch, replacePrefixMatch: /}
  backendRefs:
  - {name: orders-service, port: 8080}
- matches:
  - path: {type: PathPrefix, value: /}
  backendRefs:
  - {name: web-frontend, port: 80}

포괄 규칙은 경로 대체 규칙이지 백엔드 5xx 응답을 가로채는 규칙이 아닙니다. 목록 순서와 관계없이 더 긴 접두사가 우선합니다. 가독성을 위해 대체 경로를 마지막에 배치하세요.

요청 제한 시간

ns-reports의 reports-timeout, https 리스너의 reports.contoso.io에 대한 예제입니다.

rules:
- matches:
  - path: {type: PathPrefix, value: /reports}
  backendRefs:
  - {name: reports-service, port: 8080}
  timeouts:
    request: 800ms

요청 제한 시간은 게이트웨이의 요청/응답 처리 시간을 제한합니다. 지원되는 제한 시간을 초과하면 504가 발생할 수 있습니다. 단순히 백엔드의 첫 바이트까지 걸리는 시간이 아닙니다. backendRequest는 개별 백엔드 시도를 별도로 제한할 수 있으며 둘 다 설정되어 있으면 request 이내여야 합니다. 300ms, 2s 또는 1m 같은 지원되는 기간 값을 사용하세요. 배치/보고서 API에는 더 긴 제한을, 지연 시간에 민감한 호출에는 더 짧은 제한을 선택하세요.

요청 및 응답 헤더 수정

ns-demo의 header-modify-demo, echo.contoso.io → echo-service:8080에 대한 예제입니다.

rules:
- matches:
  - path: {type: PathPrefix, value: /}
  filters:
  - type: RequestHeaderModifier
    requestHeaderModifier:
      add:
      - {name: x-forwarded-by, value: contoso-gateway}
  - type: ResponseHeaderModifier
    responseHeaderModifier:
      add:
      - {name: x-served-by, value: approuting-istio}
      set:
      - {name: cache-control, value: no-store}
  backendRefs:
  - {name: echo-service, port: 8080}

add는 추가하고 set은 대체하며 remove는 지정된 헤더를 삭제합니다. 같은 방식으로 x-frame-options 같은 보안 헤더를 설정할 수 있습니다. 프록시도 식별 헤더를 추가한다는 이유만으로 클라이언트가 제공한 식별 헤더가 신뢰할 수 있는 보안 경계가 되는 것은 아닙니다.

HTTP를 HTTPS로 리디렉션

ns-demo의 redirect-http-to-https, hostnames [*.contoso.io]에서는 parentRefs.sectionName을 http로 바꾸세요.

rules:
- filters:
  - type: RequestRedirect
    requestRedirect:
      scheme: https
      statusCode: 301

Gateway는 백엔드로 전달하지 않고 영구 리디렉션을 반환합니다. 먼저 HTTPS를 구성하고 검증하세요.

이전 도메인 이전

redirect-legacy-domain, https의 호스트 이름 shop-old.contoso.io에 대한 예제입니다.

rules:
- filters:
  - type: RequestRedirect
    requestRedirect:
      hostname: shop.contoso.io
      statusCode: 301

클라이언트가 새 호스트 이름으로 이동하는 동안 경로는 유지됩니다. HTTPS 리디렉션에는 이전 호스트 이름의 TLS 인증서와 리스너 일치가 모두 동작해야 합니다.

API 버전 /v1을 /v2로 리디렉션

redirect-api-version, api.contoso.io에 대한 예제입니다.

rules:
- matches:
  - path: {type: PathPrefix, value: /v1}
  filters:
  - type: RequestRedirect
    requestRedirect:
      path: {type: ReplacePrefixMatch, replacePrefixMatch: /v2}
      statusCode: 301
- matches:
  - path: {type: PathPrefix, value: /}
  backendRefs:
  - {name: api-backend, port: 8080}

클라이언트에는 변경된 URL이 보입니다. 버전 변환을 내부에만 유지해야 하면 대신 URLRewrite를 사용하세요.

리디렉션 없이 API 접두사 제거

rewrite-strip-api-prefix, api.contoso.io에서는 /api/users가 api-backend:8080에서 /users가 됩니다.

rules:
- matches:
  - path: {type: PathPrefix, value: /api}
  filters:
  - type: URLRewrite
    urlRewrite:
      path: {type: ReplacePrefixMatch, replacePrefixMatch: /}
  backendRefs:
  - {name: api-backend, port: 8080}

마이크로서비스 라우팅 및 버전 접두사 제거

rewrite-microservice-routing, app.contoso.io에 대한 예제입니다.

rules:
- matches:
  - path: {type: PathPrefix, value: /v1/users}
  filters:
  - type: URLRewrite
    urlRewrite:
      path: {type: ReplacePrefixMatch, replacePrefixMatch: /users}
  backendRefs:
  - {name: users-service, port: 8080}
- matches:
  - path: {type: PathPrefix, value: /v1/orders}
  filters:
  - type: URLRewrite
    urlRewrite:
      path: {type: ReplacePrefixMatch, replacePrefixMatch: /orders}
  backendRefs:
  - {name: orders-service, port: 8080}

백엔드 Host 재작성

ns-demo의 rewrite-host-header, 수신 호스트 legacy.contoso.io에서는 외부 URL을 유지하면서 서비스 로컬 Host를 보냅니다.

rules:
- filters:
  - type: URLRewrite
    urlRewrite:
      hostname: legacy-app.ns-demo.svc.cluster.local
  backendRefs:
  - {name: legacy-app, port: 8080}

특정 Host를 요구하는 기존 백엔드를 지원하기 위한 구성입니다. 서비스 DNS 이름은 클러스터 내 예시 이름이며 노출된 비공개 호스트 이름이 아닙니다.

전체 상태 경로 하나 대체

rewrite-health-endpoint, api.contoso.io에서는 정확한 /healthz → /actuator/health를 적용합니다.

rules:
- matches:
  - path: {type: Exact, value: /healthz}
  filters:
  - type: URLRewrite
    urlRewrite:
      path: {type: ReplaceFullPath, replaceFullPath: /actuator/health}
  backendRefs:
  - {name: api-backend, port: 8080}

일치 및 필터 규칙

  • Exact 경로는 PathPrefix보다 구체적이며 긴 접두사가 짧은 접두사보다 우선합니다. 메서드/헤더/쿼리 일치는 Gateway API 우선순위 규칙에 따라 구체성을 높입니다. 동률 및 경로 간 충돌에는 추가 표준 규칙이 있으므로 YAML 순서만으로 결정되지 않습니다.
  • PathPrefix는 임의의 정규식 구문이 아니라 경로 요소 경계를 따릅니다. RegularExpression 지원은 구현별로 다릅니다.
  • RequestRedirect는 클라이언트가 보는 내용을 변경하고 URLRewrite는 내부적으로 업스트림 요청을 변경합니다. 하나의 규칙에 호환되지 않는 리디렉션/재작성 필터를 결합하지 마세요.
  • 호스트 이름 일치, 리스너 sectionName, allowedRoutes, 참조 권한 및 성공적인 백엔드 참조 확인이 모두 맞아야 합니다.
  • 이 표준 경로 예제는 응답 상태 기반 사용자 지정 오류 페이지나 NGINX 스타일의 전역 기본 백엔드를 제공하지 않습니다. 포괄 경로는 백엔드 오류를 가로채지 않습니다.

21. 원본 작성 당시의 지원 한계 및 관리형 컨트롤 플레인 버그

영역원본의 상태 및 계획 시 영향
Istio 메시 기능이 인그레스 전용 구현에는 사이드카 주입, VirtualService, DestinationRule 또는 EnvoyFilter가 없으며 메시 추가 기능을 동시에 사용할 수 없습니다.
이그레스 관리이 Application Routing Gateway 기능에서는 지원하지 않습니다.
TLSRoute/SNI 패스스루원본 GA 기준 구성에서는 지원하지 않습니다. 향후 Istio 1.30에 대한 기대가 언급되었으나 배포 보장은 아닙니다.
쿠키 세션 선호도2026년 5월 원본: sessionPersistence는 Experimental 전용이었고 설치된 Standard v1.3.0 스키마에는 없었습니다. 업스트림 Istio 구현 이슈는 미해결 상태였습니다.
업그레이드 모델Application Routing의 부/패치 버전 업데이트는 현재 위치에서 수행합니다. 메시 추가 기능은 부 버전에 리비전 기반 카나리를 사용하고 패치는 현재 위치에서 수행합니다.

고정 세션에는 원본이 애플리케이션 수준 상태/쿠키 처리, 공유 상태 저장소 또는 의도적으로 선택한 다른 지원 아키텍처를 권장합니다. 지원되지 않는 sessionPersistence 필드를 직접 패치하는 것은 해결책이 아닙니다. 해당 CRD를 금지하는 구성에 메시의 consistentHash DestinationRule을 가져올 수는 없습니다. 향후 업스트림 구현이 이루어져도 릴리스 채택과 AKS 출시가 필요하며 제공 날짜는 제시되어 있지 않습니다.

istiod HPA의 CPU 요청 누락

원본은 관리형 istiod Deployment에 resources.requests.cpu가 없어 FailedGetResourceMetric과 FailedComputeMetricsReplicas 이벤트가 반복된다고 보고합니다. CPU 요청이라는 분모가 없으면 HPA는 사용률을 계산할 수 없어 확장하지 못하고 최소값에 머무릅니다. 이는 컨트롤 플레인 HPA이며 원본의 Gateway 데이터 플레인 HPA는 정상 동작했습니다.

kubectl get hpa -n aks-istio-system
kubectl describe hpa -n aks-istio-system "YOUR_ISTIOD_HPA_NAME"
kubectl get deploy -n aks-istio-system -l app=istiod \
  -o jsonpath='{.items[*].spec.template.spec.containers[*].resources}'

원본에 따르면 직접 패치는 추가 기능 조정자가 되돌렸으며 고객 측 우회 방법은 제공되지 않았습니다. 정확한 빌드와 증거를 첨부하여 Azure 지원 사례를 열고 관리형 수정을 추적하며 알려진 이벤트 노이즈와 새로운 장애를 구별하세요. 정상적인 데이터 플레인 확장이 무제한 컨트롤 플레인 용량을 입증하는 것은 아닙니다.

22. 마이그레이션 및 운영 승인 체크리스트

  1. CLI 버전, 리전별 출시, 관리형 Standard CRD, 충돌하는 메시가 없는지 및 Accepted 상태의 approuting-istio 클래스를 확인하세요.
  2. NGINX 기준 구성을 확립하고 병렬 Gateway를 테스트하는 동안 유지하세요. 사용 중인 고정 LB IP를 재사용하거나 DNS를 성급하게 변경하지 마세요.
  3. 모든 변환 산출물, 일치하지 않는 클래스, 정규식/재작성 동작, 제한 시간 및 지원되지 않는 기존 주석을 검토하세요.
  4. Gateway 하나가 예상한 Deployment, Service, HPA 및 PDB를 만드는지 확인하세요. 프라이빗/퍼블릭 노출과 네임스페이스 토폴로지를 의도적으로 선택하세요.
  5. 가능하면 운영자 TLS 경로를 사용하고, 그렇지 않으면 수동 CSI 마운트, 회전 및 인증서 권한 부여를 명시적으로 책임지세요. 신뢰, SNI, 만료, 회전 및 새 핸드셰이크를 테스트하세요.
  6. 외부-Gateway 및 Gateway-백엔드 경로의 NetworkPolicy, 클라이언트 IP 보존 및 443을 포함한 모든 LB 프로브/포트를 검증하세요.
  7. 경로 우선순위, 헤더, 리디렉션, 요청 크기, 장기 실행 트래픽, 오류 처리, 세션 상태 및 중단 예산을 테스트하세요.
  8. 액세스 로그를 수집하고 컨트롤 플레인 HPA 문제와 데이터 플레인 오류를 구별하세요.
  9. 이전 백엔드로 되돌릴 수 있도록 DNS 또는 전면 Application Gateway 전환을 계획하세요. 경로가 원래 Host에 의존하면 이를 보존하고 DNS 조정자 간 경합을 피하세요.
  10. 트래픽과 운영 승인이 완료된 후에만 이전 인그레스를 폐기하세요. 원본은 별도 마이그레이션 가이드를 참조하지만 조사된 리포지토리 목록에는 없습니다. 누락된 상세 전환 스크립트를 만들어 내지 않았습니다.

23. 정리 및 보존 주의 사항

활성 클러스터와 네임스페이스를 확인한 후 테스트 리소스로 확인된 대상에만 정리를 실행하세요. 인증서 인프라보다 먼저 종속 경로와 Gateway를 제거하세요. 초기 수동 정리 절차는 Deployment를 권장한 뒤 Pod를 삭제하는 오류가 있었으며 아래에는 수정한 리소스 종류를 보여줍니다.

kubectl delete -n "$APP_NS" gateway httpbin-gateway
kubectl delete -n "$APP_NS" httproute httpbin
kubectl delete -n "$APP_NS" deployment secrets-store-sync-httpbin
kubectl delete -n "$APP_NS" secretproviderclass httpbin-credential-spc
kubectl delete -n "$APP_NS" secret httpbin-credential
kubectl delete -n "$APP_NS" -f https://raw.githubusercontent.com/istio/istio/release-1.27/samples/httpbin/httpbin.yaml

# Only when no remaining Gateway workload needs the implementation:
az aks update -g "$RESOURCE_GROUP" -n "$CLUSTER" --disable-app-routing-istio
# Removing managed Gateway API CRDs affects every dependent Gateway/Route:
# az aks update -g "$RESOURCE_GROUP" -n "$CLUSTER" --disable-gateway-api

# Only for a disposable vault no longer used by any workload:
# az keyvault delete --name "$AKV_NAME" --resource-group "$RESOURCE_GROUP"
# az keyvault purge --name "$AKV_NAME" --location "$LOCATION"

제거 보호는 보존 기간이 끝나기 전 영구 삭제를 막습니다. 안전장치를 비활성화하거나 즉시 제거에 성공한다고 가정하지 마세요. 운영자가 만든 리소스와 UAMI/FIC/역할 할당은 무차별적으로 삭제하지 말고 남아 있는 소비 리소스를 기준으로 검토해야 합니다. 운영자 업데이트는 완전한 ID 정리 절차를 제공하지 않습니다.
