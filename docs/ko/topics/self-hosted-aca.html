KEDA를 활용한 Azure Container Apps의 프라이빗 GitHub Actions 실행기

프라이빗 서비스 액세스, 제어된 송신 및 관리 ID 기반 App Service 배포를 지원하는 GitHub App 인증 일회성 실행기를 구축합니다.

한국어판변수화된 예제2026년 9월

한국어판은 검토·수정된 영문 게시본을 기준으로 번역했습니다. 코드, 다운로드 파일, 구조도 내부 표기와 영문 Azure Portal 캡처는 두 언어에서 동일하게 사용합니다.

환경별 관찰 결과입니다. 측정값과 미리 보기 기능의 동작은 원본 조사 환경에서 확인한 내용이며, 현재 서비스의 보장 사항이 아닙니다. 구성값은 자신의 환경에 맞게 지정해야 합니다.

이 설계가 해결하는 문제

GitHub 호스팅 실행기는 편리하지만 워크플로에 프라이빗 데이터베이스, 내부 API, 제어된 아웃바운드 경로 또는 세심하게 관리되는 도구 체인이 필요하면 한계가 생깁니다. 상시 실행되는 자체 호스팅 VM은 그중 일부를 해결하지만 유휴 컴퓨팅, 패치 및 용량 관리 부담을 더합니다. 이 가이드는 일치하는 작업이 큐에 들어오면 이벤트 기반 Azure Container Apps Jobs로 일회성 GitHub Actions 실행기를 시작합니다.

이 설계는 워크로드 프로필 기반 Container Apps 환경과 Consumption 프로필, 전용 인프라 서브넷, Azure Firewall과 사용자 정의 경로, Azure Container Registry 및 Key Vault의 프라이빗 엔드포인트, 장기 개인용 액세스 토큰 대신 GitHub App을 결합합니다. 작은 Express 애플리케이션이 구체적인 배포 대상입니다. 실행기는 관리 ID로 Azure에 인증하고 App Service ZIP 배포를 수행합니다.

이 문서는 민감한 정보를 제거한 기술적 재구성이며, 이 공개 예제를 실제로 배포했다는 주장이 아닙니다. 원문은 여러 구성 수정 후 종단 간 배포에 성공했다고 기록합니다. 초기 진행 기록, 예제 조각, README 및 보관된 제안은 서로 다른 단계를 설명합니다. 아래 지침은 그 단계들을 정리하고 수정 사항을 밝히며 원래 계정 정보와 스크린샷을 제외합니다.

일회성이란 등록된 실행기가 작업 하나를 받은 후 폐기된다는 뜻입니다. 신뢰할 수 없는 워크플로가 안전해지거나, 정확히 한 번 실행이 보장되거나, 유휴 상태의 모든 Azure 리소스가 무료가 된다는 뜻은 아닙니다. 실행 중에는 허용된 프라이빗 서비스와 관리 ID에 접근할 수 있으므로 작업을 제출할 수 있는 사람을 제한하세요.

전체 실행 및 인증 흐름

  1. 권한 있는 사용자가 워크플로를 실행합니다. GitHub는 runs-on: [self-hosted, container-app]를 사용하는 작업을 큐에 넣습니다.
  2. 관리형 KEDA GitHub 실행기 스케일러가 GitHub App 자격 증명으로 구성된 저장소를 폴링합니다. 범위와 레이블 필터를 적용하며 워크플로 실행 및 대기 작업을 열거합니다.
  3. 조건에 맞는 대기 작업이 1개 이상이면 Container Apps가 이벤트 구성과 플랫폼 제한에 따라 작업 실행을 만듭니다. 예제는 실행당 복제본 1개와 성공해야 하는 복제본 수 1개를 사용합니다.
  4. Container Apps가 프라이빗 ACR에서 실행기 이미지를 가져오고 작업 ID로 Key Vault 기반 비밀을 확인합니다. 실행기 스크립트가 도움을 줄 수 있기 전에 프라이빗 DNS와 권한 부여가 정상 동작해야 합니다.
  5. 시작 스크립트가 GitHub App 프라이빗 키로 RS256 JWT에 서명합니다. JWT를 설치 액세스 토큰으로 교환한 뒤 설치 토큰을 실행기 등록 토큰으로 교환합니다.
  6. 실행기는 사용자 지정 레이블과 --ephemeral를 사용해 저장소 또는 조직 URL에 등록합니다. 조직 범위에서는 제한된 실행기 그룹을 추가로 사용할 수 있습니다.
  7. GitHub가 조건에 맞는 작업을 할당합니다. 워크플로는 소스를 체크아웃하고 Node.js를 선택하며 잠금 파일의 종속성을 설치하고 애플리케이션 파일만 패키징한 뒤 Azure 관리 ID로 배포합니다.
  8. 실행기는 결과를 보고하고 작업 하나가 끝나면 종료합니다. 조건에 맞는 작업이 더 없으면 min-executions=0에 따라 추가 실행이 요청되지 않습니다. 일회성 스토리지가 사라지기 전에 진단 로그를 보존하세요.

프라이빗 액세스와 인터넷 송신 제어는 다름

Container Apps 환경은 VNet에 연결됩니다. 인프라 서브넷은 해당 환경 전용으로 예약되므로 VM, 다른 환경, App Service 통합은 물론 프라이빗 엔드포인트도 배치하지 마세요. 프라이빗 엔드포인트와 Azure Firewall용 서브넷을 별도로 만드세요. 최소 접두사 크기를 용량 권장값으로 간주하지 말고 플랫폼 예약량과 예상 확장 규모에 맞춰 크기를 정하세요.

워크로드 프로필 환경은 여기서 사용하는 UDR/방화벽 설계를 지원합니다. Consumption 프로필에서도 서버리스 작업을 실행할 수 있습니다. 네트워킹 기능이 다른 레거시 Consumption 전용 환경과 혼동하지 마세요. 선택한 프로필은 컴퓨팅 동작을 제어하고, VNet 연결, DNS, 경로, 네트워크 보안 규칙 및 서비스 권한 부여는 워크로드가 실제로 접근할 수 있는 프라이빗 리소스를 결정합니다.

  • 내부 환경: 인터넷에 노출된 환경 수신 엔드포인트를 피합니다. 작업에는 인바운드 HTTP 엔드포인트가 필요하지 않습니다. 내부 전용은 모든 VNet 트래픽의 일괄 차단이 아니며 강제 송신 경로를 자체적으로 생성하지도 않습니다.
  • 기본 경로: 인프라 서브넷의 0.0.0.0/0 UDR에 VirtualAppliance 다음 홉을 설정하면 일치하는 아웃바운드 트래픽이 방화벽으로 전달됩니다. 더 구체적인 시스템, 피어링, 게이트웨이 또는 사용자 경로가 우선할 수 있습니다.
  • 프라이빗 엔드포인트: DNS가 올바르게 확인되면 ACR 및 Key Vault 데이터 평면 액세스는 프라이빗 IP를 사용합니다. 연결된 프라이빗 DNS 영역을 클라이언트 VNet에 연결하거나 전달해야 합니다.
  • 프라이빗 데이터베이스와 API: 실제 VNet 피어링 또는 VPN/ExpressRoute 연결, 올바른 반환 경로, DNS 확인, 대상 방화벽 규칙 및 애플리케이션 자격 증명이 필요합니다. 기본 인터넷 경로는 이러한 연결을 제공하지 않습니다.
  • SCM 배포: App Service 공용 사이트에 접근할 수 있다고 실행기가 SCM/Kudu 엔드포인트에 접근할 수 있다는 증거는 아닙니다. 적절한 DNS를 구성한 App Service 프라이빗 엔드포인트는 앱과 SCM에 대한 인바운드 액세스를 제공합니다. 반면 App Service VNet 통합은 웹앱의 아웃바운드 연결에 관한 기능입니다.

검사되는 프라이빗 네트워크 경로에는 필요한 경우 방화벽으로 향하는 더 구체적인 경로를 추가하고, 필요한 대상 접두사와 포트만 허용하며 대칭 라우팅을 보장하세요. 직접 피어링에는 피어링으로 생성된 시스템 경로를 사용하세요. VNetPeering은 사용자 정의 경로의 다음 홉 유형이 아닙니다. 게이트웨이 경로는 호환되는 게이트웨이 경로가 실제로 있을 때만 적합합니다. 필수 검사 경계를 우회하려고 다음 홉을 만들어 내지 마세요.

필수 조건과 변수 규약

Azure CLI, Container Apps 명령 집합, Bash 및 jq를 갖춘 승인된 Azure 관리 세션을 사용하세요. 리소스 프로비저닝과 RBAC 역할 할당 권한은 다릅니다. 일반적으로 Contributor만으로 역할 할당을 만들 수 없습니다. 적절한 범위의 역할 관리자가 할당하도록 하세요. 구독 정책에 따라 Microsoft.App, Microsoft.OperationalInsights, Microsoft.Network, Microsoft.ContainerRegistry, Microsoft.KeyVault 및 Microsoft.Web 등 필수 리소스 공급자를 등록하세요. 변경 실행 전에 CLI 도움말과 지역별 서비스 제공 여부를 확인하세요.

GitHub App 생성 및 설치, 대상 저장소 또는 조직 실행기 관리, 보호된 배포 환경 생성, 네트워크 연결된 관리/빌드 호스트 접근 권한도 필요합니다. 일반 Cloud Shell 액세스가 자동으로 프라이빗 엔드포인트 접근을 제공하지는 않습니다. 프라이빗 키는 자격 증명 모음의 네트워크 정책을 일시적으로 무력화하는 방식이 아니라 승인된 프라이빗 연결 클라이언트에서 가져와야 합니다.

아래 명령은 모두 검토된 배포 환경을 위한 Bash 예제입니다. 이 문서를 위해 실행하지 않았습니다. 승인된 환경 구성을 통해 이름과 ID를 입력하세요. 구독, 테넌트, 애플리케이션, 보안 주체, 설치 또는 소유자의 실제 식별자가 입력된 예제는 없습니다.

변수의미
SUBSCRIPTION_ID, AZURE_TENANT_ID, LOCATION명시적인 대상 구독, 예상 테넌트 및 지원되는 Azure 지역.
RESOURCE_GROUP, VNET_NAME, INFRA_SUBNET, PE_SUBNET실행기 인프라 그룹, VNet, Container Apps 전용 서브넷 및 프라이빗 엔드포인트 서브넷.
FW_NAME, FW_PUBLIC_IP_NAME, ROUTE_TABLE_NAME방화벽 리소스와 인프라 서브넷의 경로 테이블. AzureFirewallSubnet은 플랫폼에서 요구하는 서브넷 이름입니다.
ACR_NAME, KV_NAME, CAE_NAME, JOB_NAME필요에 따라 전역 고유한 레지스트리/자격 증명 모음 이름, 환경 이름 및 작업 이름.
ACR_PE_NAME, KV_PE_NAME프라이빗 엔드포인트 이름이며 호스트 이름이나 자격 증명이 아닙니다.
IMAGE_NAME, IMAGE_TAG, RUNNER_VERSION, RUNNER_SHA256검토된 이미지 위치 정보와 공식 Linux x64 실행기 릴리스/체크섬.
GITHUB_APP_ID, GITHUB_APP_INSTALLATION_ID, GITHUB_OWNER, GITHUB_REPO기본 구성에서 사용하는 App 메타데이터 및 저장소 범위.
PRIVATE_KEY_FILE, SECRET_WRITER_OBJECT_ID안전한 로컬 PEM 경로와 가져오기 권한을 가진 개체 ID. 둘 다 이미지 컨텍스트에 포함하면 안 됩니다.
AZURE_RESOURCE_GROUP, AZURE_WEBAPP_NAME, APP_PLAN_NAME대상 애플리케이션 그룹, 웹앱 및 Linux App Service 요금제.
LOG_WORKSPACE_NAME, STORAGE_SERVICE_TAG진단 작업 영역과 문서화된 지역별 Storage 서비스 태그. 예를 들면 선택한 지역에 해당하는 유효한 태그입니다.
set +x
set -euo pipefail
for name in SUBSCRIPTION_ID AZURE_TENANT_ID LOCATION RESOURCE_GROUP VNET_NAME \
  INFRA_SUBNET PE_SUBNET FW_NAME FW_PUBLIC_IP_NAME ROUTE_TABLE_NAME \
  ACR_NAME KV_NAME CAE_NAME JOB_NAME ACR_PE_NAME KV_PE_NAME \
  IMAGE_NAME IMAGE_TAG RUNNER_VERSION RUNNER_SHA256 \
  GITHUB_APP_ID GITHUB_APP_INSTALLATION_ID GITHUB_OWNER GITHUB_REPO \
  PRIVATE_KEY_FILE SECRET_WRITER_OBJECT_ID AZURE_RESOURCE_GROUP \
  AZURE_WEBAPP_NAME APP_PLAN_NAME LOG_WORKSPACE_NAME STORAGE_SERVICE_TAG; do
  test -n "${!name:-}" || { printf 'Set %s before continuing.\n' "$name" >&2; exit 1; }
done

App ID와 설치 ID는 프라이빗 키가 아닌 메타데이터이며, 자격 증명 모음에 저장하는 것은 조직의 편의를 위한 선택 사항입니다. 스케일러에는 여전히 이 ID가 메타데이터로 전달됩니다. PEM은 유효한 여러 줄 형식을 유지해야 합니다. CLI의 --value, 셸 기록, 워크플로 또는 이미지 빌드 인수에 붙여 넣지 마세요.

원문에서는 임시 VM이나 기타 네트워크 연결 컴퓨팅에서 Private Link로 비밀을 가져왔습니다. 이 패턴을 사용한다면 Container Apps 인프라 서브넷 밖에 배치하고 임시 가져오기 권한만 부여한 뒤 가져오기를 확인하면 임시 역할/리소스를 제거하세요. 실행기 ID를 영구 Secrets Officer로 사용하지 말고 필요한 비밀에 읽기 전용으로 유지하세요. 자격 증명 모음의 복구, 순환 및 액세스 검토 정책을 적용하세요.

원문의 후속 실패는 Key Vault 프라이빗 엔드포인트와 프라이빗 DNS 영역이 완전히 누락된 데서 비롯되었습니다. VNet과 같은 리소스 그룹에 있는 자격 증명 모음이라고 자동으로 프라이빗 접근이 가능하지는 않습니다. 비밀 내용이나 RBAC를 진단하기 전에 실제 클라이언트에서 일반 ${KV_NAME}.vault.azure.net 호스트 이름을 확인하고 예상한 프라이빗 경로인지 검증하세요.

실행기 이미지와 보안을 강화한 시작 스크립트 준비

다운로드에는 루트가 아닌 사용자로 실행하는 완전한 Ubuntu 실행기 Dockerfile과 start.sh가 있습니다. 이미지는 curl, Git, jq, OpenSSL, zip/unzip, 실행기 런타임 종속성 및 Azure CLI를 제공합니다. 애플리케이션 자체는 이 이미지에 포함되지 않습니다. GitHub가 매 작업마다 체크아웃하고 App Service가 생성된 Node 애플리케이션을 호스팅합니다.

제공된 로컬 소스 스냅샷의 Dockerfile에는 이미 Azure CLI와 zip이 들어 있습니다. 더 오래된 보관 상태의 미병합 제안은 대신 워크플로 내부에서 sudo를 이용한 조건부 설치를 추가했습니다. 그 제안이 병합되었다고 간주하지 않습니다. 실행기가 비권한 사용자로 동작하고 배포가 sudo 제공 여부에 의존해서는 안 되므로, 여기서는 신뢰할 수 있는 이미지 빌드 중 필수 도구를 설치하는 것이 적절합니다.

JWT 및 토큰 교환 세부 사항

스크립트는 약간의 시계 오차를 허용하기 위해 60초 전의 iat 값과 540초 후의 exp 값을 만든 다음 RS256 JWT에 서명합니다. 이는 GitHub의 짧은 JWT 수명 모델을 준수합니다. POST /app/installations/{installation_id}/access_tokens를 Authorization: Bearer ${JWT}로 호출한 다음 설치 토큰으로 범위별 실행기 등록 엔드포인트를 호출합니다.

원본 스크립트는 이미 토큰 교환 인증 헤더에서 GitHub App JWT를 사용합니다. 공개 다운로드는 그 인증 흐름을 유지하면서 처리를 강화합니다. 빈 입력을 거부하고 소유자/저장소/범위 형식을 검증하며 연결 및 요청 시간을 제한하고 성공 HTTP 상태와 비어 있지 않은 토큰 필드를 확인하며 응답 본문은 출력하지 않습니다. 서명이나 토큰 오류 시 안전하게 중단하며 실행기 구성 전에 추가 검증을 수행합니다.

# This is the key authentication sequence, not the whole startup script.
INSTALL_TOKEN=$(request_token \
  "app/installations/${GITHUB_APP_INSTALLATION_ID}/access_tokens" \
  "$JWT" "Installation token")
REG_TOKEN=$(request_token "$REGISTRATION_PATH" "$INSTALL_TOKEN" \
  "Runner registration token")

./config.sh --unattended --name "runner-$(hostname)" \
  --url "$RUNNER_URL" --token "$REG_TOKEN" \
  "${GROUP_ARGS[@]}" --ephemeral --labels "$RUNNER_LABELS"
exec ./run.sh

이 발췌문만 사용하지 말고 다운로드한 전체 스크립트를 사용하세요. 실행기 그룹은 조직 범위에서만 전달됩니다. 스크립트는 기존 실행기 등록을 교체하지 않습니다. 워크플로 작업 실행 전에 프라이빗 키와 초기화 토큰을 해제하고 exec으로 불필요한 외부 셸을 피합니다. 이는 방어적 개선이지 같은 컨테이너와 관리 ID를 공유하는 코드로부터 자격 증명이 격리된다는 보장은 아닙니다.

허용 목록에 포함된 컨텍스트만 빌드

전용 이미지 빌드 디렉터리에는 Dockerfile, 시작 스크립트 및 다운로드한 빌드 컨텍스트 허용 목록을 .dockerignore로 이름을 바꾼 파일만 두세요. 프라이빗 키, 저장소 이력, 백업 압축 파일 또는 애플리케이션 비밀이 있는 디렉터리에서 빌드하지 마세요. .gitignore만으로는 Docker/ACR 빌드 컨텍스트를 제한할 수 없습니다.

공식 actions/runner 릴리스에서 지원되는 실행기 릴리스와 SHA-256을 제공하세요. 원문은 버전 2.335.1을 사용했으며 이는 과거 값이지 현재 권장값이 아닙니다. 수정된 Dockerfile은 명시적 버전을 요구하고 압축을 풀기 전에 아카이브를 검증합니다. Azure CLI 설치 관리자와 Ubuntu 기본 이미지는 여전히 외부 빌드 종속성입니다. 검토 후 관리되는 이미지 정책에 따라 버전/다이제스트를 고정하세요.

# On an approved private-connected build host with Docker and ACR push rights:
az acr login --name "$ACR_NAME"
docker build --build-arg RUNNER_VERSION="$RUNNER_VERSION" \
  --build-arg RUNNER_SHA256="$RUNNER_SHA256" \
  --tag "$ACR_LOGIN_SERVER/$IMAGE_NAME:$IMAGE_TAG" .
docker push "$ACR_LOGIN_SERVER/$IMAGE_NAME:$IMAGE_TAG"

대신 Docker 없는 ACR Tasks를 사용한다면, 제공되는 지역에서 적절히 네트워크를 구성한 전용 에이전트 풀 등 지원되는 프라이빗 연결 빌드 경로를 구성하고 레지스트리, 소스 컨텍스트, 패키지 피드 및 필수 플랫폼 엔드포인트에 접근할 수 있는지 확인하세요. 단순한 호스팅 az acr build 요청은 작업자가 프라이빗 전용 레지스트리에 접근할 수 있다는 증거가 아닙니다.

# Only after an approved compatible ACR Tasks agent pool is configured:
: "${ACR_AGENT_POOL:?Set the reviewed agent pool}"
az acr build --registry "$ACR_NAME" --agent-pool "$ACR_AGENT_POOL" \
  --image "$IMAGE_NAME:$IMAGE_TAG" --file Dockerfile \
  --build-arg RUNNER_VERSION="$RUNNER_VERSION" \
  --build-arg RUNNER_SHA256="$RUNNER_SHA256" .

원문에서는 호스팅 빌드를 위해 ACR 공용 액세스를 일시적으로 활성화하고 기본 네트워크 동작을 Deny에서 Allow로 바꾼 다음 프라이빗 전용 액세스로 되돌렸습니다. 공용 액세스 활성화만으로 Deny 규칙이 무효화되지는 않는 것도 관찰했습니다. 이는 보안에 민감한 과거의 선택이며 권장 기본값이 아닙니다. 단지 빌드를 성공시키려고 레지스트리 액세스를 넓히거나 정책을 회피하지 마세요.

Dockerfile이나 스크립트를 변경한 후에는 다시 빌드하여 새로운 불변 태그 또는 승인된 다이제스트를 푸시하고 작업 이미지를 업데이트하세요. 로컬 Dockerfile을 편집해도 실행 중인 컨테이너는 바뀌지 않습니다. 오래된 이미지는 특히 az: command not found 문제에서 원문의 중요한 교훈이었습니다. 이 실행기에는 Docker 데몬이 없습니다. 이미지 빌드 호스트는 별도 구성 요소이며 Container Apps Jobs 안에서 임의의 Docker 빌드가 작동한다고 약속하는 것이 아닙니다.

이벤트 폴링 활성화 전에 작업 ID 생성

원문에서는 새 시스템 할당 ID로 프라이빗 ACR을 참조하는 이벤트 작업을 먼저 만들려고 했습니다. ID에 AcrPull이 생기기 전의 이미지 가져오기 검증, 그리고 ScaleRules가 없어 후속 업데이트를 받아들이지 않는 이벤트 작업이라는 두 초기화 문제를 만났습니다. 역할을 부여하고 이미지를 업데이트하며 비밀/인증 참조보다 먼저 확장 메타데이터를 추가하여 복구했습니다.

공개 예제는 더 명확한 단계적 방식을 사용합니다. 무해한 Microsoft 샘플 이미지로 Manual 작업을 만들고 시스템 ID를 얻은 뒤 범위가 지정된 액세스를 부여합니다. 그다음 프라이빗 이미지, 비밀 및 완전한 이벤트 규칙을 구성한 후 Event로 전환합니다. 초기화용 작업을 시작하지 마세요. 샘플 이미지는 ID 생성에만 사용하므로 정책상 필요하다면 검토하거나 승인된 초기화 이미지로 바꾸세요. 미리 권한을 부여한 사용자 할당 ID도 설계 대안이지만 레지스트리, 비밀 참조 및 로그인도 그에 맞춰 변경해야 합니다.

az containerapp job create --name "$JOB_NAME" --resource-group "$RESOURCE_GROUP" \
  --environment "$CAE_NAME" --trigger-type Manual \
  --workload-profile-name Consumption --mi-system-assigned \
  --replica-timeout 1800 --replica-retry-limit 1 \
  --replica-completion-count 1 --parallelism 1 --cpu 0.5 --memory 1Gi \
  --image mcr.microsoft.com/k8se/quickstart-jobs:latest

JOB_ID=$(az containerapp job show --name "$JOB_NAME" --resource-group "$RESOURCE_GROUP" \
  --query id -o tsv)
JOB_PRINCIPAL_ID=$(az containerapp job show --name "$JOB_NAME" \

test -n "$JOB_PRINCIPAL_ID"

az role assignment create --assignee-object-id "$JOB_PRINCIPAL_ID" \
  --assignee-principal-type ServicePrincipal --role AcrPull --scope "$ACR_ID" -o none
az role assignment create --assignee-object-id "$JOB_PRINCIPAL_ID" \
  --assignee-principal-type ServicePrincipal --role "Key Vault Secrets User" \
  --scope "$KV_ID" -o none

az containerapp job registry set --name "$JOB_NAME" --resource-group "$RESOURCE_GROUP" \
  --server "$ACR_LOGIN_SERVER" --identity system
az containerapp job secret set --name "$JOB_NAME" --resource-group "$RESOURCE_GROUP" \
  --secrets "runner-app-key=keyvaultref:https://$KV_NAME.vault.azure.net/secrets/runner-app-key,identityref:system"

az containerapp job update --name "$JOB_NAME" --resource-group "$RESOURCE_GROUP" \
  --image "$ACR_LOGIN_SERVER/$IMAGE_NAME:$IMAGE_TAG" \
  --set-env-vars \
  "GITHUB_APP_ID=$GITHUB_APP_ID" \

완전한 KEDA 이벤트 규칙 구성

스케일러의 소유자, 저장소 목록, 범위, App ID, 설치 ID 및 레이블은 실행기 컨테이너와 설치된 GitHub App의 설정에 맞아야 합니다. 기본 구성에서 앱 설치는 선택한 저장소에 접근할 수 있고 실행기는 해당 저장소에 등록되며 실행기와 워크플로 모두 사용자 지정 레이블 container-app을 사용합니다.

다음 JSON 생성 및 ARM 업데이트는 원문을 바탕으로 보완한 초기화 절차이며 원문 명령을 그대로 옮긴 것이 아닙니다. 이미 준비한 Manual 작업을 Event로 전환하면서 한 번의 업데이트로 완전한 이벤트 구성을 제공합니다. 포함되는 것은 ID와 비밀 참조뿐이며 PEM은 절대 포함되지 않습니다. 적용 전에 생성된 구성과 작업을 살펴보세요. 해당 API 버전과 일반 리소스 업데이트가 자신의 환경에서 지원되는지 확인하세요.

EVENT_CONFIG=$(jq -n \
  --arg owner "$GITHUB_OWNER" --arg repo "$GITHUB_REPO" \
  --arg app "$GITHUB_APP_ID" --arg installation "$GITHUB_APP_INSTALLATION_ID" \
  '{
    parallelism: 1,
    replicaCompletionCount: 1,
    scale: {
      minExecutions: 0,
      maxExecutions: 5,
      pollingInterval: 30,
      rules: [{
        name: "queued-runner-work",
        type: "github-runner",
        metadata: {
          owner: $owner,
          runnerScope: "repo",
          repos: $repo,
          labels: "container-app",
          targetWorkflowQueueLength: "1",
          applicationID: $app,
          installationID: $installation
        },
        auth: [{secretRef: "runner-app-key", triggerParameter: "appKey"}]
      }]
    }
  }')
az resource update --ids "$JOB_ID" --api-version 2024-03-01 \
  --set properties.configuration.triggerType=Event \
  "properties.configuration.eventTriggerConfig=$EVENT_CONFIG" \
  --remove properties.configuration.manualTriggerConfig --output none

이후 정상적인 기존 Event 작업을 변경할 때는 Container Apps CLI의 확장 규칙 인수로 원문과 같은 익숙한 구성을 제공할 수 있습니다.

az containerapp job update --name "$JOB_NAME" --resource-group "$RESOURCE_GROUP" \
  --min-executions 0 --max-executions 5 --polling-interval 30 \
  --scale-rule-name queued-runner-work --scale-rule-type github-runner \
  --scale-rule-metadata \
  "owner=$GITHUB_OWNER" "runnerScope=repo" "repos=$GITHUB_REPO" \

속도 제한과 저장소 필터링

GitHub App 설치의 속도 제한은 설치 및 계정 상황에 따라 달라지며 언제나 시간당 15,000 요청인 것은 아닙니다. 실제 속도 제한 응답 헤더와 GitHub 문서를 확인하세요. KEDA는 저장소와 대기 실행마다 여러 요청을 보낼 수 있으므로 폴링 빈도가 적당해 보여도 저장소가 많으면 비용이 커질 수 있습니다. 불필요한 조직 전체 검색을 피하고 동등한 스케일러의 시점을 분산하거나 통합하며 폴링을 조정하고, 관리형 스케일러 버전이 지원하는 경우에만 조건부 요청 옵션을 사용하세요.

간단한 계획 추정치는 시간당 폴링 주기 수에 주기당 저장소/실행/작업 열거 요청 수를 곱하고 등록 및 기타 API 트래픽을 더한 값입니다. 이는 추정이며 원문 측정값이 아닙니다. 큐 감지가 실패할 때 폴링 속도를 높이기보다 기본 및 보조 속도 제한 응답과 백오프 동작을 관찰하세요.

App Service와 배포 경로 준비

원문은 최종적으로 README의 오래된 게시 프로필 비밀이 아니라 작업의 시스템 할당 ID로 배포했습니다. 이 예제는 원문의 후속 대상과 일치하도록 Linux App Service 요금제와 Node 22를 사용합니다. 환경에 맞는 지원 SKU/런타임을 선택하세요. 아래 B1은 원문의 소규모 데모 계층을 유지한 것이며 프로덕션 용량 권장값이 아닙니다.

az group create --name "$AZURE_RESOURCE_GROUP" --location "$LOCATION" -o none
az appservice plan create --resource-group "$AZURE_RESOURCE_GROUP" \
  --name "$APP_PLAN_NAME" --location "$LOCATION" --is-linux --sku B1
az webapp create --resource-group "$AZURE_RESOURCE_GROUP" \
  --plan "$APP_PLAN_NAME" --name "$AZURE_WEBAPP_NAME" --runtime "NODE:22-lts"
az webapp config set --resource-group "$AZURE_RESOURCE_GROUP" \
  --name "$AZURE_WEBAPP_NAME" --startup-file "npm start"

# The supplied workflow uploads node_modules built on Linux.
az webapp config appsettings set --resource-group "$AZURE_RESOURCE_GROUP" \
  --name "$AZURE_WEBAPP_NAME" --settings SCM_DO_BUILD_DURING_DEPLOYMENT=false -o none

WEBAPP_ID=$(az webapp show --resource-group "$AZURE_RESOURCE_GROUP" \
  --name "$AZURE_WEBAPP_NAME" --query id -o tsv)

일관된 패키지 전략은 두 가지입니다. 이 다운로드는 Linux 실행기에서 npm ci를 수행하고 node_modules를 포함하므로 원격 빌드를 비활성화합니다. 원문의 초기 로컬 ZIP 배포는 서버 측 빌드를 위해 SCM_DO_BUILD_DURING_DEPLOYMENT=true를 활성화했습니다. 그 대안을 선택한다면 미리 빌드한 종속성 없이 소스/매니페스트를 업로드하고 App Service 빌드 환경에서 패키지 피드에 접근하도록 허용하세요. 두 전략을 실수로 혼합하지 마세요. 네이티브 종속성은 이 작은 Express 예제보다 더 주의 깊게 Node/OS/런타임을 맞춰야 합니다.

선택 사항: App Service 프라이빗 엔드포인트

실행기 환경이 내부라고 대상 App Service까지 프라이빗이 되는 것은 아닙니다. 프라이빗 전용 대상이 필요하다면 적절한 서브넷에 승인된 App Service 프라이빗 엔드포인트를 만들고 privatelink.azurewebsites.net을 연결하며 앱과 SCM 레코드를 모두 확인하세요. 다음 내용은 원문의 SCM 연결 논의를 확장한 구성 예제이며 원문에서 프라이빗 대상을 사용했다는 주장이 아닙니다.

: "${WEBAPP_PE_NAME:?Set the target private endpoint name}"
az network private-dns zone create --resource-group "$RESOURCE_GROUP" \
  --name privatelink.azurewebsites.net
az network private-dns link vnet create --resource-group "$RESOURCE_GROUP" \

  --virtual-network "$VNET_NAME" --registration-enabled false
az network private-endpoint create --resource-group "$RESOURCE_GROUP" \
  --name "$WEBAPP_PE_NAME" --vnet-name "$VNET_NAME" --subnet "$PE_SUBNET" \

  --endpoint-name "$WEBAPP_PE_NAME" --name app-dns \

# After verifying private app and SCM access from authorized clients:

애플리케이션 및 배포 워크플로 설치

다운로드를 두 개의 별도 컨텍스트로 사용하세요. 실행기 이미지에는 Dockerfile, start.sh 및 이름을 바꾼 .dockerignore를 사용합니다. 실행 저장소 루트에는 server.js, package.json 및 package-lock.json을 두고 gitignore.txt를 .gitignore로 이름 변경합니다. 통제를 구성한 승인된 실행 저장소에서만 deploy.yml을 .github/workflows/deploy.yml로 복사하세요. 이 사이트의 다운로드 파일이 워크플로를 자동 실행하지는 않습니다.

샘플 애플리케이션은 App Service의 PORT 또는 로컬 포트 8080에서 수신합니다. GET /는 민감한 정보를 제거한 데모 JSON 응답을 반환하고 GET /health는 OK를 반환합니다. 타임스탬프는 요청 시점에 생성되며 배포 시각이 아닙니다. 원문의 호스트 이름 필드는 공개 예제에서 제거했습니다.

# Run from the sample application root, not the runner-image directory.
npm ci --omit=dev --ignore-scripts
npm start
# In another local terminal:
curl --fail http://localhost:8080/health

Express 종속성 범위, 잠금 파일 버전/무결성 값, 엔진 제약 및 원문 테스트 명령은 보존했습니다. 루트 패키지 이름은 일반화했고 종속성 후원 링크는 제외했습니다. npm test는 no tests yet만 출력하고 성공 종료합니다. 기능, 통합 또는 보안 테스트가 아닙니다. 이 문서를 읽기만 할 때 종속성 설치나 배포는 필요하지 않습니다.

필수 GitHub 구성

  • Actions 변수 AZURE_SUBSCRIPTION_ID, AZURE_TENANT_ID, AZURE_RESOURCE_GROUP 및 AZURE_WEBAPP_NAME를 설정하세요. 저장소에서 구성하기 전까지는 의도적으로 비어 있습니다.
  • 워크플로를 활성화하기 전에 GitHub 환경 deployment을 만드세요. 요금제와 정책에 맞춰 허용 배포 브랜치와 필수 검토자를 구성하세요. 환경 이름만 지정하는 것은 보호 규칙이 아닙니다.
  • 실행기 그룹/저장소 권한과 사용자 지정 레이블이 의도한 워크로드만 허용하는지 확인하세요.
  • 업데이트 정책에 따라 작업 커밋 SHA를 검토하고 고정하세요. 예제는 가독성을 위해 원문의 작업 주 버전을 유지하고, 후속 App Service 대상과 맞추기 위해 선택한 Node 버전을 22로 변경합니다.

수정된 워크플로는 수동 전용입니다. 원문은 main 푸시에도 실행되었지만 브랜치 보호 및 배포 승인 규칙을 마련한 후에만 그 트리거를 추가하세요. 내부 서비스에 접근하거나 Azure ID로 배포할 수 있는 실행기에 pull_request_target 또는 신뢰할 수 없는 포크 워크플로를 추가하지 마세요.

패키징과 관리 ID

원본 배포 단계는 .git만 제외하고 저장소 거의 전체를 ZIP으로 묶었습니다. 공개 예제는 대신 애플리케이션 진입점, 두 패키지 매니페스트 및 새로 설치한 프로덕션 종속성이라는 명시적 허용 목록만 패키징하고 키와 환경 파일을 추가로 제외합니다. 실행기 시작 스크립트, 이미지 소스, 워크플로, 백업 또는 프라이빗 키는 포함하지 않습니다. 오래된 ZIP에 파일을 덧붙이지 말고 아카이브를 새로 깨끗하게 만드세요.

rm -f deployment.zip
zip -q -r -y deployment.zip server.js package.json package-lock.json node_modules \
  -x '*/.git/*' '*/.env' '*/.env.*' '*.pem' '*.key' '*.pfx' '*.p12'

az login --identity --output none
az account set --subscription "$AZURE_SUBSCRIPTION_ID"
actual_tenant=$(az account show --query tenantId --output tsv)
test "${actual_tenant,,}" = "${AZURE_TENANT_ID,,}"
az webapp deploy --subscription "$AZURE_SUBSCRIPTION_ID" \
  --resource-group "$AZURE_RESOURCE_GROUP" --name "$AZURE_WEBAPP_NAME" \
  --src-path deployment.zip --type zip --output none

전체 워크플로는 변수/도구를 검증하고 체크아웃 자격 증명을 남기지 않으며 워크플로 토큰을 contents 읽기로 제한하고 배포를 직렬화하며 워크플로 시간 제한을 설정하고 이후 Azure CLI 계정 캐시를 지웁니다. 작업 실행 중에는 Azure 관리 ID를 계속 사용할 수 있습니다. az account clear는 ID 해지가 아닙니다. 구독 선택과 테넌트 검증은 CLI 기본 구독으로 무심코 배포하는 일을 방지합니다. 게시 프로필이나 저장된 Azure 클라이언트 비밀은 필요하지 않습니다.

기존 게시 프로필은 원문에서 폐기한 인증 방식에 속합니다. 마이그레이션을 마치고 승인된 롤백 계획을 마련한 후 사용하지 않는 GitHub 비밀을 제거하고 적절하게 실제 자격 증명을 순환하거나 해지하세요. GitHub 비밀을 제거하는 것만으로 이전에 노출된 자격 증명이 해지되지는 않습니다.

확장 전에 실행 1회 검증

  1. 먼저 승인된 네트워크 경로에서 대상 애플리케이션을 독립적으로 검증하세요. 로컬 ZIP 배포는 대상 배포 경로만 증명하며 KEDA 감지나 실행기 실행을 증명하지 않습니다.
  2. 동일한 runs-on 레이블을 사용하는 작은 신뢰 가능한 워크플로를 실행하세요. GitHub의 Queued 상태를 관찰한 다음 Container Apps 실행 목록을 확인하세요.
  3. 실행이 시작되어 예상 이미지를 가져오고 비밀을 얻으며 올바른 범위에 실행기를 등록하고 의도한 작업을 받는지 확인하세요.
  4. 제공된 배포 워크플로를 실행하세요. Node 설정, 잠금 종속성 설치, 테스트 스텁임을 명시적으로 인지한 단계, ID 로그인 및 ZIP 배포를 별도로 확인하세요.
  5. 대상 엔드포인트에 접근 권한이 있는 클라이언트에서 앱과 상태 확인 경로를 검증하세요. 실제 애플리케이션에서 배포된 리비전을 증명해야 한다면 명시적인 버전 표시를 사용하세요. 요청 타임스탬프만으로는 충분하지 않습니다.
  6. 실행기가 종료되고 두 번째 작업을 받지 않는지 확인하세요. 강제 종료 후 일회성 리소스 정리가 항상 성공한다고 가정하지 말고 오래된 등록과 실패/취소된 실행을 점검하세요.

  contents: read

확장 전에 신뢰 수준 분리

자체 호스팅 배포 실행기는 권한 있는 코드 실행 환경입니다. 저장소 쓰기 권한자, 변경 가능한 작업, 종속성 수명 주기 스크립트 및 워크플로 변경이 내부에서 실행되는 코드에 영향을 줄 수 있습니다. 관리 ID는 웹앱과 허가된 자격 증명 모음 비밀에 접근할 수 있고 VNet은 내부 서비스를 노출할 수 있습니다. 일회성 컴퓨팅은 작업 간 지속성을 줄이지만 실행 중의 권한을 제거하지는 않습니다.

  • 배포 저장소/워크플로는 신뢰할 수 있고 검토된 상태로 유지하세요. 프로덕션 네트워크 액세스나 ID를 보유한 실행기에서 신뢰할 수 없는 끌어오기 요청을 실행하지 마세요.
  • 실질적으로 다른 신뢰 수준에는 작업, ID, GitHub App 설치, 실행기 그룹 및 네트워크 세그먼트를 분리하세요. 레이블은 작업을 라우팅할 뿐 권한 부여 경계가 아닙니다.
  • App 설치를 필요한 저장소로 제한하고 Azure 역할은 실용적으로 가능한 최소 범위에 부여하세요. 비밀 읽기와 배포에 하나의 ID를 공유하는 것이 위험 모델에 맞는지 검토하세요.
  • 이전 키와 새 키의 공존 계획에 따라 GitHub App 키를 순환하고 적절하게 Key Vault 참조나 버전을 업데이트하며 새 실행과 스케일러 인증을 확인한 뒤 이전 키를 해지하세요. 모든 구성 요소가 버전 없는 참조를 즉시 새로 고친다고 가정하지 마세요.
  • 보호된 진단을 전달하고 실패 후 실행기 정리를 검토하며 전체 환경, 비밀, JWT, 설치 토큰, 등록 토큰 또는 게시 프로필을 로그에 남기지 마세요.
