Azure의 Codex: Foundry 설정, APIM 라우팅, 스트리밍 실패와 용량 설계

Azure 호스팅 Codex의 ID, 부하 분산, 스트리밍 도중 429 동작, PTU/PAYG 용량 산정을 포함한 구현 및 테스트 통합 기록입니다.

한국어판변수화된 예제2026년 9월

한국어판은 검토·수정된 영문 게시본을 기준으로 번역했습니다. 코드, 다운로드 파일, 구조도 내부 표기와 영문 Azure Portal 캡처는 두 언어에서 동일하게 사용합니다.

환경별 관찰 결과입니다. 측정값과 미리 보기 기능의 동작은 원본 조사 환경에서 확인한 내용이며, 현재 서비스의 보장 사항이 아닙니다. 구성값은 자신의 환경에 맞게 지정해야 합니다.

범위, 날짜 및 이 가이드 읽는 방법

이 문서는 게이트웨이 선택지 비교, Foundry/Codex 직접 연결 설정, API Management 부하 분산 구현, 용량 설계 메모, 2026년 6월 26일의 스트리밍 도중 속도 제한 실험이라는 다섯 엔지니어링 문서를 통합합니다. 설정 기록은 2026년 6월의 모델 가용성과 Codex CLI 0.142.2를 기준으로 합니다. 용량 메모는 계획 분석이며 완료된 프로덕션 도입 사례가 아닙니다.

아래의 성공 관찰, 가용성 목록, 가격, 재시도 기본값, 설계 가정은 해당 기록에 속합니다. 무제한 토큰, 보편적인 스트리밍 동작, 현재의 SKU 지원, 보장된 가용성을 약속하지 않습니다. 배포 전에 모델 가용성, 서비스 문서, 조직 정책, 할당량을 다시 확인하세요. 명령은 권한이 있는 환경을 위한 참고 예시이며, 이 문서 작성을 위해 클라우드 리소스를 생성하거나 변경하도록 실행한 명령은 없습니다.

실제 구독, 보안 주체, 계정, 리소스, 게시자, 엔드포인트, 개인 경로 식별자는 모두 제거했습니다. Bash 예시에는 Azure CLI, Node.js/npm, Python 3, curl 및 아래에서 사용하는 표준 텍스트 유틸리티가 설치된 Bash 호환 셸이 필요합니다. PowerShell 문법이 아닙니다. 따옴표 안의 YOUR_ 값을 자신에게 권한이 있는 값으로 교체하고, 공개되는 구성에 자격 증명을 붙여 넣지 마세요.

선택 가이드

  • 개발자 한 명이나 개념 증명에서는 게이트웨이가 필요한 제어 기능을 더하지 않는다면 직접 연결하세요.
  • 많은 개발자나 팀에 사용량 귀속, 예산, 할당량, 중앙 집중식 내부 거버넌스가 필요할 때 메모는 LiteLLM을 선호합니다.
  • 게이트웨이 홉 없이 동일 모델의 단순 PTU/PAYG 초과분 처리가 필요하다면 네이티브 스필오버를 검토하세요.
  • Azure 측 관찰 가능성, 거버넌스, 클라이언트 자격 증명과 모델 인증의 분리가 필요하면 APIM을 사용하세요.
  • 각 모델 리소스 안에서는 네이티브 스필오버를 사용하고 상위에서 LiteLLM이 팀, 모델, 리전, 사용량 귀속을 담당하도록 조합할 수 있습니다.

개요는 요청 수락 시점의 PTU 스필오버가 소진된 프로비저닝 용량에서 스트림을 시작하는 일을 피할 수 있다고 설명합니다. 이는 설계 근거이며 아래 GlobalStandard 실험의 결과가 아닙니다. 모든 스트리밍 도중 실패 방지, PAYG의 상시 용량 확보, 임의의 PTU/PAYG 조합 지원을 입증하지는 않습니다. 마찬가지로 LiteLLM의 SSE 본문 오류 탐지도 검증 제안일 뿐 시연되지 않았습니다.

설계 기록의 네트워킹 및 가격 참고

기록은 Standard v2/Premium v2의 인바운드 프라이빗 엔드포인트, Premium v2의 VNet 주입과 가용 영역, 당시 v2의 기본 다중 리전 배포 부재를 나열합니다. 이 가정에서는 리전 HA를 위해 별도 글로벌 부하 분산 아키텍처가 필요합니다. 재검증해야 하는 과거 SKU 설명입니다. 예시 Premium v2 추정치는 1단위 약 월 USD 2,801, 2단위 HA 구성 약 월 USD 4,200이며 현재 견적이 아닙니다. 리전, 단위 수, 적용 요금은 Azure 가격 계산기에서 확인하세요. 비교 기준은 동일한 기저 모델 사용량이며 PTU 약정, PAYG 사용량, 운영, 네트워킹에 따라 실제 청구액이 달라질 수 있습니다.

Foundry 직접 연결 설정: 환경과 배포

검증된 직접 경로는 East US의 AIServices 계정, gpt-5.3-codex 버전 2026-02-24의 GlobalStandard 배포 2개, 각각 50K TPM 할당, Entra RBAC, Codex CLI 0.142.2를 사용했습니다. 이 가이드에서는 배포를 A와 B로 부르며 별칭은 환경 변수로 제공합니다.

export SUB='YOUR_SUBSCRIPTION_ID'
export RG='YOUR_RESOURCE_GROUP'
export LOC='eastus'
export ACC='YOUR_FOUNDRY_ACCOUNT'
export DEPLOYMENT_A='YOUR_CODEX_DEPLOYMENT_A'
export DEPLOYMENT_B='YOUR_CODEX_DEPLOYMENT_B'
az login
az account set --subscription "$SUB"

# Inspect regional availability before choosing a version and SKU.
az cognitiveservices model list --location "$LOC" \
  --query "[?contains(model.name, 'codex')].{name:model.name, version:model.version, sku:model.skus[0].name}" \
  -o table

az group create -n "$RG" -l "$LOC" -o table
az cognitiveservices account create \
  --name "$ACC" --resource-group "$RG" --location "$LOC" \
  --kind AIServices --sku S0 --custom-domain "$ACC" --yes -o table

for DEPLOYMENT in "$DEPLOYMENT_A" "$DEPLOYMENT_B"; do
  az cognitiveservices account deployment create \
    --resource-group "$RG" --name "$ACC" \
    --deployment-name "$DEPLOYMENT" \
    --model-name gpt-5.3-codex --model-version 2026-02-24 --model-format OpenAI \
    --sku-name GlobalStandard --sku-capacity 50 -o table
done

az cognitiveservices account deployment list -g "$RG" -n "$ACC" \
  --query "[].{name:name, model:properties.model.name, ver:properties.model.version, sku:sku.name, cap:sku.capacity}" \
  -o table

6월 목록의 Codex 제품군에는 gpt-5-codex(2025-09-15), gpt-5.1-codex, gpt-5.1-codex-mini, gpt-5.2-codex, gpt-5.3-codex(2026-02-24)가 포함되었고 GlobalStandard가 표시되었습니다. 예시 쿼리는 첫 SKU 항목을 추출할 뿐 유일하게 지원되는 SKU임을 증명하지 않습니다. 계정 생성에서는 토큰 인증과 계정의 OpenAI 엔드포인트 동작을 위해 --custom-domain을 사용했습니다.

원래 설정은 --sku-capacity 10으로 시작했지만 CLI 한 턴조차 속도 제한에 걸렸습니다. 할당을 50으로 늘리자 해당 테스트에서 한 턴이 성공했습니다. 이 모델/SKU에서 그 값은 각각 10K와 50K TPM을 의미했습니다. 실험에서는 동일 배포 이름으로 deployment create를 다시 실행하면 용량이 업데이트되었지만, 시도한 deployment update --sku-capacity는 해당 환경에서 변경을 반영하지 않았습니다. 모든 CLI 버전이 같다고 가정하지 말고 용량 변경 후 항상 배포를 다시 조회하세요.

로컬 키가 비활성화된 경우의 Entra 인증

테스트한 구독은 Azure Policy로 disableLocalAuth=true를 강제했습니다. 키 목록 요청은 BadRequest: Failed to list key. disableLocalAuth is set to be true로 실패했습니다. 리소스를 false로 업데이트하려던 시도는 정책에 의해 true로 되돌아갔습니다. 이는 문제 해결 관찰이며 조직 정책을 약화하거나 우회하라는 권고가 아닙니다. 로컬 인증 비활성화를 키 자료 자체가 없다는 증거와 혼동해서는 안 됩니다. 핵심 사실은 키 인증을 사용할 수 없었다는 것입니다.

az cognitiveservices account show -n "$ACC" -g "$RG" \
  --query properties.disableLocalAuth -o tsv

ACC_ID=$(az cognitiveservices account show -n "$ACC" -g "$RG" --query id -o tsv)
MY_OID=$(az ad signed-in-user show --query id -o tsv)
az role assignment create \
  --assignee-object-id "$MY_OID" --assignee-principal-type User \
  --role 'Cognitive Services OpenAI User' --scope "$ACC_ID" -o table

export ENDPOINT="https://${ACC}.cognitiveservices.azure.com"
TOKEN=$(az account get-access-token --resource https://cognitiveservices.azure.com \
  --query accessToken -o tsv)
REQUEST=$(python3 -c 'import json,os; print(json.dumps({"model":os.environ["DEPLOYMENT_A"],"input":"Say OK in one word."}))')
curl -sS -X POST "$ENDPOINT/openai/v1/responses" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "$REQUEST"
unset TOKEN

관찰된 직접 응답은 HTTP 200과 status: completed였습니다. 자동화에서는 로그인 사용자를 조회하는 대신 의도한 서비스 주체 또는 관리 ID의 개체 ID를 제공하고 --assignee-principal-type ServicePrincipal을 사용하세요. 이 구성의 데이터 평면 추론에는 Cognitive Services OpenAI User 역할이면 충분했습니다. 불필요하게 역할 할당을 넓히지 마세요.

OpenAI v1 엔드포인트는 POST /openai/v1/responses이며 요청 본문의 model 필드가 Azure 배포 별칭을 선택합니다. 이 v1 예시에는 api-version 쿼리 매개변수를 추가하지 않습니다. 위의 bearer 토큰 문법은 의도된 인증 헤더를 매개변수화해 재구성한 것입니다. 원문의 헤더 텍스트는 이미 마스킹되어 있어 실행 가능한 문법으로 그대로 복사하지 않았습니다.

명령 기반 토큰 도우미 전체 예시

이 전체 인라인 예시를 $HOME/.codex/az-codex-token.sh로 저장하세요. 기존 Azure CLI 로그인에서 Cognitive Services 액세스 토큰을 가져와 표준 출력에 토큰만 출력합니다.

#!/usr/bin/env bash
set -euo pipefail
az account get-access-token \

구현 기록에 설명된 정책 동작

  1. 인바운드에서 authentication-managed-identity resource="https://cognitiveservices.azure.com"를 사용하여 APIM의 ID로 인증합니다.
  2. Foundry 백엔드 기본 URL은 https://YOUR_FOUNDRY_ACCOUNT.cognitiveservices.azure.com처럼 호스트만 설정합니다. 작업이 /openai/v1/responses를 추가합니다. 두 위치 모두에 /openai/v1를 넣으면 경로가 중복되어 HTTP 404가 발생했습니다.
  3. 동일 모델/버전인 A와 B 중 하나를 기본 배포로 선택하고 다른 하나를 보조 배포로 둡니다.
  4. 백엔드의 retry 블록은 HTTP 상태 429를 검사하고 재시도 1회를 허용하며 first-fast-retry를 사용합니다. 각 forward-request 전에 JSON 본문의 model 필드를 선택한 배포로 다시 씁니다. 첫 시도는 기본, 재시도는 보조 배포입니다.

무작위 라우팅이 보장이 아닌 확률을 바꾸는 이유

무작위 선택을 복원하면 CLI의 각 재시도는 새로운 APIM 호출이자 새로운 백엔드 선택이 됩니다. 두 백엔드 사이에서 독립적이고 동일 확률로 선택하며, 하나의 백엔드가 계속 정상이고 총 시도가 6회라고 가정하면 정상 백엔드에 한 번 이상 도달할 확률은 다음과 같습니다.

1 - (1/2)^6 = 63/64 = 98.4375%
Probability of choosing the blocked backend all six times = 1/64 = 1.5625%

이는 수학적 시나리오이며 관찰된 98.4% 성공률 측정이나 SLA가 아닙니다. 가중 라우팅, 상관된 선택, 공유 할당량 압력, 제한과 무관한 오류, 두 백엔드 모두의 소진은 단순 가정을 무효화합니다. 하드코딩된 기본 배포 실험이 측정한 것은 6회 실패이지 무작위 정책의 장기 신뢰성이 아닙니다.

운영상의 의미와 검증되지 않은 대안

  1. 실제 용량을 먼저 해결하세요. 충분한 PTU를 프로비저닝하거나 충분한 PAYG 할당량을 확보하세요. 게이트웨이 재시도나 분산은 기저 할당량 상한을 높이지 않습니다.
  2. 실제 에이전트 요청 크기에 충분한 동일 모델/버전 용량을 확보하세요. 실습에서는 작은 턴도 전체 문맥/도구 오버헤드가 14K–18K토큰이었습니다.
  3. 가능하면 해당 요청에 실패한 것으로 알려진 백엔드를 제외하는 등 재시도 라우팅을 의도적으로 설계하세요. 기록은 sticky-avoid 또는 weighted-exclude 전략을 제안하지만 구현은 제공하지 않습니다.
  4. 실제로 HTTP 429를 반환하는 비스트리밍 요청에서는 시연한 정책이 보조 배포로 투명하게 재시도할 수 있습니다. 그래도 정상 대상과 재시도 여유가 필요합니다.
  5. 적용 가능한 HTTP/URL 기반 실패에는 추가 배포나 리전, APIM 백엔드 풀/회로 차단기를 고려하세요. 상태 기반 회로 차단기가 HTTP 200 내부의 SSE 오류 이벤트를 자동 검사하지는 않습니다.

더 큰 변경이 필요한 두 아이디어가 기록되었지만 검증되지는 않았습니다. 백엔드 요청을 stream:false로 강제하고 HTTP 429에서 장애 조치한 후 성공 응답을 Codex 호환 SSE로 다시 변환하는 방법, 또는 클라이언트 헤더를 확정하기 전에 초기 SSE 이벤트를 검사/버퍼링하여 초기 오류 시 다른 백엔드를 선택하는 방법입니다. 둘 다 지연 시간, 구현, 클라이언트 호환성 문제가 있습니다. HTTP 헤더나 응답 일부를 보낸 후에는 프로토콜을 이해하는 처리 없이 이를 소급하여 새 상태로 바꾸거나 안전하게 재생할 수 없습니다. 6월 실험은 성능상의 이유로 SSE 버퍼링을 명시적으로 제외했습니다. 이 문서가 제공하는 즉시 사용 가능한 APIM 기능이 아닙니다.

제안된 PTU/PAYG 구조

각 모델에 측정된 기본 부하용 GlobalProvisionedManaged 배포 하나와 최선형 버스트 처리용 GlobalStandard 배포 하나를 프로비저닝합니다. 세 쌍, 총 여섯 배포입니다. 각 쌍의 모델과 버전은 동일하게 유지하세요. LiteLLM은 선택한 모델에 따라 라우팅하고, 해당 모델의 호환 엔드포인트 안에서만 분산하거나 대체 경로로 전환합니다.

실제로 여유 용량을 늘리는 요소

  • 메모는 할당량 범위를 구독, 리전, 모델, 배포 SKU로 봅니다. 따라서 각 모델에 관련 풀이 따로 있습니다. 대상 서비스의 정확한 할당량 차원을 확인하세요.
  • 동일 리전/모델/SKU의 할당량을 더 많은 배포로 나누어도 총 할당량은 늘지 않습니다. 배포별 할당은 분산을 개선하고 각 배포에 할당된 몫을 격리할 수 있지만 추가 사용 권한을 만들지는 않습니다.
  • 제안된 설계에서 PTU와 PAYG는 별개의 용량/할당량 범주입니다. 각각 실제로 할당 가능하다면 둘을 함께 사용하여 하나만 사용할 때보다 여유 용량을 늘릴 수 있습니다.
  • 같은 구독/리전/모델/SKU 내 별도 계정은 주로 격리와 가용성 수단이지 공유 할당량을 배수로 늘리는 방법이 아닙니다.
  • 한 모델이 승인된 Korea Central 용량을 소진하면, 다른 지원 리전에 추가 배포하여 별도의 리전 할당량 풀을 활용할 수 있습니다. 할당량 승인, 용량 가용성, 데이터 상주 제약이 전제됩니다.

대체 가능성을 검증한 뒤에만 부서별 모델 할당

메모는 한 부서에 gpt-5.3-codex, 다른 부서에 gpt-5.5, 또 다른 부서에 gpt-5.4를 배정하고 각각 PTU/PAYG 쌍을 두는 방안을 제안합니다. LiteLLM은 인증된 부서를 기본 모델에 매핑할 수 있습니다. 이렇게 하면 에이전트 세션 도중 모델을 바꾸지 않고 모델별 할당량 풀로 수요를 분산할 수 있습니다.

이는 부서 업무가 할당된 모델의 코드 품질과 도구 루프 동작을 수용할 수 있을 때만 유효합니다. Codex 특유의 다단계 패치 안정성이 필요한 워크플로는 적합한 Codex 모델을 유지해야 합니다. 메모는 Codex CLI를 -codex 접미사가 있는 모델로 제한할 필요가 없다고 언급하며 model 설정을 통해 범용 gpt-5.4/gpt-5.5 모델을 테스트할 것을 제안합니다.

정성적 평가는 최신 범용 모델이 단발 코드 품질에서 동등하거나 더 나을 수 있는 반면, Codex 계열은 apply_patch, exec, 다단계 작업 지속성을 포함한 Codex 에이전트 하네스에 맞춰 튜닝되었다는 것이었습니다. 이 주장에 대한 비교 벤치마크는 제공되지 않았습니다. 부서별 모델 할당을 도입하기 전에 각 후보로 같은 작업을 실행하고 파일 생성 성공, 패치 성공, 지속적인 도구 사용, 출력 품질을 비교하세요. 모델 이름의 접미사를 측정된 품질 순위로 여기지 마세요.

  • 중복 명령을 통합했습니다. 실패한 로컬 인증 정책 변경 시도는 정책을 약화하는 단계로 권장하지 않고 과거 사실로 설명합니다. 이미 마스킹된 bearer 헤더는 유효한 변수 기반 문법으로 수정했습니다.
  • 무제한 용량, 보편적인 스트리밍 도중 실패 방지, 429 없음 보장, 가용성 100% 주장은 설계 가정 또는 제한된 테스트 결과로 한정했습니다. 과거의 리전별 SKU, 가격, CLI 기본값 설명은 독립적으로 재검증하지 않았습니다.
