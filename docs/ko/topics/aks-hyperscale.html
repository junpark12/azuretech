AKS Hyperscale 컨트롤 플레인: 병목에 맞춘 크기 선택과 메트릭 해석

H2/H4/H8, 독립적인 etcd 파티션, 지원되는 수명 주기 변경, schema v2 관리형 Prometheus, 그리고 10월 1일의 소규모 관측으로 입증할 수 있는 것과 없는 것을 다루는 실용적인 Preview 가이드입니다.

한국어판변수화된 예제2026-10-07

한국어판은 검토·수정된 영문 게시본을 기준으로 번역했습니다. 코드, 다운로드 파일, 구조도 내부 표기와 영문 Azure Portal 캡처는 두 언어에서 동일하게 사용합니다.

환경별 관찰 결과입니다. 측정값과 미리 보기 기능의 동작은 원본 조사 환경에서 확인한 내용이며, 현재 서비스의 보장 사항이 아닙니다. 구성값은 자신의 환경에 맞게 지정해야 합니다.

1. 컨트롤 플레인 문제부터 구분하기

AKS Hyperscale은 Kubernetes API 동시성, Pod 생성·삭제 빈도, 스케줄링 수요가 특히 높은 워크로드를 위해 컨트롤 플레인 용량을 미리 프로비저닝합니다. 워커 노드 확장 기능은 아닙니다. API 서버, 스케줄러, 컨트롤러, etcd는 원하는 상태를 관리하고, 워커 노드는 애플리케이션을 실행하는 CPU, 메모리, 네트워크, 스토리지를 제공합니다. 컨트롤 플레인을 키워도 GPU 용량이 생기거나 이미지 다운로드 오류가 해결되거나 부적합한 노드가 Pod의 배치 조건을 만족하게 되지는 않습니다.

이 글은 2026년 10월 7일에 게시한 비공식 기술 현장 노트입니다. 관측은 2026년 10월 1일의 과거 기록이며, 새 테스트, 제품 보장, 가격 정책, SLA가 아닙니다. 이 글을 위해 확인한 공개 문서에서 Hyperscale은 여전히 Preview입니다. 해당 문서는 AKS Preview를 있는 그대로, 사용 가능한 상태로 제공하며 서비스 수준 계약과 제한적 보증에서 제외하고, 최선의 노력 수준으로 지원하며, 프로덕션용으로 의도하지 않았다고 명시합니다. 의사 결정 전에 최신 약관과 지원 범위를 다시 확인하세요.

기본 AKS 컨트롤 플레인 모드는 용량을 동적으로 조정하며 대부분의 워크로드에 대한 문서상의 권장 방식입니다. 여러 배포 컨트롤러의 동시 실행, 분산 배치 작업 생성, 예측 가능한 API 활동 급증처럼 대표성 있는 근거가 컨트롤 플레인 압박을 가리킬 때 Hyperscale을 평가할 가치가 있습니다. 공개 문서가 미션 크리티컬 사용 사례를 소개하더라도 Preview의 프로덕션 사용 경고를 무효화하지는 않습니다.

크기를 선택하기 전에 세 가지를 나누어 질문하세요. API 클라이언트가 처리를 기다리는가, Pod가 스케줄링을 기다리는가, 아니면 이미 스케줄링된 Pod가 Ready 상태를 기다리는가? 각각 담당 영역이 다른 별개의 대기열입니다. 클라이언트 측 시간 초과도 기록하세요. API 서버에 도달하지 못한 요청은 서버의 요청 카운터에 나타나지 않을 수 있습니다.

2. H2, H4, H8의 용량 차원 이해하기

다음 수치는 10월 7일에 확인한 공개 크기별 특성이며 이 글에서 측정한 결과가 아닙니다. 공식 표는 동시성 열을 “Kube API Server flow control executing requests”라고 부르며, 모니터링 지침은 현재 사용량을 API Priority and Fairness(APF) 실행 seat로 표현합니다. 이 값을 애플리케이션의 초당 요청 수로 해석하면 안 됩니다.

Seat는 요청 속도가 아니라 동시성 단위

APF seat는 동시 작업의 단위입니다. 대규모 목록 조회처럼 일부 요청은 여러 seat를 차지할 수 있으며, 요청 소요 시간도 seat 점유 기간에 영향을 줍니다. 따라서 요청 속도가 같아도 점유량은 다를 수 있습니다. APF는 작업을 대기열과 동시성 제어가 있는 우선순위 수준으로 나누므로, 클러스터 전체 합계가 작아 보여도 특정 수준은 제한될 수 있습니다. 단순히 그래프를 낮추기 위해 APF 정책을 변경하지 마세요.

스케줄링은 애플리케이션 준비 완료가 아님

스케줄링은 적합한 노드를 선택하고 Pod를 바인딩합니다. 이미지 다운로드, 볼륨 연결, 컨테이너 시작, 초기화, 준비 상태 프로브는 그 이후에 수행됩니다. 스케줄러 시도 카운터에는 실패한 시도와 재시도가 포함될 수 있으므로 그 속도는 Ready가 되는 고유 Pod 수가 아닙니다. 스케줄링 불가 상태를 컨트롤 플레인 용량 탓으로 돌리기 전에 리소스 요청, taint, affinity, 스토리지 제약을 조사하세요.

공개된 크기 사이에서 동시성은 두 배가 되지만 스케줄링 수치는 200에서 300, 400으로 증가하며 단계마다 두 배가 되지는 않습니다. 현장 가이드도 이와 다른 상위 원문의 주장을 이미 지적합니다. 여기에는 측정된 속도 향상, Pod당 가격 비교, 가용성 약속이 없습니다. Standard/Premium 가격 책정 계층과 H2/H4/H8 컨트롤 플레인 크기는 별도 설정이며, 어느 것도 워커 크기 결정이나 최신 비용 검토를 대신하지 않습니다.

3. etcd 파티션 6개에는 각각 독립된 한도가 있음

Hyperscale은 리소스 범주별로 etcd를 6개의 클러스터로 분리합니다. 스토리지 수치는 파티션별 한도이며, 어떤 리소스 유형이든 자유롭게 사용하는 통합 풀이 아닙니다. H2에서 H4 또는 H8로 변경해도 공개된 파티션 수나 파티션당 스토리지는 늘어나지 않습니다.

파티션저장하는 Kubernetes 리소스운영 확인 사항
이벤트Event 객체반복 실패가 불필요한 이벤트 생성을 유발하는가?

PodPod 객체완료되었거나 더 이상 필요 없는 워크로드 객체가 쌓이는가?

기본Deployment, Service, ConfigMap 등 나머지 모든 리소스보존 중인 사용자 지정 리소스나 구성 객체가 증가하는가?

6개 파티션의 평균이 아니라 가장 많이 찬 파티션과 그 증가 추이를 추적하세요. 복제본마다 서로 다른 객체를 저장하는 것처럼 복제본 데이터베이스 크기를 더하면 안 됩니다. 반환된 파티션 및 인스턴스 라벨을 확인한 뒤 각 파티션 안에서 복제본의 최댓값을 사용하세요. 파티션 식별 정보가 없다면 라벨을 만들어 내지 말고 해당 관측 공백을 해결하세요.

공개 문서는 파티션당 2 GB 이하를 목표로 설계하고, 파티션 사용률이 50%에 접근하면 리소스 수를 검토하라고 권장합니다. 또한 본문에서는 8 GB 하드 한도라고 설명하지만 크기 표에서는 8 GiB라고 표기합니다. 이 단위 불일치는 여기서 해결하지 않습니다. 위 표는 GiB를 유지하고 권장 사항은 문서의 표현을 유지합니다. 확인 없이 이 차이를 정확한 바이트 기반 경고 임계값으로 변환하지 마세요. 더 큰 컨트롤 플레인은 스토리지 보존 전략이 아니므로, 승인된 정리 작업에 앞서 객체 수명 주기를 검토해야 합니다.

4. 마이그레이션과 크기 조정을 구분하기

공개 Hyperscale 가이드는 기존 Hyperscale 클러스터의 크기 변경을 명시적으로 설명합니다. “신규 클러스터만 가능”이라는 제한은 일반 클러스터에 프로파일을 추가하는 경우에 해당하며, 이미 있는 프로파일의 크기를 변경하는 경우가 아닙니다. 이는 현장 가이드가 지적한, H4에서 H2 또는 H8로 변경하려면 재구축해야 한다는 과거 상위 원문의 설명을 바로잡습니다.

작업2026년 10월 7일 문서 기준계획에 미치는 영향
일반 컨트롤 플레인에서 Hyperscale로 전환기존 클러스터에 프로파일 추가 불가조건을 충족하는 새 클러스터를 만들고 워크로드와 데이터 이전 계획 수립
H2, H4, H8에서 다른 Hyperscale 크기로 변경컨트롤 플레인 크기 업데이트 작업으로 지원수요와 변경 위험을 검토하고 결과 프로파일 및 관측 데이터 확인
Hyperscale에서 일반 컨트롤 플레인으로 전환생성 후 프로파일 제거 불가교체 및 이전 계획 수립. 삭제는 롤백 절차가 아님
프로비저닝 도구aks-preview를 포함한 Azure CLI, REST API, ARM 템플릿이 문서화되어 있으며 Preview 가이드에서 SDK와 Terraform은 미지원클라이언트가 속성을 전송할 수 있다는 이유만으로 지원을 추론하지 않음

다음 PowerShell은 실행하지 않은 예시입니다. 첫 번째 명령은 쓰기 작업으로, Hyperscale이 이미 활성화된 클러스터에 H4 컨트롤 플레인 크기를 요청합니다. 일반 클러스터에서 Hyperscale을 활성화하거나 워커 풀 크기를 변경하지 않으며, 중단 없는 변경을 보장하지도 않습니다. 사용 전에 자리 표시자를 바꾸고 변경 승인을 받은 뒤 현재 서비스 동작을 검토하세요. 두 번째 명령은 결과 프로파일을 읽기만 합니다.

$ResourceGroup = "REPLACE_RESOURCE_GROUP"
$ClusterName = "REPLACE_CLUSTER_NAME"
az aks update --resource-group $ResourceGroup --name $ClusterName --control-plane-scaling-size H4
az aks show --resource-group $ResourceGroup --name $ClusterName --query controlPlaneScalingProfile --output json

교체 계획에는 ID, 네트워크 종속성, 정책, 영구 데이터, 백업·복원 검증, DNS 또는 트래픽 전환, 롤백 가능 기간이 포함되어야 합니다. 구독과 지역 조합당 Hyperscale 클러스터 하나라는 Preview 제한은 병행 교체를 제약할 수 있습니다. 이 이전 방식에 의존하기 전에 할당량과 배치를 해결하세요. 자리를 확보하려고 현재 클러스터부터 삭제하면 안 됩니다.

5. 읽기 전용 검색으로 자격 조건 확인하기

10월 7일에 확인한 공개 사전 조건은 AKS Standard 또는 Premium 계층, Kubernetes 1.33.0 이상, Azure CLI 확장 aks-preview 버전 21.0.0b8 이상, 구독 기능 ControlPlaneScalingProfilePreview 등록입니다. Free 계층은 지원되지 않습니다. 프로파일은 새 클러스터를 만들 때 선택하며, Preview에서는 구독과 지역 조합당 Hyperscale 클러스터 하나가 허용됩니다. 일반 AKS 할당량과 워커 VM 할당량도 별도의 제약으로 남습니다.

다음은 읽기 전용 검색 명령의 예시이며 실행한 검증이 아닙니다. 이미 인증되어 있고 명시적으로 선택한 Azure 구독과 Kubernetes 컨텍스트를 사용하세요. 로그인, 구독 전환, 자격 증명 다운로드, 확장 설치, 기능 등록은 수행하지 않습니다. 환경별 출력은 비공개로 유지하세요.

$Location = "REPLACE_LOCATION"
$ResourceGroup = "REPLACE_RESOURCE_GROUP"
$ClusterName = "REPLACE_CLUSTER_NAME"
az version
az extension show --name aks-preview --query version --output tsv
az feature show --namespace Microsoft.ContainerService --name ControlPlaneScalingProfilePreview --query properties.state --output tsv
az provider show --namespace Microsoft.ContainerService --query registrationState --output tsv
az aks get-versions --location $Location --output table
az aks show --resource-group $ResourceGroup --name $ClusterName --query "{version:kubernetesVersion,tier:sku.tier,profile:controlPlaneScalingProfile,identityType:identity.type}" --output json
kubectl config current-context
kubectl get configmap ama-metrics-settings-configmap --namespace kube-system --output yaml

확장을 찾을 수 없다는 결과는 도구 준비가 더 필요하다는 뜻입니다. ConfigMap이 없다는 사실만으로 관리형 Prometheus가 비활성화되었다고 판단할 수는 없습니다. 버전 목록은 해당 지역에서 제공되는 Kubernetes 버전을 보여줄 뿐, Hyperscale 자격, 할당량, 보장된 용량을 입증하지 않습니다. 최신 Hyperscale 및 할당량 문서로 별도 확인하세요. 등록, 공급자 새로 고침, 확장 설치, 클러스터 생성은 모두 상태를 바꾸므로 의도적으로 승인된 설정 절차에 맡깁니다.

Azure CNI Overlay는 Pod 수가 많은 환경에 대한 공개 가이드의 권장 사항이며, 다른 모든 CNI를 배제하는 필수 조건이 아닙니다. 또한 대규모 클러스터에서는 API 부하 때문에 Azure Policy 추가 기능을 권장하지 않습니다. 이러한 사항은 아키텍처 절충으로 다루세요. 성능 권장 사항을 따른다는 이유만으로 필수 거버넌스를 제거하면 안 됩니다.

6. 그래프를 해석하기 전에 수집을 명확히 하기

Azure 플랫폼 메트릭과 관리형 Prometheus는 서로 다른 관측 수단입니다. Hyperscale 문서는 플랫폼 seat 사용량 apiserver_flowcontrol_executing_seats를 Prometheus 게이지 apiserver_flowcontrol_current_executing_seats에 대응시킵니다. 플랫폼 스케줄링은 scheduler_schedule_attempts_rate를 사용하고, Prometheus 카운터는 scheduler_schedule_attempts_total입니다. 플랫폼 메트릭 이름을 PromQL에 붙여 넣은 뒤 빈 결과를 부하 없음으로 해석하지 마세요.

관리형 컨트롤 플레인 메트릭 가이드는 관리 ID 인증과 Azure Monitor의 관리형 Prometheus 서비스를 요구하며, 이 수집 기능에서 Azure Private Link를 지원하지 않는다고 명시합니다. 자체 호스팅 Prometheus는 전체 컨트롤 플레인 복제본을 관측하기 위한 지원 대안이 아닙니다. 컨트롤 플레인 스크레이핑은 노드 측 ama-metrics 추가 기능 밖에서 실행되므로, 노드 수집기가 정상이라는 사실만으로 컨트롤 플레인 수집을 입증할 수 없습니다.

관리형 Prometheus 연결과 컨트롤 플레인 메트릭 활성화는 별도 단계입니다. 의도한 작업 영역에 이미 연결된 클러스터에서 다음 쓰기 예시는 컨트롤 플레인 수집을 활성화합니다. 관측 데이터 수집량과 비용이 증가할 수 있습니다. 이 명령은 작업 영역을 선택하거나 검증하지 않으며 여기서 실행하지 않았습니다.

az aks update --resource-group $ResourceGroup --name $ClusterName --enable-control-plane-metrics

데이터 손실을 진단하기 전에 연결된 Azure Monitor 작업 영역에 대한 접근 권한과 쿼리 권한을 확인하세요. 공개 가이드는 작업 영역 데이터를 보기 위한 역할로 Monitoring Reader 또는 Monitoring Contributor를 명시합니다. 설정 전파와 첫 샘플 수집에는 수분이 걸릴 수 있으며, 수집을 켜도 과거 데이터가 소급 생성되지는 않습니다. 활성화 이후 시간 범위에서 원시 시계열부터 확인하고, 충분한 샘플이 생긴 뒤 범위 함수를 사용하세요.

Schema v2: 덮어쓰지 말고 병합하기

10월 1일 원본은 cluster-metrics와 controlplane-metrics가 분리된 schema v2를 사용했습니다. 컨트롤 플레인 수집에서 API 서버 및 etcd 대상은 기본 활성화되지만 스케줄러는 그렇지 않습니다. 최소 수집 프로파일에는 API 요청 카운터가 포함되지만 현재 실행 seat와 APF 거절 요청은 나열되어 있지 않습니다. 모든 API 서버 메트릭을 켜는 대신 이 두 메트릭을 명시적으로 추가하세요.

이 YAML은 구성 조각이며 그대로 적용할 수 있는 완전한 매니페스트가 아닙니다. 메타데이터, 다른 대상, keep-list, 수집 간격, 클러스터 측 구성을 보존하면서 검토된 설정 ConfigMap에 병합하세요. keep-list의 두 항목은 최소 수집을 확장하며, 이 조각은 스케줄러 수집을 켜지 않습니다. 기존 schema v1 파일이 있다면 버전을 섞지 말고 문서의 마이그레이션 절차를 따르세요.

data:
  schema-version: v2
  controlplane-metrics: |-
    default-targets-scrape-enabled: |-
      apiserver = true
      etcd = true
    default-targets-metrics-keep-list: |-
      apiserver = "apiserver_flowcontrol_current_executing_seats|apiserver_flowcontrol_rejected_requests_total"
    minimal-ingestion-profile: |-
      enabled = true

v2에서는 default-targets-scrape-enabled, 컨트롤 플레인 섹션 안에서 이전 controlplane- 접두사를 뺀 대상 이름, 중첩된 minimal-ingestion-profile 구성을 사용합니다. 스케줄링 분석이 필요하다면 kube-scheduler 활성화와 필요한 메트릭 유지는 별도로 검토할 변경입니다. keep-list 항목은 수집 의도를 나타낼 뿐, 대상이 해당 메트릭을 노출하거나 전달한다는 증거는 아닙니다.

검토된 전체 ConfigMap을 적용하는 것은 수집 동작을 바꾸는 Kubernetes 쓰기 작업입니다. 다음 명령은 그 효과를 명시적으로 보여줍니다. 위 조각을 전체 파일처럼 적용하지 마세요. 병합된 설정을 다시 읽고 작업 영역에서 실제 시계열을 확인하세요. 관리형 Prometheus 전체 수집을 끄는 것은 컨트롤 플레인만 변경한 작업에 대한 제한적인 롤백이 아닙니다.

$ReviewedConfigPath = "REPLACE_WITH_REVIEWED_COMPLETE_CONFIGMAP.yaml"
kubectl apply --filename $ReviewedConfigPath

7. 올바른 유형, 범위, 시간 구간으로 쿼리하기

아래 PromQL은 모두 읽기 전용 예시입니다. REPLACE_SCOPE_LABEL과 REPLACE_SCOPE_VALUE를 정확히 하나의 클러스터를 선택하는 확인된 라벨과 값으로 바꾸고, REPLACE_TARGET_LABEL과 REPLACE_TARGET_VALUE를 해당 컨트롤 플레인 대상의 라벨과 값으로 바꾸세요. 작업 영역의 시계열 탐색기에서 확인하고 라벨 이름, 클러스터 별칭, 대상 값을 가정하지 마세요. 첫 번째 그룹은 API 서버 대상, 스케줄링은 스케줄러 대상, 데이터베이스 크기는 etcd 대상을 사용합니다. 모든 분자와 분모에 이 범위를 유지하세요. 집계 전에 복제본 식별 정보와 중복 수집 여부를 확인하세요.

시계열 수는 수집 확인이고 게이지는 점유량

count(apiserver_request_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"})
count(apiserver_flowcontrol_current_executing_seats{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"})

sum(apiserver_flowcontrol_current_executing_seats{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"})

처음 두 식은 요청이나 점유 seat가 아니라 반환된 라벨 조합을 셉니다. 세 번째 식은 각 평가 시점에서 선택한 시계열의 순간 게이지 값을 더합니다. 범위 그래프는 이 계산을 시간에 따라 반복하며, 모든 타임스탬프의 값을 한꺼번에 더하지 않습니다. 이 점유량 게이지에는 rate()나 increase()를 적용하지 마세요. 진단할 때는 전체 합계만 보지 말고 우선순위 수준별 보기도 유지하세요.

카운터 변화량과 속도는 다른 질문에 답함

sum by (code) (
  increase(apiserver_request_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"}[5m])
)

sum by (code) (
  rate(apiserver_request_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"}[5m])
)

sum(rate(apiserver_request_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE",code=~"429|5.."}[5m]))
/

  increase(apiserver_flowcontrol_rejected_requests_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"}[5m])
)

시계열별 초기화를 처리할 수 있도록 먼저 각 카운터에 범위 함수를 적용하고 나서 합산하세요. increase()는 구간의 변화량을 추정하며 외삽 때문에 소수 값을 반환할 수 있습니다. rate()는 평균 초당 속도를 제공합니다. 5분은 분석 구간의 예시이지 수집 간격이나 보편적인 경고 규칙이 아닙니다. 샘플이 충분한 구간을 선택하고 공백이나 재시작을 조사할 때는 원시 시계열을 유지하세요.

백분율은 선택한 전체 API 요청 중 HTTP 429와 5xx 응답을 합친 비율입니다. 용량 점수나 애플리케이션 오류율이 아닙니다. 일치하는 오류 시계열이 없으면 결과가 없을 수 있고, 트래픽이 없으면 분모가 0이 될 수 있습니다. 무조건적인 0 대체로 관측 데이터 누락을 숨기지 마세요. APF 거절은 흐름 제어 진단에 도움이 되지만 HTTP 오류에 더하면 같은 요청을 중복 계산할 수 있습니다. 사용 가능한 우선순위 수준 및 이유 라벨을 별도로 확인하세요.

스케줄러 시도와 파티션별 데이터베이스 크기

sum by (result) (
  rate(scheduler_schedule_attempts_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"}[5m])
)

max by (REPLACE_PARTITION_LABEL) (
  etcd_mvcc_db_total_size_in_bytes{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"}

결과 그룹을 해석하기 전에 스케줄러의 실제 result 라벨과 값을 확인하세요. 실패한 시도 수는 실패한 고유 Pod 수가 아닙니다. Hyperscale 문서는 접미사가 붙은 스케줄러 이름도 나열하지만 기본 수집 참조 문서는 여기서 사용하는 정식 카운터를 나열합니다. 문서에 나온 모든 변형이 존재한다고 가정하지 말고 실제 노출된 시계열을 확인하세요. 어느 식도 Pod Ready 지연 시간을 측정하지 않습니다.

실제 리소스 파티션 차원을 확인한 뒤에만 REPLACE_PARTITION_LABEL을 바꾸세요. etcd 식은 파티션별 가장 큰 복제본 데이터베이스 크기를 GiB로 반환하며, 데이터베이스 크기의 합이나 사용률을 반환하지 않습니다. 게이지이므로 카운터 속도를 적용하지 않습니다. 필요한 파티션 라벨이나 메트릭이 없다면 문서화된 플랫폼 데이터베이스 사용률 메트릭의 리소스 유형 차원을 사용하거나 수집을 수정하세요. 모든 파티션을 하나의 통합 용량처럼 조용히 합쳐서는 안 됩니다.

신호첫 조사가능한 다음 단계
높은 seat와 최근 APF 거절 증가를 동반한 지속적인 API 지연우선순위 수준별 수요, 요청 구성, list/watch 동작, 재시도, webhook 확인불필요한 API 작업을 줄이고 대표성 있는 근거가 있을 때만 다른 크기 평가
API 용량에 여유가 있는데 스케줄링 불가 시도가 발생노드 리소스, taint, affinity, 볼륨 토폴로지, Pod 요청 확인더 큰 컨트롤 플레인이 해결한다고 가정하지 말고 배치나 워커 용량 수정
스케줄링된 Pod가 준비 상태가 되지 않음이미지, 볼륨, 초기화, 네트워크, 프로브 확인워커와 애플리케이션 경로를 별도로 측정
다른 파티션은 작은데 하나의 etcd 파티션만 증가리소스 수, 객체 크기, 보존 정책, 복제본 집계 검토안전한 수명 주기 변경 계획 수립. H4/H8은 공개된 파티션당 스토리지를 늘리지 않음
구성 변경 후 그래프가 비어 있음작업 영역 접근, 대상 활성화, 스키마, keep-list, 라벨, 수집 경과 시간 확인데이터 부재를 정상적인 무부하로 해석하기 전에 관측 기능 복구

유용한 평가 계획은 후보 크기 사이에서 워크로드 형태, 작업 구성, 클라이언트 동시성, 객체 수, 관측 기간을 동일하게 유지합니다. 리소스가 실제 보고한 크기, 수집 간격, 쿼리 범위, 누락 데이터, 클라이언트 완료 시간, 요청 지연 시간, 오류 변화량, 워커 용량을 기록하세요. 이는 앞으로 수행할 방법의 제안이며 여기서 실행한 테스트가 아닙니다. Deployment 10개 시연으로 벤치마크를 주장하지 마세요.

  • 변경을 승인하기 전에 날짜가 명시된 Preview 자격 조건, 약관, 지역 할당량, 지원 도구를 확인하세요.
  • 일반 클러스터 마이그레이션과 기존 Hyperscale 크기 업데이트를 구분하고, 데이터를 안전하게 지킬 롤백 계획을 유지하세요.
  • 경고를 설정하거나 크기를 비교하기 전에 관측 범위와 카운터·게이지의 의미를 검증하세요.
  • API 동시성, 스케줄링 시도, Pod Ready 지연 시간, 파티션 증가 추이를 별도 패널로 유지하세요.
  • 하나의 누적 오류 총계나 저부하 스크린샷 대신 지속적이고 서로 연관된 신호를 사용하세요.
  • 최신 가격과 모든 관측 데이터, 워커, 네트워크, 스토리지 비용을 별도로 검토하세요. 이 글은 가격이나 SLA 결론을 제공하지 않습니다.

10. 공개 참조 문서와 날짜를 명시한 해석

다음 공개 참조 문서는 2026년 10월 7일에 확인했습니다. 위의 기능 제약과 메트릭 의미를 뒷받침할 뿐, 독자의 구독이 자격을 갖췄거나 어떤 명령이 성공적으로 실행되었다는 주장은 아닙니다. 과거 노트는 관측의 근거이며, 지원되는 수명 주기 설명은 공개 제품 문서를 기준으로 합니다.

  • Microsoft Learn: 컨트롤 플레인 확장 프로파일을 사용하는 AKS Hyperscale 구성 — 크기 선택, Preview 약관, Standard/Premium 요구 사항, 사전 조건, 신규 클러스터 제한, 크기 변경, 파티션, 모니터링 지침.
  • Microsoft Learn: AKS 컨트롤 플레인 메트릭 모니터링 — 관리형 수집, ID 및 Private Link 제한, schema v2, keep-list, 작업 영역 접근.
  • Microsoft Learn: 기본 Prometheus 메트릭 구성 — 최소 수집, 대상 기본값, 정식 메트릭 이름. 이전 접두사가 붙은 섹션 제목은 v2 구성 키를 대신하지 않습니다.
  • Azure Prometheus 수집기: 공개 설정 ConfigMap — 유지 관리되는 스키마 참조. 모든 기본값을 무조건 적용하지 말고 병합 전에 변경 사항을 검토하세요.
  • Microsoft Learn: AKS 리소스, SKU, 지역 한도 — 기능별 Preview 클러스터 하나 제한과 구분되는 일반 할당량.
  • Kubernetes: API Priority and Fairness — seat 점유량, 요청 폭, 우선순위 수준, 대기열.
  • Kubernetes: 스케줄러 — 애플리케이션 준비 상태가 아닌 노드 적합성, 점수 계산, 바인딩.

원본 수준의 두 가지 모호함은 명시적으로 바로잡았습니다. Hyperscale 크기 간 변경은 지원되며, 스케줄링 용량은 크기 단계마다 두 배가 되지 않습니다. 문서의 두 가지 주의점은 그대로 드러냅니다. etcd의 GB와 GiB 표기 차이, 그리고 실제 검색이 필요한 스케줄러 메트릭 이름 변형입니다. 어느 것도 문서에 없는 보장을 추론할 이유가 되지 않습니다.
