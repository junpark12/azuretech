APIM AI Gateway: 스트리밍 응답을 위한 Content Safety

llm-content-safety, 관리 ID, 정규식 차단 목록, 여덟 가지 정책 시나리오, 현재 디버그 추적, 스트리밍 윈도와 겹침의 탐지·지연 시간 절충 관계를 다루는 실습 가이드입니다.

한국어판변수화된 예제2026년 9월

한국어판은 검토·수정된 영문 게시본을 기준으로 번역했습니다. 코드, 다운로드 파일, 구조도 내부 표기와 영문 Azure Portal 캡처는 두 언어에서 동일하게 사용합니다.

환경별 관찰 결과입니다. 측정값과 미리 보기 기능의 동작은 원본 조사 환경에서 확인한 내용이며, 현재 서비스의 보장 사항이 아닙니다. 구성값은 자신의 환경에 맞게 지정해야 합니다.

비공식 실습 가이드이며 Microsoft 서비스 보장이 아닙니다. 이 영어 원문 기반 문서는 현재 문서화된 동작, 과거 관찰 결과, 검증되지 않은 튜닝 가설을 구분합니다. 원문 검토에서는 2026년 9월 17일 Microsoft Learn을 확인했으며, 2026년 8월 18일자 정책 참조 문서도 포함했습니다. 이번 편집 작업에서는 리소스를 다시 배포하거나 Azure 실험을 재실행하지 않았습니다. 탐지율, 지연 시간, 호출 횟수, HTTP 상태, 스트림 종료 예시는 SLA가 아닙니다.

중요 정정: 문서화된 기본 응답 윈도 크기는 10,000자가 아니라 1,000자입니다. 요청 윈도는 10,000자이며 window-size로 변경할 수 없습니다. 과거에 명시적으로 설정한 3,000자 및 10,000자 응답 설정은 기본값이 아니라 예시로 유지합니다.

다운로드할 수 있는 base-policy.xml과 이에 대응하는 policy-payload.json은 Content Safety 정책이 없는 패스스루 기준 구성입니다. 상속되는 정책은 별도로 검토하세요. 이 파일만 배포해도 해당 보호 기능이 추가되는 것은 아닙니다.

1. 아키텍처와 스트리밍 동작 계약

클라이언트는 Azure API Management(APIM)를 통해 Azure OpenAI 또는 호환되는 Foundry 모델 배포로 chat-completions 요청을 보냅니다. 인바운드 llm-content-safety 정책은 프롬프트를 검사할 수 있고, 아웃바운드 인스턴스는 생성된 응답을 검사할 수 있습니다. 정책은 로컬에서 분류하지 않으며, 전용 APIM 백엔드 엔터티를 통해 별도의 Azure AI Content Safety 리소스를 호출합니다.

  1. set-backend-service로 모델 라우팅을 구성하고 authentication-managed-identity로 모델에 대한 APIM 인증을 설정합니다.
  2. 필요에 따라 Prompt Shields, 유해성 범주, 차단 목록을 사용해 인바운드 요청을 검사합니다.
  3. Server-Sent Events(SSE)를 위해 buffer-response="false"로 백엔드 응답을 전달합니다.
  4. 아웃바운드에 llm-content-safety를 배치하여 슬라이딩 윈도로 스트리밍 텍스트를 버퍼링하고 평가합니다.

모델 백엔드와 Content Safety 백엔드는 각각 구성과 권한 부여가 필요합니다. 요청과 응답 검사에는 서로 다른 범주, 임계값, 차단 목록을 사용할 수 있습니다. 스트리밍 정책 위반이 발생하면 문서화된 스트림 처리기는 403을 반환하는 대신 후속 이벤트 전달을 중단합니다. 이미 클라이언트에 전달된 텍스트는 회수할 수 없습니다. 인증 오류, 인바운드 거부, 백엔드 실패는 여전히 다른 HTTP 결과를 낼 수 있으므로, 모든 스트리밍 요청이 200을 반환한다는 뜻은 아닙니다.

2. 사전 요구 사항과 실습 안전 수칙

이 문서는 무인 배포 스크립트가 아니라 수동 Bash/WSL 실습입니다. 실행 전에 각 단계를 읽으세요. 리소스 생성에는 비용이 발생하며, 정책 PUT은 해당 범위의 정책을 교체합니다. 공유 또는 프로덕션 환경이 아닌 새 전용 실습 리소스 그룹을 사용하세요. 게시 준비 중 이 문서의 명령을 Azure에서 실행하지 않았습니다.

  • Azure CLI 2.7x 이상, Bash, Python 3, jq, 그리고 --fail-with-body를 지원하는 curl 7.76 이상이 필요합니다. 설치된 버전과 현재 명령 도움말을 확인하세요. Ubuntu/Debian 또는 WSL에서 jq가 없다면 sudo apt-get install -y jq로 설치하세요.
  • 리소스 생성 및 해당 범위의 역할 할당 권한이 필요합니다. 제어 평면의 Owner/Contributor 권한이 필요한 Content Safety 데이터 평면 역할을 자동으로 대체하지는 않습니다.
  • 선택한 APIM 계층, Azure AI Content Safety, 모델, 모델 버전, 배포 유형, 할당량을 지원하는 리전이 필요합니다. 조사할 예로 eastus2, swedencentral, westus3가 있지만 모든 조합의 지원을 뜻하지는 않습니다. 같은 리전에 배치하면 지연 시간 분석이 간단해지지만 필수는 아닙니다.
  • 문서화된 정책 지원 계층은 Developer, Basic, Basic v2, Standard, Standard v2, Premium, Premium v2입니다. Consumption은 지원되지 않습니다. Developer는 실습에 간편한 선택입니다.

원문에서는 Azure CLI 2.86의 SKU 목록에 v2 SKU 대신 Basic | Consumption | Developer | Isolated | Premium | Standard가 az apim create --sku-name의 선택지로 표시됨을 관찰했습니다. 이는 CLI 버전에 대한 관찰이며 정책 지원 표가 아닙니다. az apim create --help를 확인하세요. 부록에 별도의 ARM 대안이 있습니다.

키와 토큰은 프로세스 변수에만 보관하세요. 값을 명령에 붙여 넣거나 출력하거나 파일로 저장하거나 커밋하지 마세요. set -x, curl -v, 공유 터미널 녹화를 피하세요. 변수 기반 -H 인수도 확장된 비밀 정보를 프로세스 인수에 노출할 수 있습니다. 이 명령은 신뢰할 수 있는 개인 실습에서만 사용하고, 프로덕션 자동화에는 보호된 비밀 정보 입력 방식을 사용하세요.

curl 성공 여부만 보지 말고 HTTP 상태와 오류 내용을 확인하세요. 등록/분석 성공(2xx), 예상된 정책 차단(403), 인증 실패(401/403), 제한(429), 서비스 오류(5xx)를 구분하세요. HTTP 200, [DONE], curl 종료 코드 0만으로 안전 검사가 실행되었다고 증명할 수는 없습니다. 실패하면 진행을 멈추고 원인을 조사하세요.

4.5 두 APIM 백엔드 생성

az apim backend create \

Content Safety 백엔드 URL은 API 경로가 없는 리소스 호스트입니다. 권한 부여 대상(audience)은 이 엔드포인트 URL이 아닙니다.

필수 수동 포털 단계: APIM에서 content-safety-backend를 편집하고 권한 부여를 열어 관리 ID를 활성화한 다음 클라이언트 리소스를 정확히 https://cognitiveservices.azure.com으로 설정하세요. 저장 후 시스템 할당 ID와 Content Safety RBAC 할당을 확인하고, 실제 정책 호출을 검증한 뒤 진행하세요.

credentials.authorization: {"scheme":"Bearer"}는 HTTP 인증 스키마를 지정할 뿐 관리 ID 토큰을 발급하지 않습니다. 검토한 공개 ARM 2024-05-01 및 2025-09-01-preview의 BackendCredentialsContract 스키마에는 managedIdentity가 노출되지 않았습니다. 따라서 이 가이드는 두 버전 모두에서 credentials.managedIdentity.resource를 검증된 REST 페이로드로 제시하지 않습니다. 향후 REST 자동화는 먼저 선택한 API 버전의 지원을 확인해야 합니다.

4.7 패스스루 기준 구성 적용 및 검사

검토한 코어 CLI에는 az apim api policy create 명령이 없습니다. az rest를 통해 ARM REST를 사용하세요. 현재 인터페이스는 az apim api --help로 확인하세요. 다운로드한 기준 구성을 전용 실습 디렉터리에 저장하고 다음 재사용 도우미를 정의하세요.

apply_api_policy() {
  local xml_file="$1"
  local payload
  [[ -r "$xml_file" ]] || { echo "Cannot read policy XML" >&2; return 1; }
  command -v jq >/dev/null || { echo "jq is required" >&2; return 1; }
  payload=$(jq -Rs --arg fmt "rawxml" \
    '{properties:{format:$fmt,value:.}}' "$xml_file") || return 1
  az rest --method PUT \
    --url "https://management.azure.com/subscriptions/$SUB_ID/resourceGroups/$RG/providers/Microsoft.ApiManagement/service/$APIM_NAME/apis/azure-openai-api/policies/policy?api-version=$APIM_API_VERSION" \
    --body "$payload" --output none || return 1
}

apply_api_policy base-policy.xml

az rest --method GET \
  --url "https://management.azure.com/subscriptions/$SUB_ID/resourceGroups/$RG/providers/Microsoft.ApiManagement/service/$APIM_NAME/apis/azure-openai-api/policies/policy?api-version=$APIM_API_VERSION&format=rawxml"
<policies>
    <inbound>
        <base />
        <set-backend-service backend-id="openai-backend" />
        <authentication-managed-identity resource="https://cognitiveservices.azure.com" />
    </inbound>
    <backend>
        <forward-request timeout="180" buffer-response="false" />
    </backend>
    <outbound>
        <base />
    </outbound>
    <on-error>
        <base />
    </on-error>
</policies>

먼저 7절의 구독 키 및 정상 요청 절차로 클라이언트 → APIM → 모델 패스스루를 확인하세요. 이 정책은 Content Safety를 추가하지 않습니다. buffer-response="false"는 일반 전달 버퍼링을 끌 뿐 안전 정책의 검사 윈도 버퍼링을 끄지 않습니다. PUT은 기존 API 정책을 교체하며, <base />는 이전 API 정책이 아니라 상위 범위 정책을 상속합니다. 교체 전에 기존 구성을 보존하고 검토하세요.

        <category name="SelfHarm" threshold="4" />

5.2 범주와 경계값을 포함하는 임계값

설정정의
categories범주 규칙을 담는 선택적 컨테이너입니다.
output-type기본값은 FourSeverityLevels이며 출력은 0, 2, 4, 6입니다. EightSeverityLevels는 0부터 7까지 반환합니다.

임계값이 4이면 EightSeverityLevels는 4–7을 차단하고 FourSeverityLevels는 반환값 중 4와 6을 차단합니다. 더 세밀한 출력이 더 높은 정확도나 특정 입력에 대한 다른 결정을 보장하지는 않습니다. 임계값 0은 점수가 0인 콘텐츠도 거부할 수 있습니다.

5.3 차단 목록, 정규식, 안전한 테스트 데이터

blocklists는 id 참조를 담는 선택적 컨테이너이며, 참조 대상 목록은 Content Safety 리소스에 등록됩니다. APIM이 목록을 생성하지는 않습니다. ID는 정책 식을 지원합니다. 목록은 네 가지 유해성 범주가 표현하지 못하는 조직별 용어, 알려진 민감 값, 형식 패턴을 처리할 수 있습니다. 이는 완전한 PII 탐지기나 정보 공개 방지 보장이 아닙니다. 철자 변경, 정규화, 경계 동작, 서비스 실패를 테스트하세요.

정규식을 지원합니다. Content Safety REST 2024-09-01의 TextBlocklistItem 스키마에는 선택적 isRegex가 있습니다. true이면 text를 정규식으로 처리하고, false이거나 생략하면 일반 텍스트 항목을 만듭니다. 일반 텍스트 일치가 대소문자를 구분하는 부분 문자열 비교와 같다고 가정하지 마세요. 대소문자, 단어 경계, 정규화, 검사 경계를 테스트하세요. 이는 차단 목록에 정규식을 사용할 수 없다는 과거 주장을 정정합니다.

{
  "blocklistItems": [
    { "description": "Plain-text example", "text": "hate" },
    { "description": "Regex example", "text": "b[i1][a@][s\\$]", "isRegex": true }

}

검토한 코어 Azure CLI에는 전용 차단 목록 명령이 없습니다. Content Safety 데이터 평면 REST API를 사용하세요. disableLocalAuth=true이면 계정 키 대신 Entra 토큰을 사용하세요. 현재 로그인한 실습 운영자는 APIM의 ID와 별개로 Cognitive Services User 역할이 필요합니다.

이 정규식은 형태만 일치시킵니다. 날짜, 체크섬, 발급 여부, 신원, 실제 PII 여부를 검증하지 않습니다. 실제 식별자나 비밀 정보로 바꾸지 마세요.

모델 보장이 아닌 과거 관찰 결과: 6자리/1자리/6자리 코드를 요청했을 때 첫 정규식이 기대하는 연속된 7자리 접미부 대신 하이픈 두 개가 출력되기도 했습니다. 비식별화한 예시는 991332-1-000000, 991332-3-000000, 991332-4-000000입니다. 하이픈이 하나인 원래 정규식으로는 일치시킬 수 없습니다.

접근이 제한된 진단 자료에는 필요한 항목 식별자, 결정, 상관관계 메타데이터만 기록하세요. 원문 프롬프트/응답이나 PII 로깅을 기본으로 활성화하지 마세요. 예외적으로 원문 텍스트를 보관하려면 승인, 마스킹, 접근 제어, 짧은 보존 기간이 필요합니다.

5.4 스트리밍 동작: 근거와 현재 디버그 추적 방식

과거의 특정 환경에 한정된 근거: 아래의 200/403 비교, 처음 검사한 198자 구간, 14바이트 다운로드, data: [DONE]는 과거의 특정 요청에 대한 결과입니다. 게이트웨이, 모델, 정책 버전 전반에서 보장되지 않습니다. 요청들은 통제된 동일 바이트 시퀀스가 아니라 서로 다른 모델 응답을 생성했습니다. 비식별화한 테스트 데이터의 길이는 원래 관찰된 길이와 다를 수 있습니다.

문서화된 슬라이딩 윈도 처리기는 이벤트를 버퍼링하고 스트리밍 위반을 감지하면 후속 이벤트 전달을 중단합니다. 해당 스트리밍 위반에 대해 403을 반환하지 않습니다. 같은 정책 참조 문서는 요청 또는 응답이 Content Safety 문자 제한을 넘으면 403을 반환하는 경우를 별도로 설명합니다. 응답 윈도가 작다는 이유만으로 모든 길이 관련 오류가 불가능하다고 볼 수는 없습니다.

계산만으로 정확한 서비스 호출 횟수를 추론하지 마세요. 11,000자 텍스트에 1,000자 윈도를 사용한다고 해서 정확히 11개 윈도 또는 Content Safety 11회 호출이 성립하지는 않습니다. 겹침, SSE 및 메시지 구조, 끝부분 텍스트, 재시도, 구현 세부 사항이 영향을 줄 수 있습니다. 이는 이전 실습 설명의 검증되지 않은 추론을 정정합니다.

상태와 헤더만으로 차단 구성 요소를 식별할 수 없는 이유

원문에서는 성공한 요청에서도 x-ms-rai-invoked: true를 관찰했습니다. 이 헤더만으로 모델의 네이티브 콘텐츠 필터가 거부 원인이었다고 입증할 수는 없습니다. 요청과 APIM 정책 추적을 연계하여 APIM Content Safety, 모델 필터링, 인증 실패, 제한, 무관한 오류를 구분하세요.

1단계: 수명이 짧은 API별 디버그 자격 증명 발급

APIM_ARM_ID="/subscriptions/$SUB_ID/resourceGroups/$RG/providers/Microsoft.ApiManagement/service/$APIM_NAME"
DEBUG_BODY=$(jq -n --arg api "$APIM_ARM_ID/apis/azure-openai-api" \
  '{credentialsExpireAfter:"PT15M",apiId:$api,purposes:["tracing"]}')
DEBUG_TOKEN=$(az rest --method POST \
  --url "https://management.azure.com$APIM_ARM_ID/gateways/managed/listDebugCredentials?api-version=$APIM_API_VERSION" \
  --body "$DEBUG_BODY" --query token -o tsv)
[[ -n "$DEBUG_TOKEN" && "$DEBUG_TOKEN" != "null" ]] || {

}

관찰된 정규식 재현성: 합성 형식을 명시하기

특정 환경의 관찰 결과: 정확한 형식 없이 가상의 운전면허번호 유사 문자열 5개를 요청하면 00-00-000001과 00-00-000002처럼 그룹 3개가 출력되기도 했습니다. 필요한 정규식은 그룹 4개이므로 마지막 2자리 그룹이 빠지면 일치하지 않았고, 관찰된 비스트리밍 응답은 200이었습니다.

2 digits-2 digits-6 digits-2 digits를 지정하고 00-00-000001-00 같은 합성 예시를 제공한 한 테스트에서는 끝부분이 000001-00부터 000005-00까지인 일치 시퀀스를 생성했습니다. 그 요청은 403으로 차단되었고 추적에서는 등록된 4개 그룹 패턴이 확인되었으며, 유해성 범주는 심각도 0을 유지했습니다.

명시적인 형식 지시는 변수 하나를 줄일 뿐 확률적 모델을 결정적으로 만들지 않습니다. 먼저 고정된 합성 입력으로 정규식을 검증한 후, 모델의 형식 변형, 공백, 하이픈, 그룹 수를 별도로 평가하세요. 이 정규식은 포괄적인 PII 보호가 아닙니다.

5.5 윈도 크기, 겹침, 경계 탐지 및 스트리밍 지연 시간

튜닝 가설과 실험 설계이며 새로운 벤치마크나 공식 권장값이 아닙니다. 윈도가 커진다고 탐지 정확도가 단조 증가하지는 않습니다. 탐지, 문맥 보존, 체감 응답성, 종단 간 시간, 분석량, 비용은 서로 다른 결과입니다. 실제 게이트웨이, 모델, 겹침, 부하 조건에서 함께 측정하세요.

변경가능한 이점가능한 비용 또는 제한
window-size 증가더 긴 문자열, 패턴, 문맥이 하나의 분석 구간에 들어갈 수 있습니다.텍스트를 모으는 동안 최초 콘텐츠 또는 후속 전달이 지연될 수 있습니다. 문맥이 많다고 더 정확한 분류가 보장되지는 않습니다.
window-size 감소더 작은 구간을 더 일찍 검사하고 내보낼 수 있습니다.검사가 잦아지면 서비스 지연, 제한 압력, 비용이 늘어날 수 있습니다. 작은 윈도가 항상 더 빠르지는 않습니다.
window-overlap-size 증가패턴이 인접한 검사 윈도에 걸칠 때 탐지 누락을 줄일 수 있습니다.일부 텍스트를 반복 분석하므로 분석량, 호출 빈도, 지연 시간, 비용이 증가할 수 있습니다. 실제 호출은 추정하지 말고 관찰해야 합니다.

window-size는 분석 구간 크기를, window-overlap-size는 인접 구간이 공유하는 양을 설정합니다. 서로 대체할 수 있는 설정이 아닙니다. 1,000/200자나 3,000/500자 같은 값은 비교 후보이지 보편적인 권장값이 아닙니다.

경계 예시: LAB_BLOCK_ / MARKER

Registered literal: LAB_BLOCK_MARKER

Logical inspection window A: ... LAB_BLOCK_
Logical inspection window B: MARKER ...

독립적으로 검사하는 두 구간 중 어느 쪽에도 전체 리터럴이 없으면 일치를 놓칠 수 있습니다. 이는 논리적 검사 윈도 경계의 예시이며 네트워크 패킷이나 SSE 이벤트를 나누면 반드시 탐지가 누락된다는 주장이 아닙니다. 게이트웨이는 평가 전에 전송 이벤트 여러 개의 텍스트를 조합할 수 있습니다. 이러한 경계는 별도로 테스트하세요.

  • 겹침은 정규식 소스 코드의 문자 수가 아니라 일치해야 하는 텍스트 길이와 필요한 주변 문맥을 고려해 선택하세요.
  • 가변 길이 정규식 일치와 긴 문맥을 필요로 하는 판단은 고정된 겹침에 들어가지 않을 수 있습니다. 공백, 정규화, 다른 철자, 형식 변형도 별도의 탐지 공백을 만듭니다.
  • 겹침은 경계 위험을 줄일 수 있지만 모든 탐지를 보장하지는 않습니다. 윈도를 키우는 것만으로 경계 효과가 사라지지는 않습니다.
  • 나중 검사에서 전송을 중단하더라도 이미 전달된 앞부분은 회수할 수 없습니다. 이 정책만으로 민감한 조각이 전혀 노출되지 않는다고 보장할 수는 없습니다.

스트리밍이 몰아서 출력되는 것처럼 느껴질 수 있는 이유

충분한 텍스트가 모이기를 기다린 뒤 Content Safety를 기다리면 점진적 출력이 일시 정지 → 일괄 전달 → 일시 정지로 바뀔 수 있습니다. 여기서는 정확한 플러시 조건과 일괄 전달 크기를 확정하지 않습니다. 큰 윈도의 누적 대기 시간과 작은 윈도에서 늘어날 수 있는 검사 오버헤드는 상충합니다. 작은 윈도를 확실한 지연 최적화로 보지 말고 윈도와 겹침을 함께 비교하세요.

측정 항목기록할 내용
최초 콘텐츠 도착 시간요청 시작부터 첫 비어 있지 않은 콘텐츠 델타까지의 시간입니다. 최초 HTTP 헤더나 빈 SSE 이벤트까지의 시간이 아닙니다.
콘텐츠 델타 도착 간격간격, 긴 정지, 일괄 전달 패턴을 기록합니다. 평균뿐 아니라 반복 실행의 p50과 p95를 비교하세요.
종단 간 시간정상 완료, 차단, 연결 끊김, 시간 초과를 구분해 기록하세요. 차단으로 중단된 짧은 응답은 성능 향상이 아닙니다.
경계 탐지 및 누락동일한 합성 리터럴이나 패턴을 예상 논리적 경계 앞, 경계에 걸친 위치, 경계 뒤에 배치하세요. 콘텐츠는 고정한 채 겹침을 바꾸세요.
서비스 호출, 분석량, 오류 및 비용사용 가능한 서비스 메트릭과 최소한의 추적 메타데이터로 호출/분석량, 429, 실패, 비용을 측정하세요. 문자 수를 윈도 크기로 나눈 값은 측정된 호출 횟수가 아닙니다.
  1. 먼저 고정된 합성 SSE 출력을 재생하는 통제된 테스트 백엔드를 사용하세요. 콘텐츠, 출력 길이, 이벤트 타이밍을 고정한 채 예상 검사 경계에 대한 마커 위치를 바꾸세요. 이렇게 하면 모델 변동성과 버퍼링을 분리할 수 있습니다. 원문은 설계만 제공하며 즉시 사용할 수 있는 재생 서버는 제공하지 않습니다.
  2. 안전 정책을 추가하지 않은 패스스루 기준 구성과 여러 윈도/겹침 조합을 비교하세요. 입력, 출력 길이, 동시성, 관련 환경 설정을 일정하게 유지하고 반복 실행하세요.
  3. 그다음 실제 모델 생성을 별도로 테스트하세요. 모델은 마커 출력 여부, 위치, 형식을 바꿀 수 있으므로 두 모델 호출은 동일 출력을 통제한 실험이 아닙니다.
  4. 아웃바운드를 테스트할 때 검사 대상 차단 목록은 인바운드에서 제외하세요. 그렇지 않으면 생성 전에 프롬프트가 차단될 수 있습니다. 합성 테스트 데이터만 사용하세요.

원문에서 제안한 10–20% 겹침과 3,000자 윈도에 300–500자라는 예시는 실험 시작점이지 공식 비율이 아닙니다. 반복 분석 오버헤드와 경계 일치 누락을 함께 평가하세요. 정확한 호출 횟수 보장이나 측정된 지연 시간 분포는 제공되지 않습니다.

문자 수 계산의 한계: 과거 작성자는 ASCII와 한글이 각각 한 문자로 동작함을 관찰했습니다. 둘 다 기본 다국어 평면에 있으므로 이 관찰로 Unicode 코드 포인트와 UTF-16 코드 단위를 구분할 수는 없습니다. 이모지, 보충 평면 문자, 결합 문자는 검증하지 않았습니다. REST 차단 목록 항목의 코드 포인트 길이 정의를 APIM 스트리밍 구현에 그대로 적용하지 마세요. UTF-8 바이트, Python len(), 실제 분석 구간을 각각 비교하세요.

5.6 큰 인바운드 요청: 코딩 및 에이전트 워크로드

에이전트 요청에는 긴 시스템 프롬프트, 도구 정의, 이력, 파일 내용, diff가 함께 들어갈 수 있습니다. 원문의 한 관찰은 도구 10개와 약 67 KB JSON 본문을 가진 코딩 에이전트 요청을 설명했습니다. 이전의 약 67,000자라는 설명에는 별도의 문자 수 측정이 없었습니다. 바이트와 문자는 서로 대체할 수 없습니다.

문서화된 제한과 실행하지 않은 실험의 구분: 정책 참조 문서는 10,000자 요청 윈도와 Content Safety 문자 제한 초과 시 403을 설명합니다. 그러나 모든 메시지와 도구가 나뉘지 않은 하나의 검사 문자열로 직렬화된다거나 자동 분할이 절대 발생하지 않는다고 여기서 입증되지는 않습니다. JSON 바이트 크기만으로 거부를 예측할 수 없습니다. 다음은 검증 설계이며 새로 측정한 차단 경계나 원래의 67 KB 도구 스키마 요청 재현이 아닙니다.

  1. 먼저 불필요한 문맥과 도구 스키마의 부피를 줄이고, 허용 요청 크기와 초과 처리 방식을 명확히 정의하세요. 길이 오류를 피하려고 인바운드 안전 검사를 자동으로 비활성화하지 마세요. shield-prompt나 유해성 임계값 변경은 길이 제한의 우회책이 아닙니다.
  2. 아웃바운드 검사는 추가 계층으로 사용해야 하며 길이 오류가 발생할 수 없다는 증거로 삼아서는 안 됩니다. 아웃바운드 전용 보호는 공격과 유해 입력에 대한 입력 단계 보호를 제거하므로, 보안 검토에서 이 공백을 문서화하세요.
  3. 사용자 지정 검사 설계에는 구조화된 JSON 파싱, 분할, 실패 처리가 필요합니다. 마지막 사용자 메시지만 검사하면 시스템 메시지, 이력, 도구가 빠지므로 전체 요청 검사와 동등하지 않습니다.

<on-error>
    <base />
    <choose>
        <when condition='@(context.LastError != null &amp;&amp; context.LastError.Source == "llm-content-safety")'>
            <trace source="content-safety" severity="warning">
                <message>@{
                    return new JObject(
                        new JProperty("blocked", true),
                        new JProperty("source", context.LastError.Source),
                        new JProperty("reason", context.LastError.Reason),
                        new JProperty("timestamp", DateTime.UtcNow)
                    ).ToString();
                }</message>
            </trace>
        </when>
    </choose>
</on-error>

원문에서 가져온 blocked 레이블은 검증된 콘텐츠 위반 횟수가 아닙니다. Content Safety 정책 오류에는 다른 원인이 있을 수 있습니다. reason과 연계된 근거를 조사하고 이 추적을 보편적인 차단 메트릭으로 바꾸지 마세요. 짧은 소요 시간이나 응답 크기는 조사 단서이지 원인이 아닙니다.

FourSeverityLevels는 반환값 4와 6을, EightSeverityLevels는 4–7을 차단합니다. 더 세밀한 출력은 임계값 선택지를 늘리지만 임계값 4에서 다른 결정이나 정확도 향상을 보장하지 않습니다.
