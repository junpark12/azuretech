Azure AI Gateway 계층: 미리 보기 설정, 정책, MCP 및 토큰 모니터링

전용 AI Gateway 미리 보기 계층을 원문에 근거해 기술적으로 평가하고, 측정된 정책 동작과 애플리케이션 수준 토큰 보고를 살펴봅니다.

한국어판변수화된 예제2026년 9월

한국어판은 검토·수정된 영문 게시본을 기준으로 번역했습니다. 코드, 다운로드 파일, 구조도 내부 표기와 영문 Azure Portal 캡처는 두 언어에서 동일하게 사용합니다.

환경별 관찰 결과입니다. 측정값과 미리 보기 기능의 동작은 원본 조사 환경에서 확인한 내용이며, 현재 서비스의 보장 사항이 아닙니다. 구성값은 자신의 환경에 맞게 지정해야 합니다.

평가 범위와 제품 구분

이 글은 2026년 8월 20일 기술 검증 보고서를 번역하고 통합한 내용입니다. 원문은 East US 2의 실제 배포와 curl, OpenAI SDK, MCP JSON-RPC를 사용한 런타임 검사를 설명합니다. 문서에 명시된 미리 보기 지역은 East US 2와 Sweden Central이었습니다. 아래의 모든 시간, 횟수, 상태 코드, 가격 공개 여부, 기능 제한은 해당 평가를 설명하며, 새로운 테스트나 현재 서비스에 대한 보장이 아닙니다. 이 공개판을 준비하면서 클라우드 리소스 작업이나 추론 요청을 실행하지 않았습니다.

전용 AI Gateway 계층은 형식이 Microsoft.ApiManagement/service이고 SKU가 AIGateway이며 용량이 1인 ARM 리소스입니다. Microsoft.ApiManagement/gateways 형식과 WorkspaceGatewayPremium SKU로 식별되는 APIM 작업 영역 게이트웨이와는 다릅니다. 생성과 구성에는 독립 포털 https://ai.gateway.azure.com/ai-gateways를 사용합니다. 생성된 리소스는 ARM으로 검사할 수 있습니다.

az resource show \
  --ids "/subscriptions/YOUR_SUBSCRIPTION_ID/resourceGroups/YOUR_RESOURCE_GROUP/providers/Microsoft.ApiManagement/service/YOUR_GATEWAY_NAME" \
  --query "{sku:sku.name, capacity:sku.capacity, url:properties.gatewayUrl, identity:identity.principalId}" -o json
# Expected resource shape: SKU AIGateway, capacity 1, gateway URL, principal ID.

원본 포털 스크린샷에는 비공개 리소스 이름과 식별자가 포함될 수 있어 의도적으로 제외했습니다. 절차와 관찰 결과는 텍스트로 재현했습니다. 모든 YOUR_* 값은 기존 리소스가 아니라 반드시 대체해야 할 값입니다.

전용 미리 보기 계층과 기존 APIM 비교

기존 APIM은 범용 API 관리 서비스에 AI 게이트웨이 기능을 추가합니다. 백엔드를 등록하고 API를 가져오거나 정의하며, llm-token-limit, llm-semantic-cache 등의 XML 정책을 작성합니다. 전용 미리 보기 계층은 모델, MCP 서버, 토큰 제어, 셀프 서비스 카탈로그를 기본 리소스로 취급하며 XML 대신 정책 카드를 사용합니다.

아키텍처와 액세스 경계

  1. 게이트웨이가 api-key 헤더의 런타임 액세스 키를 인증합니다.
  2. 요청한 모델 또는 도구 자산에 연결된 정책을 평가합니다.
  3. 정확한 모델 등록 이름 또는 도구 라우팅으로 백엔드를 선택하고 구성된 자격 증명으로 업스트림을 인증합니다.
  4. 응답을 반환하고 지원되는 원격 분석을 내보냅니다.

OpenAI 호환 모델은 https://YOUR_GATEWAY_HOST/default/models/openai/v1을 공유합니다. Anthropic은 프로토콜별 경로인 /default/models/anthropic/v1/messages를 사용합니다. MCP 서버는 /default/toolservers/YOUR_MCP_SERVER_NAME/mcp를 사용합니다. default 세그먼트는 작업 영역 구분자입니다. 모델 등록 이름을 고유하게 지정하고, 추정한 내부 모델 ID가 아니라 정확히 그 이름을 요청에 전송하세요. 공급자별 기능과 매개 변수 호환성은 여전히 테스트가 필요합니다.

관리자는 Entra ID로 포털에 인증합니다. 애플리케이션은 키 또는 액세스 키 가져오기에서 생성한 수명이 긴 런타임 액세스 키를 사용합니다. 이 키에는 이름과 소유자가 있으며 명시적으로 교체하거나 해지할 때까지 유효합니다. 하나의 키로 게이트웨이의 모든 모델과 도구에 접근할 수 있습니다. 별도 키는 사용량 귀속을 제공할 뿐 모델별 권한 격리를 제공하지 않습니다. 애플리케이션 및 환경마다 키 하나를 사용하고, 비밀 관리 저장소에 보관하거나 환경 변수로 주입하며, 더 강한 자산 경계가 필요하면 게이트웨이를 분리하세요. 백엔드 공급자 키는 각 애플리케이션이 아니라 게이트웨이에 남습니다.

Foundry 준비, 게이트웨이 생성 및 모델 가져오기

원문에서는 평가 비용을 제한하기 위해 gpt-5-mini, 버전 2025-08-07, GlobalStandard 용량 1을 사용했습니다. 가져오기 전에 Foundry 계정에 배포가 있어야 합니다. 빈 계정을 선택하면 가져올 수 있는 모델이 없습니다. 계정 명령은 --kind AIServices, SKU S0 및 명시적 사용자 지정 도메인을 사용합니다.

az cognitiveservices account create \
  --subscription YOUR_SUBSCRIPTION_ID \
  -n YOUR_FOUNDRY_ACCOUNT -g YOUR_RESOURCE_GROUP -l eastus2 \
  --kind AIServices --sku S0 --custom-domain YOUR_FOUNDRY_ACCOUNT --yes
az cognitiveservices account deployment create \
  --subscription YOUR_SUBSCRIPTION_ID \
  -g YOUR_RESOURCE_GROUP -n YOUR_FOUNDRY_ACCOUNT \
  --deployment-name YOUR_DEPLOYMENT_NAME \
  --model-name gpt-5-mini --model-version 2025-08-07 \
  --model-format OpenAI --sku-name GlobalStandard --sku-capacity 1

이는 프로비저닝 예제이며 공개를 위해 실행한 명령이 아닙니다. 사용 전에 할당량, 모델 가용성, 권한, 비용, 대상 리소스 그룹을 확인하세요. 원문에서는 새 gpt-4o-mini 배포를 시도하다 ServiceModelDeprecating을 만났습니다. 이는 특정 환경과 날짜의 관찰이지 모든 지역이나 기존 배포에 대한 포괄적 설명이 아닙니다.

  1. 전용 포털에 로그인하고 게이트웨이 선택을 엽니다. 구독과 리소스 그룹으로 필터링하고 이름으로 검색하며 필요하면 새로 고침을 사용합니다.
  2. AI Gateway 만들기를 선택합니다. YOUR_GATEWAY_NAME을 입력하면 UI가 가용성을 확인하고 런타임 URL을 생성합니다. 사용 가능한 미리 보기 지역을 선택합니다. 고급을 펼쳐 리소스 그룹을 선택하거나 생성합니다.
  3. 시스템 할당 관리 ID를 확인합니다. 생성 시 용량이나 규모 단위를 묻지 않았으며 원문 테스트에서는 1분 이내에 완료되었습니다.
  4. 게이트웨이를 선택해 모델, MCP 서버, 정책, 모니터링, 네트워킹의 컨텍스트를 설정합니다. 게이트웨이를 전환할 때는 선택 화면으로 돌아갑니다.
  5. 모델 → Foundry에서 가져오기를 엽니다. 리소스 선택에서 구독과 Foundry 계정을 선택한 다음 검색된 배포를 선택합니다.
  6. 공급자 세부 정보에서 YOUR_PROVIDER_NAME과 표시 이름을 입력하고 관리 ID 또는 공급자 키 인증을 선택합니다.
  7. 역할 할당 결과를 확인합니다. 포털은 선택한 Foundry 계정에서 게이트웨이의 관리 ID에 Foundry User를 부여하려고 했습니다. 관리자에게 해당 역할 할당을 생성할 권한이 필요합니다. RBAC가 부족해 이후 추론이 실패하더라도 공급자 항목은 존재할 수 있습니다.
  8. 홈 또는 모델로 돌아가 애플리케이션 구성에 사용할 YOUR_GATEWAY_MODEL_NAME과 엔드포인트를 기록합니다.

Foundry에서 가져오기는 계정을 전용 게이트웨이 포털로 가져오는 것을 의미합니다. Azure Portal의 Foundry 블레이드에서 이름이 비슷한 게이트웨이 연결 작업을 사용하는 뜻이 아닙니다. 후자는 기존 APIM을 연결하는 다른 워크플로입니다.

MCP 도구 등록 및 페더레이션

  1. MCP 서버 → MCP 서버 추가를 엽니다. 마법사는 원본과 확인 단계로 구성됩니다.
  2. 원격 MCP URL, OpenAPI 명세 파일/URL 또는 기본 제공 커넥터 중 원본을 선택합니다. 하나의 논리 서버에 여러 원본 유형을 함께 사용할 수 있습니다.
  3. 각 백엔드에 고유한 YOUR_MCP_BACKEND_NAME을 지정합니다. 이 이름은 생성되는 도구 이름의 접두사가 됩니다. 예: YOUR_MCP_BACKEND_NAME_addANewPetToTheStore. 나중에 이름을 바꾸면 클라이언트에 보이는 이름도 바뀝니다.
  4. 클라이언트 런타임 키 인증과 별개로 업스트림 인증을 구성합니다. 선택지는 없음, API Key, OAuth 2.0, 관리 ID입니다. 없음은 원문의 인증 없는 시연 API에만 적합했습니다.
  5. 다른 백엔드 추가로 원본을 더 통합한 다음 논리 서버를 확인합니다.
  6. 엔드포인트 URL, 백엔드, 업스트림 인증, Streamable HTTP 프로토콜 및 실패 모드를 검토합니다. 백엔드 하나의 장애로 통합 서버 검색이 실패할 수 있다면 요청 실패 같은 설정이 중요합니다.
  7. 정책 및 모니터링 탭을 검토하고 사용을 선택해 애플리케이션 팀에 제공할 연결 코드 조각을 가져옵니다.

업스트림 MCP 엔드포인트 자체를 기존 APIM 서비스가 노출할 수도 있습니다. 원문은 기존 API 자산을 다시 구축하지 않고 재사용하기 위해 이 구성을 사용했습니다. OpenAPI 요약/설명은 도구 설명이 되었고, 요청 본문 스키마는 JSON Schema inputSchema 정의가 되었습니다. 따라서 명세의 품질은 도구 검색과 호출 정확도에 직접 영향을 줍니다.

POST https://YOUR_GATEWAY_HOST/default/toolservers/YOUR_MCP_SERVER_NAME/mcp
api-key: YOUR_RUNTIME_ACCESS_KEY
Content-Type: application/json
Accept: application/json, text/event-stream

{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}

원문에서는 정상적인 tools/list 결과를 받았습니다. Streamable HTTP는 Accept 헤더에 text/event-stream을 포함해야 했습니다. 모델과 도구는 동일한 게이트웨이 호스트와 런타임 키를 공유했습니다. 카탈로그는 자산 연결 예제, 즐겨찾기 및 Ctrl+K 명령 팔레트(macOS에서는 Command+K)도 제공했습니다.

모델 호출과 Responses 기반 에이전트

배포 경로나 날짜 기반 api-version 쿼리 대신 표준 OpenAI 호환 채팅 완성 경로를 사용하세요. 원문의 성공 응답은 HTTP 200, 모델 gpt-5-mini-2025-08-07, 콘텐츠 OK를 반환했습니다. 사용량은 프롬프트 토큰 8개, 완성 토큰 75개, 총 83개였으며 완성 토큰에 추론 토큰 64개가 포함되었습니다. 따라서 화면에 표시되는 답변이 짧더라도 상당한 추론 토큰을 소비할 수 있습니다.

POST https://YOUR_GATEWAY_HOST/default/models/openai/v1/chat/completions
api-key: YOUR_RUNTIME_ACCESS_KEY
Content-Type: application/json

{"model":"YOUR_GATEWAY_MODEL_NAME","messages":[{"role":"user","content":"Say OK"}]}

요청의 모델 등록 이름과 응답의 실제 공급자 모델 ID는 다를 수 있습니다. 별도 개념으로 기록하세요. OpenAI SDK 코드에는 default_headers={"api-key": API_KEY}를 명시적으로 설정해야 합니다. SDK의 api_key 인수로만 키를 전달하면 일반적으로 Authorization: ******가 생성되며 문서에 명시된 게이트웨이 헤더를 구현하지 않습니다. 원문 후반부에서 작동한 Responses 예제는 SDK가 요구하는 더미 값으로 api_key="unused"를 사용하고 실제 키를 default_headers로 전달했습니다. 다운로드 가능한 스크립트도 이 패턴을 따릅니다.

관찰된 응답 필드해석
x-ms-served-model실제 제공된 내부 모델. 이 테스트에서 요청이 백엔드에 도달했음을 보여 주는 유용한 근거
x-ratelimit-key호출자의 키 이름이 아니라 YOUR_GATEWAY_MODEL_NAME이 표시됨
x-ratelimit-limit-requests / x-ratelimit-limit-tokens관찰한 한 구성에서는 분당 요청 1개와 토큰 1,000개를 반환
x-ratelimit-remaining-requests / x-ratelimit-remaining-tokens예제에서는 0과 992를 반환. 애플리케이션은 사용 가능한 헤더로 호출 속도를 조절할 수 있음
x-ratelimit-renewalperiod-*관찰값은 60초. 모든 reset/renewal 변형이 존재한다고 가정하지 말고 실제 헤더 집합을 검사
x-ms-rai-invoked예제에서 true이며 백엔드의 책임 있는 AI 처리를 나타냄
apim-request-id / x-ms-region요청 상관 관계 식별자 / East US 2

Responses API는 previous_response_id를 통한 대화 이어가기와 server_url이 게이트웨이 자체 MCP 엔드포인트를 가리키는 type=mcp 도구를 지원했습니다. 애플리케이션 측 도구 실행 루프를 요구하지 않고 모델 서비스가 도구 실행을 처리했습니다. Responses 출력에는 mcp_list_tools와 mcp_call 항목이 포함되어 요청한 도구와 인수를 보여 주었습니다. 원래 시연에서는 require_approval=never를 사용했습니다. 이는 도구 작업을 자동으로 허용하므로 쓰기 가능한 도구에서 사용자가 모르는 기본값으로 사용하기에는 부적합합니다. 함께 제공하는 스크립트는 always/never를 명시적으로 선택하도록 요구하며 always를 선택하면 mcp_approval_request 응답을 대화형으로 처리합니다. 프롬프트, 도구 인수 또는 진단 로그에 개인정보나 비밀을 넣지 마세요.

정책 구성과 카운터 차원

유형 → 자산 → 구성을 통해 정책을 추가합니다. 정책은 게이트웨이 전체에 자동 적용되는 것이 아니라 선택한 자산에 연결됩니다. 여러 자산을 선택할 수 있고 모델마다 다른 설정을 적용할 수 있습니다.

정책자산 유형구성과 목적
콘텐츠 안전모델 및 MCP 서버증오, 폭력, 자해, 성적 콘텐츠. 범주마다 엄격, 균형, 관대 또는 끄기
IP 필터모델 및 MCP 서버IP 주소/CIDR 범위 허용 또는 거부
토큰 속도 제한모델만기간별 허용 토큰. 호출자 ID 또는 호출자 IP 주소
요청 속도 제한모델 및 MCP 서버갱신 기간별 호출 수. 모델과 도구 경로를 요청 루프로부터 보호

검토한 문서에서 토큰 정책은 분/시간/일 단위 기간을 제공했습니다. 테스트는 분당과 호출자 ID를 사용했습니다. 애플리케이션별 키를 분리하면 이 차원을 애플리케이션 예산과 맞출 수 있습니다. 반면 호출자 IP는 동일한 NAT 주소 뒤의 클라이언트를 하나로 묶으므로 많은 네트워크에서 애플리케이션별 경계로 신뢰하기 어렵습니다. MCP 서버에도 요청 제어를 적용하세요. 모델에만 적용되는 토큰 정책은 반복되는 도구 호출을 제한할 수 없습니다.

측정된 토큰 제한: 응답 후 집계와 초과 사용량 이월

테스트에서는 호출자 ID 기준 분당 100토큰 제한을 연결하고 완성 토큰 10,000개를 허용하는 요청을 보냈습니다. 첫 요청은 프롬프트 토큰 12개와 완성 토큰 1,345개로 성공했으며, 완성 토큰에는 추론 토큰 576개가 포함되어 총 1,357개였습니다. 다음 요청은 HTTP 429와 Retry-After: 747, {"statusCode":429,"message":"Token limit is exceeded. Try again in 747 seconds."}를 반환했습니다.

이는 해당 평가에서 응답 후 집계를 보여 줍니다. 게이트웨이는 비용이 큰 요청을 완료하도록 두고 사용량으로 카운터를 갱신한 후 후속 요청을 차단했습니다. 크기가 큰 첫 요청을 예측해 거부하지 않았습니다. 초과 사용량은 60초 후 완전히 초기화되지 않고 이월된 부채처럼 동작했습니다.

Excess = 1,357 - 100 = 1,257 tokens
Recovery estimate = 1,257 / 100 TPM = 12.57 minutes = 754 seconds
Observed Retry-After = 747 seconds, approximately consistent with time between calls.

이후 Retry-After 값은 약 20초 동안 708에서 687로 감소했습니다. 초과 사용량이 남아 있는 동안 5토큰 요청도 거부되었고 차단은 12분 넘게 지속되었습니다. 따라서 매우 낮은 제한은 한 번의 초과 사용 이후 장시간 서비스 중단을 일으킬 수 있습니다. 실제 요청의 평균 토큰 수 × 목표 RPM에 여유분을 더해 예산을 정하고, 추론 사용량을 포함하며, max_completion_tokens로 클라이언트 출력을 제한하고, 통제된 부하에서 복구를 측정하세요. 이 정책은 엄격한 요청별 지출 상한이 아닙니다.

원문 테스트의 429 발생 원인게이트웨이 정책Foundry 할당량
본문APIM statusCode/message 객체rate_limit_exceeded가 포함된 OpenAI error 객체
Served-model 및 rate-limit 헤더차단된 응답에 없음관찰된 백엔드 응답에 있음
Retry-After 예747초, 누적 초과 사용량에 비례30초

오류를 분류할 때 본문과 헤더 근거를 함께 사용하세요. 관찰된 헤더 차이는 진단용 경험칙이지 모든 공급자나 향후 게이트웨이 버전에 적용되는 보편적 계약이 아닙니다. 백엔드 제한과 게이트웨이 초과 사용량에는 실질적으로 다른 백오프 동작이 필요할 수 있습니다.

측정된 요청 제한: 수락 제어와 빠른 복구

비교 정책은 60초당 호출 5개를 허용하고 모델과 MCP 서버를 모두 대상으로 했습니다. UI는 30초, 60초, 2분, 5분을 제공했습니다. 작은 모델 요청 7개를 순차적으로 보내자 HTTP 200 응답 5개, Retry-After: 1을 포함한 여섯 번째 HTTP 429 응답, 이후 HTTP 200이 나왔습니다. 거부된 응답에는 Rate limit is exceeded. Try again in 1 seconds.가 표시되었고 백엔드의 served-model 헤더는 없었습니다.

토큰 집계와 달리 요청 수는 전달 전에 확인할 수 있습니다. 여섯 번째 호출은 추가 백엔드 소비를 만들지 않고 거부되었으며, 원문은 일곱 번째 호출의 빠른 복구를 롤링 방식 용량 갱신으로 해석했습니다. 관찰된 1초는 모든 요청에 보장되는 복구 시간이 아닙니다. 남용과 에이전트 루프에는 요청 제한을, 사용량 제어에는 토큰 제한을 사용하세요. 어느 하나만으로는 고빈도 트래픽과 비용이 매우 큰 단일 완성을 모두 방지할 수 없습니다.

콘텐츠 안전: 게이트웨이 차단과 모델 거절은 다름

관찰한 포털은 네 가지 범주 사전 설정만 제공했으며 Content Safety 리소스를 요청하지 않았습니다. 정책 생성 전후의 역할 할당에는 기존 Foundry 역할만 있었고 Cognitive Services User 역할은 추가되지 않았습니다. 리소스 목록에도 새로 생성된 Content Safety 계정은 없었습니다. 원문은 이를 완전 관리형 게이트웨이 기능으로 해석했습니다. 이는 고객이 선택한 Content Safety 백엔드가 필요하다는 검토 문서와 달랐습니다. 해당 UI에는 Prompt Shields, 차단 목록, 로그 전용 모드, 4/8단계 심각도 제어가 보이지 않았습니다. 이 중 필요한 기능이 있다면 현재 동작을 다시 확인하세요.

유해 콘텐츠 생성 요청은 모델에 도달했고 모델은 HTTP 200 답변에서 거절했습니다. 원문은 추론 토큰 832개를 포함한 총 1,165토큰을 기록했으며, 프롬프트 필터의 폭력 분류는 안전이었습니다. 모델이 요청을 거절했다고 게이트웨이 정책이 이를 차단한 것은 아닙니다. 텍스트 분류와 의도 추론은 서로 다른 문제입니다. 모델 거절은 백엔드 처리 이후에 발생하며 토큰을 소비할 수 있습니다.

유해한 것으로 분류된 콘텐츠를 포함한 별도 테스트는 백엔드에 도달하기 전에 HTTP 403과 {"statusCode":403,"message":"Request failed content safety check."}로 차단되었습니다. 백엔드 응답에서 관찰된 served-model, responsible-AI, rate-limit, APIM-request 헤더는 없었습니다. 원문은 게이트웨이가 차단한 이 요청에 모델 토큰 소비가 없다고 기록했습니다. 이것이 모든 정책 기능에 서비스 요금이 없음을 뜻하지는 않습니다. 검토 문서에는 400으로 나와 있었지만 실제 측정된 게이트웨이 응답은 403이었습니다.

계층시점관찰된 응답모델 토큰 영향
게이트웨이 콘텐츠 안전모델 호출 전APIM 메시지를 포함한 403거부된 요청의 백엔드 토큰 없음
백엔드 필터 또는 모델 정렬Foundry 도달 후200 거절 또는 공급자별 content_filter 오류처리/사용량은 공급자 응답에 따라 다름. 거절 테스트에서는 토큰을 소비함

IP 필터링과 프라이빗 네트워킹

IP 필터 UI는 허용/거부 작업과 쉼표로 구분한 CIDR 목록을 받습니다. 단일 IPv4 호스트에는 YOUR_CLIENT_IPV4/32를 사용해야 합니다. 실수로 넓은 접두사를 대입하지 마세요. /10은 400만 개가 넘는 주소를 포함합니다. 테스트 호출자를 포함한 범위를 거부하자 런타임 키가 유효해도 HTTP 403과 {"statusCode":403,"message":"Forbidden"}이 반환되었습니다. 이는 해당 테스트에서 추가적인 네트워크 기반 권한 경계를 입증하지만, 키 인증에 대한 IP 필터링의 내부 실행 순서를 입증하지는 않습니다.

콘텐츠 안전도 같은 403 상태를 사용하며 두 제한 정책은 429를 사용합니다. 상태만이 아니라 안전하게 기록할 수 있는 오류 메시지도 기록하세요. 허용 목록 계획에 모니터링/관리 원본 범위를 포함하고 NAT 집계를 이해하며 롤백을 준비하세요. 런타임 IP를 차단하는 것 자체가 Entra로 인증하는 관리 포털에서 정책을 수정하지 못하게 하지는 않습니다.

정책관찰된 거부 메시지복구 조건

네트워킹 제어는 정책 카드와 별개입니다. 인바운드 기본값은 프라이빗 엔드포인트가 없는 퍼블릭 네트워크 액세스: 사용이었습니다. 사용 안 함은 프라이빗 엔드포인트를 통한 액세스만 허용합니다. 아웃바운드 기본값은 퍼블릭 라우팅이었고 프라이빗 백엔드를 위한 프라이빗 라우팅을 사용할 수 있었습니다. 인바운드 액세스 잠금과 프라이빗 백엔드 액세스 활성화는 독립적인 변경입니다. 퍼블릭 클라이언트를 허용하면서 프라이빗 Foundry 백엔드에 접근할 수도 있습니다. 이는 기존 주입형 게이트웨이를 서브넷 안에 배치하는 아키텍처와 다릅니다. 배포 전에 서브넷 위임/크기, DNS, 라우팅 및 현재 프라이빗 네트워킹 문서를 검토하세요. 원문은 모든 관련 자산에 기본 콘텐츠 안전/IP 제어를 적용하고 비용이 큰 모델이나 제약이 있는 도구에 속도 제한을 별도로 조정할 것을 권고했습니다.

  3. 새로 만들기는 게이트웨이와 동일한 구독, 리소스 그룹, 지역에 Insights 리소스를 자동 생성합니다. 이 필드는 읽기 전용이었습니다. 다른 위치가 필요하면 원하는 Insights 리소스를 별도로 생성하고 기존 항목을 선택하세요.
  4. 시스템 할당 또는 사용자 할당 ID를 선택합니다. Monitoring Metrics Publisher가 부여되었는지 확인합니다.
  5. 실제 범위를 검사합니다. 이 전용 계층 테스트에서는 Insights 리소스가 아니라 관리형 Data Collection Rule이었습니다. 수집 문제를 해결할 때 DCR RBAC를 확인하세요.
  6. 화면에 표시되는 Insights 리소스뿐 아니라 관리형 리소스 그룹에 자동 생성된 관리형 Azure Monitor Workspace도 검사합니다.

제품 아키텍처는 OpenTelemetry 용어를 사용하지만 원문에서 관찰된 것은 토큰 사용량 메트릭뿐이었고 요청 로그, 추적 또는 MCP 호출 메트릭은 아니었습니다. 포털은 /api/v1/query_range로 관리형 Prometheus 엔드포인트를 쿼리했습니다. 메트릭 이름은 Azure 전용 네임스페이스인 azure.ai_gateway.client.token.usage였습니다. KQL이 아니라 PromQL로 쿼리하세요.

increase({__name__="azure.ai_gateway.client.token.usage",
          microsoft.appresourceid="/subscriptions/YOUR_SUBSCRIPTION_ID/resourceGroups/YOUR_RESOURCE_GROUP/providers/microsoft.insights/components/YOUR_APPLICATION_INSIGHTS_NAME",
          azure.ai_gateway.workspace="default"}[7200s])

구성 직후 포털은 HTTP 400과 Monitoring account=YOUR_MONITORING_ACCOUNT_ID not found를 보고했습니다. 원문에서는 프로비저닝 전파 지연이었고 몇 분 기다린 뒤 다시 시도를 선택하자 해결되었습니다. 이 증상만으로 구성을 자동 재생성하지 마세요. 오류가 계속되면 RBAC, 작업 영역 및 엔드포인트 조사가 필요합니다.

대시보드는 정규화된 토큰과 공급자 기본 토큰, 모델 필터, 1H/24H/7D/30D 기간 및 Azure Portal에서 열기를 제공했습니다. 빈 대시보드는 모델을 호출한 후 수집이 완료되면 새로 고치도록 안내했습니다. 이후 측정에서는 새 모델 사용량이 수초 내에 나타났지만, 보장된 수집 지연 시간은 아닙니다. 기존 Insights를 선택하면 데이터는 선택한 Azure 구독에 유지되며 사용자 지정 OTLP 대상에는 해당 구성과 공급자 약관이 적용됩니다.

두 개의 별도 런타임 키로 두 모델을 호출한 후 24시간 공급자 기본 보기에는 다음 원문 값이 표시되었습니다. 리소스/모델 등록/키 이름은 자리 표시자로 대체했으며 공개된 내부 모델 유형은 유지했습니다.

두 백엔드 모두 Foundry였지만 공급자 추정 로직은 한 별칭을 Other로, 다른 별칭을 OpenAI로 분류했습니다. 원문은 이를 등록 이름과 사용량 필드에 기반한 추정 때문으로 보았습니다. 가능하면 모델 ID와 유사한 등록 이름을 사용하고 추정을 무조건 신뢰하지 말고 공급자 그룹화를 검증하세요.

API 키별 토큰 사용량 패널에는 YOUR_APP_1_KEY_NAME이 13.6K, YOUR_APP_2_KEY_NAME이 5.6K로 표시되었습니다. 각 키가 다른 모델을 호출했으므로 이 실험에서는 키 총량과 모델 총량이 일치했습니다. 이는 애플리케이션 수준 보고를 사용할 수 없다는 원문 초기 가정을 바로잡았습니다. 차원은 키의 비밀 값이 아니라 이름입니다. x-ratelimit-key 응답 헤더 값이 모델이라고 해서 대시보드의 키 기반 귀속이 부정되는 것은 아닙니다.

애플리케이션 예산, 제한 사항 및 도입 결정

  1. YOUR_APPLICATION-YOUR_ENVIRONMENT-key 같은 명확한 이름 규칙으로 애플리케이션/환경별 런타임 키를 발급합니다.
  2. 독립적인 호출자들이 NAT 기반 예산을 공유하지 않도록 토큰 제한 카운터에서 호출자 ID를 선택합니다.
  3. 지원되는 응답 헤더로 요청 속도를 조절합니다. 모델 값이 들어 있는 헤더를 애플리케이션 ID로 취급하지 마세요.
  4. 프롬프트, 개인정보 또는 자격 증명을 포함하지 않고 apim-request-id나 애플리케이션 상관 관계 값으로 요청을 연결합니다.
  5. 재무 대사에는 공급자 청구서 또는 Azure Cost Management를 사용합니다. 원문 문서는 토큰 메트릭을 재무 보고 데이터가 아닌 사용량 추정치라고 설명했습니다.

키/모델 차원은 일반적인 애플리케이션별 비용 가시화에 편리하지만 팀/부서/기능 차원에는 다른 계측이나 명시적 counter-key 식 같은 기존 APIM 정책이 필요합니다. 스트리밍 또는 통과 전달 응답에 사용량이 없으면 0이 아니라 알 수 없음입니다. 키 교체 시 연속성은 검증되지 않았습니다. 보고서에서 모델별 키 범위 지정은 사용할 수 없었으며 MCP 호출은 토큰 원격 분석에 나타나지 않았으므로 클라이언트 측 도구 감사가 여전히 필요했습니다.

원문은 프로덕션 SLA 요구 사항, 한국/아시아 배포 요구 사항, 재현 가능한 IaC 파이프라인, 기존 API 자산과의 통합, 의미 체계 캐싱, 부하 분산/회로 차단기, 사용자 지정 차원 및 예측 가능한 공개 가격이 필요할 때 기존 APIM을 권장했습니다. 전용 계층은 비핵심 다중 공급자 실험, 빠른 MCP 페더레이션, 적은 구성으로 진행하는 개념 증명, 카탈로그 셀프 서비스 및 기본 제공 키별 토큰 보고에 적합하다고 보았습니다. 요구된 지역 밖에 있는 미리 보기 지역이 왕복 지연 시간이나 데이터 상주 요구 사항을 충족한다고 가정할 수 없습니다.

통제된 파일럿을 넘어가기 전에 SLA 및 지역 가용성, 가격과 Cost Management 귀속, 모델/도구/키/처리량 제한, 템플릿 기반 생성, 의미 체계 캐시/풀/회로 차단기 지원, 키 교체 연속성, 사용자 지정 OTLP 내보내기의 키 차원, 요청 로그와 추적 내보내기, MCP 트래픽 보고 및 세분화된 키 범위를 다시 확인하세요. 비핵심 워크로드부터 시작하고 롤백 경로를 유지하며 실제 대상 버전에서 측정 기반 정책 테스트를 다시 실행하세요.

제공 템플릿과 참조 문서

다운로드는 원문에서 파생하고 민감 정보를 제거한 템플릿으로 사용자의 값을 입력해야 합니다. gateway-requests.http에는 채팅, MCP 검색 및 명시적으로 표시한 정책 테스트 요청이 포함됩니다. responses-agent.py에는 Python과 openai 패키지, AI_GATEWAY_HOST, AI_GATEWAY_API_KEY, AI_GATEWAY_MODEL_NAME, AI_GATEWAY_MCP_SERVER_NAME, AI_GATEWAY_MCP_SERVER_LABEL 및 명시적 AI_GATEWAY_MCP_APPROVAL 값이 필요합니다. 자동 도구 승인을 의도적으로 정당화할 수 있는 경우가 아니라면 always를 사용하세요. resource-commands.sh는 비용이 발생하는 프로비저닝 참조 자료이며 명시된 모든 환경 변수가 필요합니다. 자동 종단 간 게이트웨이 배포가 아닙니다. token-usage.promql에는 리소스 식별자를 매개 변수화한 원문 쿼리가 포함됩니다. 이 공개판을 위해 어느 파일도 클라우드에서 테스트하지 않았습니다.

참고 리소스

원본 자료를 기반으로 변수화한 참고 리소스입니다. 자리표시자, 권한, 의존성과 배포 영향을 검토한 뒤 사용하세요. 한 번에 자동 배포되는 패키지는 아닙니다.

  • gateway-requests.http

    원문에서 파생하고 민감 정보를 제거한 채팅, MCP 검색 및 수동 제어 정책 테스트 요청입니다.

    환경 변수로 구성하며 도구 승인 방식을 명시적으로 선택하는 Responses/MCP 에이전트 템플릿입니다.

  • resource-commands.sh

    원문에서 파생한 Foundry 프로비저닝 및 게이트웨이 검사 명령입니다. 값 지정과 별도의 실행 승인이 필요합니다.

  • token-usage.promql

    원문의 PromQL 토큰 사용량 쿼리를 매개 변수화한 템플릿입니다.
