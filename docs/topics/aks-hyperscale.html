AKS Hyperscale Control Plane: Size the Bottleneck, Read the Metrics

A practical Preview guide to H2/H4/H8, independent etcd partitions, supported lifecycle changes, schema v2 managed Prometheus, and what a small October 1 observation can—and cannot—prove.

English editionParameterized examples2026-10-07

The Korean edition follows this reviewed English article. Code, downloadable resources, diagram labels, and English Azure Portal captures are shared between editions.

Environment-specific evidence. Measurements and preview behavior reflect the source investigation. They are not current service guarantees. All configuration values must be supplied for your own environment.

1. Start with the control-plane problem

AKS Hyperscale preprovisions control-plane capacity for workloads with unusually high Kubernetes API concurrency, Pod churn, or scheduling demand. It is not a worker-node scaling feature. The API server, scheduler, controllers, and etcd manage desired state; worker nodes supply the CPU, memory, networking, and storage that run applications. A larger control plane does not create GPU capacity, repair an image pull, or make an unsuitable node satisfy a Pod's placement constraints.

This is an unofficial technical field note, published October 7, 2026. The observations are historical, from October 1, 2026, and are not new tests, product guarantees, pricing policy, or an SLA. Hyperscale remains Preview in the public documentation checked for this article. That documentation says AKS previews are provided as-is/as-available, excluded from service-level agreements and limited warranty, supported on a best-effort basis, and not intended for production use. Recheck the current terms and support matrix before any decision.

The default AKS control-plane mode dynamically adjusts capacity and remains the documented recommendation for most workloads. Hyperscale is worth evaluating when representative evidence points to control-plane pressure: for example, many deployment controllers acting together, distributed batch-job creation, or predictable bursts of API activity. Public documentation discusses mission-critical use cases, but that positioning does not override its Preview production-use warning.

Separate three questions before selecting a size: are API clients waiting for service, are Pods waiting for scheduling, or are already scheduled Pods waiting to become Ready? These are different queues with different owners. Record client-side timeouts too: requests that never reach the API server may not appear in its request counters.

2. H2, H4, and H8 describe different capacity dimensions

The following figures are the published sizing characteristics checked on October 7, not measured results from this article. The official table calls the concurrency column “Kube API Server flow control executing requests”; the monitoring guidance expresses current usage as API Priority and Fairness (APF) execution seats. Do not reinterpret the values as application requests per second.

SizePublished flow-control concurrencyPublished scheduling rate, Pods/setcd partition countStorage per partition
H21,75020068 GiB
H43,50030068 GiB
H87,00040068 GiB

Seats are concurrency, not request rate

An APF seat is a unit of concurrent work. Some requests, such as large lists, can occupy multiple seats; request duration also affects how long seats remain occupied. The same request rate can therefore produce different occupancy. APF divides work into priority levels with queuing and concurrency controls, so a particular level can be constrained even when a cluster-wide sum looks small. Do not change APF policies simply to make a graph fall.

Scheduling is not application readiness

Scheduling chooses a feasible node and binds the Pod. Image downloads, volume attachment, container startup, initialization, and readiness probes happen later. Scheduler attempt counters can include unsuccessful attempts and retries; their rate is not the number of unique Pods becoming Ready. Investigate resource requests, taints, affinity, and storage constraints before attributing unschedulable Pods to control-plane capacity.

Concurrency doubles between these published sizes, but the scheduling figures increase from 200 to 300 to 400—not by a factor of two at each step. The field guide already flags an upstream claim to the contrary. There is no measured speedup, price-per-Pod comparison, or availability promise here. Standard/Premium pricing tier and H2/H4/H8 control-plane size are separate settings; neither replaces worker sizing or a current cost review.

3. Six etcd partitions are six separate limits

Hyperscale separates etcd into six clusters by resource category. The storage number is per partition, not an interchangeable pool that any resource type can consume. Moving from H2 to H4 or H8 does not increase the published partition count or per-partition storage.

PartitionStored Kubernetes resourcesOperational question
EventsEvent objectsIs repeated failure producing avoidable event churn?
LeasesCoordination leasesIs the coordination-object population expected?
NodesNode objectsDo node records match the intended fleet lifecycle?
PodsPod objectsAre completed or obsolete workload objects accumulating?
SecretsSecret objectsAre object size and retention appropriate, without exposing contents?
DefaultAll remaining resources, including Deployments, Services, and ConfigMapsAre retained custom resources or configuration objects growing?

Track the fullest partition and its growth, not the average across all six. Replica database sizes must not be added together as though each replica represented different stored objects. Inspect the returned partition and instance labels, then take the maximum across replicas within each partition. If the partition identity is absent, resolve that telemetry gap rather than inventing a label.

The public page recommends designing for 2 GB or less per partition and reviewing resource counts when a partition approaches 50% utilization. It also describes an 8 GB hard limit in prose while its sizing table says 8 GiB. This unit inconsistency is unresolved here: the table above preserves GiB, while the recommendations preserve the page's wording. Do not turn the discrepancy into an exact byte-based alert threshold without confirmation. A larger control-plane size is not a storage-retention strategy; review object lifecycles before any approved cleanup.

4. Distinguish migration from size adjustment

The public Hyperscale guide explicitly documents resizing an existing Hyperscale cluster. Its “new clusters only” limitation concerns adding the profile to an ordinary cluster, not changing the size of a profile already present. This resolves the older upstream statement, noted by the field guide, that changing H4 to H2 or H8 required a rebuild.

OperationDocumented position on October 7, 2026Planning consequence
Ordinary control plane to HyperscaleCannot add the profile to an existing clusterCreate a new eligible cluster and plan workload/data migration
H2, H4, or H8 to another Hyperscale sizeSupported through the control-plane size update operationReview demand and change risk; verify resulting profile and telemetry
Hyperscale to ordinary control planeCannot remove the profile after creationPlan replacement and migration; deletion is not a rollback procedure
Provisioning toolsAzure CLI with aks-preview, REST API, and ARM templates are documented; SDKs and Terraform are not supported in the Preview guideDo not infer support merely because a client can submit a property

The following PowerShell example is illustrative, not executed. The first command is a write: it requests an H4 control-plane size for an already-enabled Hyperscale cluster. It does not enable Hyperscale on an ordinary cluster, resize worker pools, or guarantee a disruption-free change. Replace the placeholders, obtain change approval, and review current service behavior before use. The second command only reads the resulting profile.

$ResourceGroup = "REPLACE_RESOURCE_GROUP"
$ClusterName = "REPLACE_CLUSTER_NAME"
az aks update --resource-group $ResourceGroup --name $ClusterName --control-plane-scaling-size H4
az aks show --resource-group $ResourceGroup --name $ClusterName --query controlPlaneScalingProfile --output json

A replacement plan must cover identities, network dependencies, policies, persistent data, backup/restore validation, DNS or traffic cutover, and a rollback window. The Preview limit of one Hyperscale cluster per subscription per region can constrain a side-by-side replacement. Resolve quota and placement before depending on that migration pattern; do not delete the current cluster merely to free a slot.

5. Establish eligibility with read-only discovery

As checked on October 7, the public prerequisites are an AKS Standard or Premium tier, Kubernetes 1.33.0 or later, the Azure CLI extension aks-preview version 21.0.0b8 or later, and the subscription feature ControlPlaneScalingProfilePreview registered. Free tier is not supported. The profile is selected at new-cluster creation, and the Preview permits one Hyperscale cluster per subscription per region. General AKS and worker VM quotas remain separate constraints.

These examples are read-only discovery commands, not an executed validation. Use an already authenticated, deliberately selected Azure subscription and Kubernetes context. They do not sign in, switch subscriptions, download credentials, install an extension, or register a feature. Keep any environment-specific output private.

$Location = "REPLACE_LOCATION"
$ResourceGroup = "REPLACE_RESOURCE_GROUP"
$ClusterName = "REPLACE_CLUSTER_NAME"
az version
az extension show --name aks-preview --query version --output tsv
az feature show --namespace Microsoft.ContainerService --name ControlPlaneScalingProfilePreview --query properties.state --output tsv
az provider show --namespace Microsoft.ContainerService --query registrationState --output tsv
az aks get-versions --location $Location --output table
az aks show --resource-group $ResourceGroup --name $ClusterName --query "{version:kubernetesVersion,tier:sku.tier,profile:controlPlaneScalingProfile,identityType:identity.type}" --output json
kubectl config current-context
kubectl get configmap ama-metrics-settings-configmap --namespace kube-system --output yaml

An extension-not-found result means tooling still needs preparation; a missing ConfigMap is not itself proof that managed Prometheus is disabled. The version list establishes Kubernetes offerings in that region, not Hyperscale eligibility, quota, or guaranteed capacity. Confirm those separately using the current Hyperscale and quota documentation. Registration, provider refresh, extension installation, and cluster creation all change state and are intentionally left to the approved setup procedure.

Azure CNI Overlay is the public guide's recommendation for large Pod populations, not a requirement that excludes every other CNI. It also advises against the Azure Policy add-on for large clusters because of API load. Treat those as architecture trade-offs: do not remove required governance merely to follow a performance recommendation.

6. Make collection explicit before interpreting a graph

Azure platform metrics and managed Prometheus are different telemetry surfaces. The Hyperscale page maps platform seat usage apiserver_flowcontrol_executing_seats to the Prometheus gauge apiserver_flowcontrol_current_executing_seats; platform scheduling uses scheduler_schedule_attempts_rate, while the Prometheus counter is scheduler_schedule_attempts_total. Do not paste a platform metric name into PromQL and assume an empty result means no load.

The managed control-plane metrics guide requires managed identity authentication and Azure Monitor managed service for Prometheus; it lists Azure Private Link as unsupported for this collection feature. Self-hosted Prometheus is not the supported substitute for complete control-plane replica visibility. Control-plane scraping runs outside the node-side ama-metrics add-on, so healthy node collectors alone do not prove control-plane collection.

Managed Prometheus onboarding and enabling control-plane metrics are separate steps. For a cluster already onboarded to the intended workspace, the following illustrative write enables control-plane collection. It can increase telemetry ingestion and cost. It does not choose or validate a workspace and has not been executed here.

az aks update --resource-group $ResourceGroup --name $ClusterName --enable-control-plane-metrics

Verify access to the linked Azure Monitor workspace and query permission before diagnosing data loss. The public guide identifies Monitoring Reader or Monitoring Contributor for viewing workspace data. Configuration propagation and first samples can take several minutes; enabling collection does not backfill earlier history. Start with raw series in the time range after enablement, then use range functions after enough samples exist.

Schema v2: merge, do not overwrite

The October 1 source used schema v2, with separate cluster-metrics and controlplane-metrics sections. API-server and etcd targets are enabled by default for control-plane collection; the scheduler is not. The minimal profile includes the API request counter but does not list current executing seats or APF rejected requests. Add those two metrics deliberately rather than enabling every API-server metric.

This YAML is a configuration fragment, not an apply-ready manifest. Merge it into the reviewed settings ConfigMap while preserving its metadata, other targets, keep-lists, scrape intervals, and cluster-side configuration. The two keep-list entries extend minimal collection; this fragment does not enable scheduler collection. With an existing schema v1 file, follow the documented migration rather than mixing schema versions.

data:
  schema-version: v2
  controlplane-metrics: |-
    default-targets-scrape-enabled: |-
      apiserver = true
      etcd = true
    default-targets-metrics-keep-list: |-
      apiserver = "apiserver_flowcontrol_current_executing_seats|apiserver_flowcontrol_rejected_requests_total"
    minimal-ingestion-profile: |-
      enabled = true

In v2, use default-targets-scrape-enabled, target names without the old controlplane- prefix inside the control-plane section, and nested minimal-ingestion-profile configuration. Enabling kube-scheduler and retaining its required metrics is a separate reviewed change if scheduling analysis is needed. A keep-list entry establishes intent, not proof that the target exposes or forwards that metric.

Applying a complete reviewed ConfigMap is a Kubernetes write that changes collection behavior. The next command shows that effect explicitly; do not apply the fragment above as the complete file. Read back the merged settings, then confirm actual series at the workspace. Disabling all managed Prometheus collection is not a narrowly scoped rollback for a control-plane-only change.

$ReviewedConfigPath = "REPLACE_WITH_REVIEWED_COMPLETE_CONFIGMAP.yaml"
kubectl apply --filename $ReviewedConfigPath

7. Query the right type, scope, and time window

All PromQL below is read-only and illustrative. Replace REPLACE_SCOPE_LABEL and REPLACE_SCOPE_VALUE with a verified label/value selecting exactly one cluster; replace REPLACE_TARGET_LABEL and REPLACE_TARGET_VALUE with the relevant control-plane target label/value. Discover these in the workspace series browser—do not assume a label name, cluster alias, or target value. Use the API-server target for the first group, the scheduler target for scheduling, and etcd for database size. Preserve this scope on every numerator and denominator. Verify replica identity and duplicate ingestion before aggregation.

Series count is a collection check; a gauge is occupancy

count(apiserver_request_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"})
count(apiserver_flowcontrol_current_executing_seats{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"})

sum(apiserver_flowcontrol_current_executing_seats{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"})

The first two expressions count returned label combinations, not requests or occupied seats. The third sums instantaneous gauge values across selected series at each evaluation time. A range graph repeats that calculation over time; it does not add every timestamp together. Do not apply rate() or increase() to this occupancy gauge. Retain per-priority-level views for diagnosis instead of relying only on the global sum.

Counter change and rate answer different questions

sum by (code) (
  increase(apiserver_request_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"}[5m])
)

sum by (code) (
  rate(apiserver_request_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"}[5m])
)

100 *
sum(rate(apiserver_request_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE",code=~"429|5.."}[5m]))
/
sum(rate(apiserver_request_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"}[5m]))

sum(
  increase(apiserver_flowcontrol_rejected_requests_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"}[5m])
)

Apply the range function to each counter before summing so resets can be handled per series. increase() estimates the change over the window and can return fractional values because of extrapolation; rate() gives the average per-second rate. Five minutes is an example analysis window, not a collection interval or a universal alert rule. Choose a window with enough samples and retain the raw series when investigating gaps or restarts.

The percentage combines selected HTTP 429 and 5xx responses over all selected API requests. It is not a capacity score or an application error rate. No matching error series can yield no result; zero traffic can make the denominator zero. Do not mask missing telemetry with an unconditional zero fallback. APF rejections help diagnose flow control, but adding them to HTTP errors can double-count the same requests. Inspect available priority-level and reason labels separately.

Scheduler attempts and per-partition database size

sum by (result) (
  rate(scheduler_schedule_attempts_total{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"}[5m])
)

max by (REPLACE_PARTITION_LABEL) (
  etcd_mvcc_db_total_size_in_bytes{REPLACE_SCOPE_LABEL="REPLACE_SCOPE_VALUE",REPLACE_TARGET_LABEL="REPLACE_TARGET_VALUE"}
) / (1024 * 1024 * 1024)

Verify the scheduler's actual result label and values before interpreting its outcome groups; unsuccessful attempts are not unique failed Pods. The Hyperscale page also lists suffixed scheduler names, but the default collection reference lists the canonical counter used here. Discover the exposed series instead of assuming every documented variant exists. Neither expression measures Pod Ready latency.

Replace REPLACE_PARTITION_LABEL only after identifying the actual resource-partition dimension. The etcd expression returns the largest replica database size per partition in GiB, not a summed database size or percent full. It is a gauge, so no counter rate is applied. If the required partition labels or metric are missing, use the documented platform database-utilization metric with its resource-type dimension or fix collection; do not silently collapse all partitions into one apparent allowance.

8. What the October 1 observation actually establishes

The historical source describes one low-load cluster and a small illustrative scenario of ten Deployments with three Pods each. It confirms schema v2 managed Prometheus configuration and returned API-request and executing-seat series. It does not establish maximum cluster capacity or a matched H2-versus-H4 performance comparison. The API-counter capture and seat capture were taken at different times and must not be correlated as one synchronized load sample.

The Grid evaluation time was 16:37:34.673 KST on October 1. It is a query evaluation timestamp, not evidence that every underlying replica was scraped at exactly that instant. The graph showed an approximate change from 3 to 6; sampling can miss short-lived peaks. The legend mean of 4.45 is not a guaranteed time-weighted mean, and dividing any of these values by 1,750 would not establish an official H2 utilization percentage without aligned metric scope and capacity semantics.

In particular, 53 cumulative HTTP 429 responses do not mean 53 rejections in the most recent thirty minutes, do not establish overload during this scenario, and do not prove that H2 was too small. A 403 points to authorization investigation; a 409 may involve an object-update conflict. A 429 can reflect a constrained APF priority level, and a 503 can involve API-server readiness or an aggregated API backend. Correlate recent-window changes with latency, APF signals, and appropriately protected logs before attributing a cause.

The retained evidence supports a collection-path check and metric-reading lesson. It does not demonstrate sustained saturation, a scheduling-rate measurement, per-partition storage pressure, resize duration, zero disruption, an H4 improvement, or application startup performance. No original screenshots or raw environment output are republished.

9. Turn observations into an operational decision

SignalFirst investigationPotential next step
Sustained API delay with high seats and recent APF rejection growthCheck per-priority-level demand, request mix, list/watch behavior, retries, and webhooksReduce avoidable API work; evaluate another size only with representative evidence
Unschedulable attempts with available API capacityInspect node resources, taints, affinity, volume topology, and Pod requestsFix placement or worker capacity rather than assuming a larger control plane solves it
Scheduled Pods remain unreadyInspect images, volumes, initialization, networking, and probesMeasure the worker/application path separately
One etcd partition grows while others are smallReview resource counts, object size, retention, and replica aggregationPlan safe lifecycle changes; H4/H8 do not add published storage per partition
Empty graphs after a configuration changeVerify workspace access, target enablement, schema, keep-list, labels, and elapsed collection timeRepair observability before interpreting absence as healthy zero load

A useful evaluation plan keeps the same workload shape, operation mix, client concurrency, object population, and observation duration across candidate sizes. Record the size actually reported by the resource, scrape interval, query scope, missing data, client completion times, request latency, error changes, and worker capacity. This is a proposed future method, not a test performed here. Do not claim a benchmark from the ten-Deployment demonstration.

  • Confirm dated Preview eligibility, terms, regional quota, and supported tooling before approving a change.
  • Distinguish an ordinary-cluster migration from an existing Hyperscale size update; retain a data-safe rollback plan.
  • Verify telemetry coverage and counter/gauge semantics before setting alerts or comparing sizes.
  • Keep API concurrency, scheduling attempts, Pod Ready latency, and partition growth on separate panels.
  • Use sustained, correlated signals instead of one cumulative error total or one low-load screenshot.
  • Review current pricing and all telemetry, worker, network, and storage costs separately; this article supplies no price or SLA conclusion.

10. Public references and dated interpretation

These public references were checked on October 7, 2026. They support the feature constraints and metric semantics above, not a claim that any reader's subscription is eligible or that any command was successfully executed. The historical notebook supplies the observations; the public product documentation governs the supported lifecycle description.

  • Microsoft Learn: Hyperscale configuration for AKS using a control-plane scaling profile — sizing, Preview terms, Standard/Premium requirement, prerequisites, new-cluster limitation, resizing, partitions, and monitoring guidance.
  • Microsoft Learn: Monitor AKS control-plane metrics — managed collection, identity and Private Link limitations, schema v2, keep-lists, and workspace access.
  • Microsoft Learn: Default Prometheus metrics configuration — minimal ingestion, target defaults, and canonical metric names. Legacy prefixed section headings do not replace v2 configuration keys.
  • Azure Prometheus collector: public settings ConfigMap — the maintained schema reference; review changes before merging, rather than blindly applying all defaults.
  • Microsoft Learn: AKS resource, SKU, and region limits — general quotas, distinct from the feature-specific one-cluster Preview limit.
  • Kubernetes: API Priority and Fairness — seat occupancy, request width, priority levels, and queuing.
  • Kubernetes: Scheduler — node feasibility, scoring, and binding, rather than application readiness.

Two source-level ambiguities are resolved explicitly: Hyperscale-to-Hyperscale resizing is supported, and scheduling capacity does not double at every size step. Two documentation caveats remain visible: GB versus GiB wording for etcd, and scheduler metric-name variants that require discovery. None is a reason to infer undocumented guarantees.
